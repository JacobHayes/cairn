# Frontend state is machines for lifecycles and functions for the rest

Question (from putting `web/app` and `web/client` on one state architecture, starting with writes): the data layer grew by hand-written stores and per-control hooks, each with its own idea of when async work starts, ends and is dropped, and two of them lost a write's outcome because a component owned it. What decides where XState goes, and where it must not?

Call: a workflow mode gets an XState v5 machine, however small. A workflow mode is a state that decides which async work exists, when it expires, or which events may proceed while work is outstanding. Everything else stays plain: derived values are pure functions computed from their source and never stored beside it (the sync chip's display is `summarize`, a projection with no states of its own); payloads and stored records are plain data, never snapshots; each fact has one owner and others read it through a tagged selector, never a pushed copy; preferences (`useAxis`, `useFrame`) keep their independent values and keyed overrides. Timers are delayed transitions, requests are invoked actors, a busy state does not accept a new start, and cancelling stops the UI waiting without undoing a commit. The rule is in PRACTICES (Frontend state); the first machines are the write and its owners (`a-write-is-an-operation-the-edit-manager-owns`).

Alternatives: XState everywhere, preferences and projections included (a machine with one state and no async work is a store with extra ceremony, and a derived value held in context goes stale beside its source); plain reducers and hooks everywhere (what the app had: a lifecycle spread over a component, a store and a timer, with nothing that says which events a busy write may take); a state library without machines (it offers no place for the timers and requests that make the states).

What would change it: a lifecycle machine that grows no states beyond idle and busy after its steps land, which would go back to a function; or a cost in bundle size or test time that the lifecycles do not repay. The two dependencies (`xstate` for the machines, `@xstate/react` for `useSelector` and `useActorRef`) added about 17 kB gzipped to the app's JavaScript in all (757,642 B to 774,343 B across the build's chunks; the library itself is about 22 kB, and the code the write path replaced is a few kB smaller).
