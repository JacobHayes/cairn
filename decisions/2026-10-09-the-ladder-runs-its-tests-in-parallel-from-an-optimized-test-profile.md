# The ladder runs its Rust tests in parallel, from a test profile that optimizes the computing crates

Question (from the validation ladder's speedups): `mise run check:fast` took about 70 s warm and spent most of it waiting: the engine's property and cost tests ran unoptimized for 16 s, 27 test binaries ran one after another, and every rung paid cargo's start-up. What can be sped up without changing what the ladder checks?

Call: the tests of `cairn-engine`, `-schema`, `-service`, `-store`, and `-wasm` are built at opt-level 2 through `[profile.test.package.<crate>]`, and rung 6 runs `cairn-wasm-cases` with `--profile test` so it links the same optimized units (the engine's property binary went from 16 s to 3 s; `cairn-wasm-cases` from 50 s to 10 s). Debug assertions and overflow checks stay on. The same override under `[profile.dev.package.*]` was tried first and changed the browser host's wasm-bindgen output, because `wasm-dev` inherits it; the test profile is not inherited by `wasm-dev` or `wasm`, so build:wasm and rung 5 stay byte-identical. `scripts/ladder-tests` builds every test binary once and runs them in parallel, and rungs 2, 3, and 4 (and rung 6's binary tests) pick their tests out of the same run by name, so suite names and counts are unchanged, except that `cairn-store` reads 20 instead of 21 because the one ignored doc test is no longer counted in rung 2. Doc tests moved to rung 4 (no crate has one that runs; a suite appears when one does). eslint keeps a per-file result cache, and rung 6 reuses `cairn-wasm-cases` while a hash of the crates it links, the fixtures, and the manifests is unchanged.

Alternatives: `cargo-nextest` (measured 4 to 5 times slower here: 722 process spawns), `opt-level` for every dependency (three more minutes of build, no visible test gain), a dedicated `ladder` profile and target directory (a second full build of the tree), and running rungs 2 to 4 as one rung (renumbers the ladder every document names).

What would change it: a test that passes optimized and fails unoptimized (an overflow or ordering bug that opt-level 2 hides; debug assertions stay on to limit that), a cached eslint result going stale after a change in another file's types (delete `dist/ladder/eslint-cache`; CI has none), or a doc test that must run in the inner loop.
