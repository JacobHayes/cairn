# The spike testbed is removed

- Question: `testbeds/spike/` (brief 1.3) was a throwaway experiment whose README said a later brief would fold it in or delete it. It has its own Cargo workspace and lock file, depends on no Cairn code (tokio and axum only), and runs on a pinned patina revision, so the nightly `mise run sim` re-proved the same result on the same binary every night. Should it stay a sim leg?
- Call: delete it, with every reference that kept it alive (its `sim.sh` legs ran through the `testbeds/*/sim.sh` glob, and the lint step's lock-file loop covered it). The multiplayer testbed already runs Cairn's real HTTP server (axum on tokio) under patina on one current-thread runtime, which is the configuration the spike proved, against Cairn's own code. The patina limits the spike's gap legs reproduced are tracked as patina issues outside this repository, and the `[patina]` files in `decisions/` keep their record. The landed brief, its proof and the earlier decision files are history and stay as written.
- Alternatives: keep it in the nightly run (the same result every night on a pinned binary, at a cost in build time and upkeep, and a leg that fails only when patina changes, which the multiplayer testbed's own gap legs already tell us); run it only on a patina bump (a second harness to remember and a second place to update on every bump, for coverage the multiplayer testbed gives).
- What would change it: a need to test a multi-thread runtime once patina supports it. That check would be a leg of the multiplayer testbed, which drives the real server, not a revival of the spike.
