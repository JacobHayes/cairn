# A journey whose conditions compare entities is held to the deployment it was checked with

- Question: review round 1 found a race: a journey patch that names no deployment revision (a pin, say) is validated against the aliases loaded with it, and an entity merge committed between that validation and the patch's commit can make a condition comparing entities true, so the patch commits a graph that no longer holds the plan invariants (F5, A15). The merge's own check saw the journey before the patch; the patch's commit checked no deployment revision. E6 asks only a patch that writes an entity reference to name one, and the mutation semantics record (`2026-10-06-mutation-semantics-the-prd-leaves-implicit.md`, item 10) checks none when none is named.
- Call: when the journey a patch leaves has a condition on an entity decision's answer (the only way aliases reach a journey's invariants), the service adds the deployment revision it loaded as a commit precondition, whether or not the patch named one, so a merge in between answers the patch stale instead (the client refetches and resubmits as for any conflict). Other journey patches are not held to the deployment, so entity creates and merges elsewhere never make them stale. On Turso the precondition writes the deployment's revision row (DECISIONS.md 3.1), so commits to two such journeys at once conflict there and one is retried once, which is rare at this scale.
- Alternatives: every journey patch held to the deployment (every commit would write the deployment row, serializing commits to different journeys, which ARCHITECTURE rejects); the store rechecking the plan at commit (it has no engine); the merge rechecking each journey at commit (same).
- What would change it: another way for the deployment to reach a journey's invariants (the condition test widens), or contention on the deployment row showing in the multiplayer testbed (6.1).
