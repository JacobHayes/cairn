# Behind Google Cloud IAP, Cairn verifies the signed assertion on every request

- Question: a deployment on a GCP VM behind an HTTPS load balancer with Identity-Aware Proxy (IAP) needs each person signed in as themselves, and none of the providers fit. OIDC against Google means a second sign-in after IAP's, plus an OAuth client that has to be made by hand. Tailscale's proxy mode trusts identity headers only from loopback, so it would need a header-rewriting proxy on the VM. The dev provider signs everyone in as one user. Not part of any brief: this came from a deployment.
- Call: a `gcp_iap` provider. IAP signs every request it lets through with an ES256 JWT in `x-goog-iap-jwt-assertion`. The provider verifies it with `openidconnect`'s ID-token verifier, as the OIDC provider verifies its tokens, so nothing is checked by hand: the signature against Google's published IAP key set, issuer `https://cloud.google.com/iap`, the configured audience (the backend service, `/projects/<number>/global/backendServices/<id>`), expiry, and issue time, with 30 s of clock skew either way. ES256 is the only algorithm allowed. A good assertion names the identity (subject = `sub`, IAP's stable account id such as `accounts.google.com:1234`; display = `email`; the email is listed as verified, since Google verified it). A missing header is `Absent`; any bad one is a refused credential, and a key set that cannot be fetched is `Unavailable`. Since the signature is the credential, the provider runs on any listener, unlike Tailscale's proxy mode.
- Key set: fetched on first use and kept. An assertion naming an unknown key id fetches the set again, at most once a minute, so Google's key rotation needs nothing and forged key ids cannot cause a fetch per request. Fetches go through the auth crate's outbound client (https only, no redirects, 10 s, body limit). Two new auth-crate limits, both in PRACTICES: the refetch interval (60 s) and the clock skew (30 s).
- Alternatives:
  - Trust `X-Goog-Authenticated-User-Email`. Rejected: it is safe only while nothing but the load balancer can reach the port. A firewall change or a sidecar on the VPC could then sign anyone in, and Google's own guidance is to verify the JWT.
  - Email as the subject. Rejected: a renamed account would become a new identity. `sub` is stable, and the email stays the verified email H3 matches on.
  - A periodic key-set refresh. Rejected: refetching on an unknown key id covers rotation. A retired key stays usable until the next unknown key id, and only for assertions that last ten minutes anyway.
- What would change it: IAP signing with another algorithm or moving its key set. Also a deployment that puts IAP in front of App Engine, whose audience shape (`/projects/<number>/apps/<id>`) the provider already accepts, since only the `/projects/` prefix is checked.
