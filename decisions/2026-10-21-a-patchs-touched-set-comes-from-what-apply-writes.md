# A patch's touched set comes from what apply writes

- Question: the decision to apply a stale patch compared what intervened with a touched set predicted from the mutations alone, a hand list beside the handlers that do the writing. The list missed what handlers write depending on what they find: removing a role also clears its fill and rewrites insertions that map it, removing a participation kind rewrites insertions, reopening a node clears its guard bypass, creating a journey from a route writes the route version it copies. So a removal of an empty role, made stale by someone filling it, was judged safe and silently cleared the fill. The work was the fix for that lost update, from the audit of rules kept in more than one place.
- Call: nothing predicts a patch's touched set; the per-mutation list is deleted. A stale rejection carries the patch's own touched set beside what intervened, from the change set the engine's apply builds with the patch moved to the current revisions. The engine fills it when it finds the patch stale; the store, which cannot apply, says the whole domain, and the service, on a stale commit, applies the patch once more over a fresh load to say what it would really write. A patch that would not apply at the current revisions (invalid, or stale on a revision a mutation names) touches its whole domain, so it is never applied over what intervened: the person sees what intervened. The service compares the two sets with the engine's overlap check. The assistant's node count for a direct write reads the same derived set, from applying the patch at the current revision as its overflow proposal would draft it; a state write that would be refused there is answered with that rejection without running.
- Alternatives: correct the hand list and add a property test that applied writes stay inside the prediction (still two homes for one rule, and the generators do not reach roles, kinds or overrides, so the gaps above would not have been found); have the client apply the patch itself (the Rust client holds no records, and a client's records may be behind); let a patch that would be refused at the current revisions be applied, since it writes nothing (its rejection is more specific, but its outcome could change with the day before the write lands, so it fails closed).
- What would change it: a stale answer's extra apply showing up in write latency under contention (it runs only when a patch is stale), or the multiplayer testbed finding a write landing over a change that a later state made it overwrite.
