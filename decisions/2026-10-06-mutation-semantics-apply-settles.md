# Mutation semantics apply settles

- Question: the PRD's tables and requirements leave some behavior of individual mutations open.
- Call: (1) Dates (D1, F1, F2): start records today as the start date and stop clears it; complete and reach record today as the finish; a first answer records today as the decided date and a revision keeps it; skip records no date; reopen clears both dates (and a decision's answer, so the role fill or pin it produced goes too, E3). (2) A replaced node whose kind changes starts over in the new kind's initial state, keeping its provenance (its old machine does not apply); an answer-type change keeps the answer, so the patch is rejected unless it also reopens the decision (A4: answer-type validity is an invariant). (3) A removal tombstones every route-copied node in the subtree, not only its root (B4: "covering the subtree"); names in a removal that no longer apply (a child moved out since) are ignored, since removing less than the author saw is safe, while anything the subtree holds that the removal does not name rejects it (A18). (4) Removing a role drops its direct fill; any other reference to it rejects the patch (A18). (5) A guard bypass must accompany a guarded transition of its node in the same patch (complete, a first answer, reach), else it is rejected; it records the failures of the guards it names present on the patch's final graph (D4). (6) Journey status (B11): active and completed move both ways, either may be archived, an archived journey returns only to completed; a no-op status change is rejected. The archived write ban holds every mutation, a riding entity create included, and each of an applied proposal's mutations. (7) Applying a proposal is one event whose delta holds every write its mutations made plus the applied status, attributed to the proposal's author and agent with the applying user as confirming user (H2, I6); its review items are not enforced at apply (their resolutions are 2.7's, written into the proposal as mutations). A proposal for a new destination must create it; one for an existing destination may delete it, and its event goes to the deployment log (A19). (8) A merge names the journeys referencing either entity (by an answer, a direct fill, an explicit participation, or a condition comparing an entity decision with it) at their revisions; the loaded referencing journeys must match exactly or the patch is stale, and each is validated with the merge applied (MergeBreaksJourney, E6). (9) A journey patch that names no deployment revision is not checked against one; one that names a stale revision is stale.
- Alternatives: (1) keeping dates on reopen as history (events already keep it); (2) rejecting kind changes on a node with state; (3) a single tombstone on the subtree root; (4) rejecting a role removal while it is filled; (5) a bypass allowed on its own, recording nothing; (9) requiring a deployment revision whenever a journey patch names an existing entity.
- What would change it: 2.3 wanting skipped work to carry a finish date; 2.7's upgrade needing per-root tombstones; an H5 reading that makes the deployment revision mandatory (then a new violation code).
