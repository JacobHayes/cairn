# Restoring a tombstone adds a local copy under fresh keys; resetting a field writes the route's value and clears the marker

- Question: the brief asks for "tombstones with restore", and B4 for "reset to route" on a local-edit marker. A tombstone's key is retired, and the Invariants say a removed key never comes back (the engine refuses a tombstoned node with `retired_key_reused`); no mutation removes a tombstone. B4 says reset "clears the marker", but clearing alone would leave the journey's value in place until an upgrade overwrote it.
- Call: restore adds a journey-local copy of the route version's node and of the removed nodes beneath it, under fresh keys at the path they had, each reference kept where the journey still holds its target (renamed to the copies within the subtree, dropped otherwise: a condition's clause, a date rule's source, a stage bound, a draft's answer placeholder). The tombstone stays, so an upgrade still does not re-add the route's own node, and a tombstone whose path a journey node occupies again is shown as such instead of offering a second restore. Reset writes the route version's value of the field (or requirement, participation, or resource) and then clears the marker in the same patch, as an upgrade's "take the route's value" resolution does. A shape marker (a kind or answer-type change) is shown but not reset by hand: replacing the node whole would mark every aspect that differs, and the upgrade's review already settles it (B7).
- Alternatives: an engine mutation that lifts a tombstone and un-retires its keys (breaks the never-reused invariant that H5's touched sets and upgrades rely on); reset as a bare marker clear (the field would still show the journey's value, so nothing visibly resets).
- What would change it: a PRD reading under which a restored node must keep its route identity, which needs an invariant change first.
