# A write is an operation the edit manager owns

Question (from the write identity work; PRD H5, A18, A19, D7): once a write is an actor owned by the tab, what does each answer make of it, what does it resend, how often, and how does the control that sent it see it?

Calls:

- **What each answer makes of a write.** An applied or `already_applied` answer lands it; a rejection makes it `rejected`; a refusal that says its subject no longer exists makes it `gone`, which offers only Discard. `gone` is read from the shapes the engine answers: a stale rejection naming the write's own journey or route at revision 0 (the engine's revision of a domain it does not hold, and the base is checked first, so a deleted journey answers stale and never `target_missing`), or an invalid rejection with a `dangling_reference` at the mutation's own node with nothing `related`. A live node that points to a removed one is `related` to it and stays `rejected`. An HTTP 4xx answer to the first send is `stopped`: the server refused it and nothing committed. No answer, status 0 or 5xx, is `unconfirmed`; a 4xx answer to a resend stays unconfirmed (and waits for a manual Retry), since it says nothing of whether the lost attempt committed. Every failure unconfirmed, as the old code had it, would make "unconfirmed" mean nothing and resend definite refusals. The browser host reports every failure as status 0, so there a refusal reads as unconfirmed (a known limit).
- **A resend sends the last patch it dispatched.** The content hash covers the base revision and the safe retry may rebase a stale patch before the answer is lost, so resending the original would be answered `patch_id_reused`. The write reports each rebased patch before it goes out and the record is rewritten before the request leaves.
- **The safe-retry bound is per write.** `retry.ts` restarts its count on every call, so resends could multiply PRACTICES' 32 resubmissions. The write keeps the count in its context and its record and counts on from it; `retry.ts` is unchanged.
- **The resend limit is 5, backed off from 250 ms to 15 s**, a row in PRACTICES' limits table and a named constant (`RESEND_COUNT_MAX`), with the backoff one function (`backoffDelayMs`) the stream's reopening and the journeys' refetches use too. Each attempt waits for the connection (the browser is online and the tick stream is open), so time offline uses none; past the limit the chip asks for Retry. Version skew stops resends.
- **The chip's colour keeps its rule.** A write that is out or still resending is in flight (SAVING, with OFFLINE and RECONNECTING above it as before); it turns red (NOT SAVED, with Retry) only when it stops resending, because red means "not landing until you act" (`the-sync-chips-colour-says-what-it-asks-of-you`).
- **A control's draft becomes its write when sent.** Save sends the draft and clears it in one handler; while a write exists for the edit, the form shows a newer draft if there is one, else the write's payload; landing or Discard removes the write and so closes the form. Keep my edit rebases the newer draft, else what the write sent. Text typed after a send is never lost to a landing, mounted or not, and a skew-stopped edit survives the reload in its record.
- **One busy write per edit.** An edit is the control's own key (`title:<journey>:<node>`). The manager refuses a submit while a write of that edit is busy (`sending` or `unconfirmed`, including waiting for a manual Retry), and a submit over a settled write (`rejected`, `stopped`, `gone`) replaces it. A write in `sending` ignores a second submit.
- **What a reload resends.** A kept `sending` or `unconfirmed` record is resent at once with a fresh resend budget: it may have committed, the resend is safe, and the reload is the person's retry. A `stopped` record is not resent by itself.
- **Restoring waits for the root.** XState forbids reading an actor's snapshot while it initializes, and a restored write's start reads the session root, so the manager spawns restored writes on a `restore` event the session sends after the root has started, never in the manager's initial context.

Alternatives: keeping the old key derived from a write's target (any later landing to that target resolved it, which is the defect); resending the original payload; a per-call bound; red at once for an unconfirmed write; a draft kept until landing and cleared if unchanged (it needs a landing effect on another module's storage).

What would change it: a host that tells refusals from silence in the browser; a resend limit that people hit in practice (a design signal to revisit, not a knob); a second kind of command that does not rebase.
