# The engine names the current stages, the final milestone and the day a snooze lifts

Question (from removing the web app's copies of engine rules): the canvas decided which stages are current, the summary which milestone to lead with, and the plan list when a snooze lifts, each by re-reading the document in the tab. Should the engine derive them?

Call: yes. The derived values carry `current_stages` (top-level groups holding an acting-frontier or active node), `final_milestone` (the final milestone while it is open or done), and per node `snooze_lifts` (the latest day any hold on it or on a container above it ends; absent when a hold has no day). The web reads them. Completing the journey is also suggested once the final milestone is done, as before, but now only for a final milestone the engine considers in play, so a final milestone ruled out by an answer no longer suggests completion.

Authoring forms: the pre-send checks of every form that builds a document's values (blank, id shape, counts, byte limits, whole-number ranges, an address's, email's or journey id's form, a date rule's source and offset) are the engine's. One wasm call takes a node form's values for the fields the node has (with its date rules) and returns one problem per field that cannot be sent; a sibling takes the loose values of the other forms, each named by the form, and returns one problem per value. A loose value is read as an id, route id, journey id, title, text, address or email through the types the patch reader builds the document from, so a form and the reader share one rule set; it may also name its siblings' values (`taken`: an id is unique among them, an email is compared as the store holds it), or be a count held to a named limit (the engine says "At most 32 roles."). The forms show the messages at the fields, which are marked invalid and point to their message (and to each violation the engine reports about the field), and nothing is sent until the engine has answered for the values as they are; a check that cannot be made says so and can be asked again. The proposal editors read the same check to show and to gate their writes. A condition's check stays as it was.

What the web still holds is facts about its screen, never a rule: the sibling ids and the counts it passes to the engine (what the graph on screen holds), an email chip's trimmed and lower-cased form (the form the chip shows before the store holds it), and the address-to-page mapping. Asking the engine is asynchronous on the server host, where the derive worker owns the only instance, so nothing is answered per keystroke on the main thread: an email chip is taken when Enter, a separator, a paste or blur commits it (the input is read-only for the moment the answer takes), a search is applied when Enter commits it, and a journey address is read and watched only once the engine has said it is a journey id. An address whose search is over the title limit is sent as it stands and the engine refuses it in words, instead of the page dropping it.

Alternatives: reporting patch-reading failures as violations with a field (the reader's failures carry no field to place); keeping the web copies of these checks.

What would change it: a field the form checks that the types do not, or a check that needs more of the graph than its counts and sibling ids (it belongs to the preview).
