# The engine names the current stages, the final milestone and the day a snooze lifts

Question (from removing the web app's copies of engine rules): the canvas decided which stages are current, the summary which milestone to lead with, and the plan list when a snooze lifts, each by re-reading the document in the tab. Should the engine derive them?

Call: yes. The derived values carry `current_stages` (top-level groups holding an acting-frontier or active node), `final_milestone` (the final milestone while it is open or done), and per node `snooze_lifts` (the latest day any hold on it or on a container above it ends; absent when a hold has no day). The web reads them. Completing the journey is also suggested once the final milestone is done, as before, but now only for a final milestone the engine considers in play, so a final milestone ruled out by an answer no longer suggests completion.

Authoring forms: the pre-send checks of every form that builds a document's values (blank, id shape, counts, byte limits, whole-number ranges, an address's or email's form, a date rule's source and offset) are the engine's. One wasm call takes a node form's values for the fields the node has (with its date rules) and returns one problem per field that cannot be sent; a sibling takes the loose values of the other forms (an id, a route id, a title, text, an address, an email) each named by the form and returns one problem per value. Both read each value through the types the patch reader builds the document from, so a form and the reader share one rule set; the wording of those types' errors is written for people. The forms show the messages at the fields, which are marked invalid and point to their message, and nothing is sent until the engine has answered for the values as they are; a check that cannot be made says so and can be asked again. The proposal editors read the same check to show and to gate their writes. A condition's check stays as it was. What stays in the web is what needs the screen's own state, not a rule of the engine's: a count or a sibling-unique id against the graph on screen, a search box (a request parameter, held to the title limit), an email chip as it is typed (taken or refused one at a time), and the shape of a journey id in an address.

Alternatives: reporting patch-reading failures as violations with a field (the reader's failures carry no field to place); keeping the web copies of these checks.

What would change it: a field the form checks that the types do not, or a check that needs the whole graph (it belongs to the preview), or a chip or search input that can wait for an answer from the engine.
