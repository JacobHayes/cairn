# A page under any proposal layer, or of an archived journey, offers no live write

Question (from the rule-journey-screens unit): which pages offer writes was decided per component. The journey header offered edits after a proposal was applied while the route header offered none; Summary and the Walkthrough looked live under an applied or discarded proposal and then quietly became the Graph; on an archived journey the Summary was read-only while the node panel, the card, the list rows and the canvas menu still offered Start, Done, Add note, Edit and Upgrade, each then refused. What is the one rule, and does a control that cannot act stay visible?

Call: one gate, `useWritable(journey?)` in `web/app/src/screens/writable.ts`, is read by every write surface (node actions and menus, the canvas context menu, row actions, notes and links, the stalled panel, editors, the checklist, bulk selection, the header's Edit, Insert and Re-link, the structure editor, the route draft's publish, import, discard and retire, and the Identities page). A page takes no live write while any proposal layer is on it, whatever its mode (reviewing, applied, discarded or missing), and a journey takes none while its status does not accept changes. The status rule is the engine's (`JourneyStatus::accepts_changes`, emitted as `STATUS_ACCEPTS_CHANGES` in the generated rules), so the screens and the engine cannot disagree. A control that cannot act is absent, not disabled: the menus keep only where to find a node (Show in graph or list, Show insertion, Copy link). The status moves themselves come from the engine's table too, so an archived journey's menu still offers Un-archive, and Delete once archived. Summary and the Walkthrough are marked unavailable in the view picker under any proposal layer, with the reason, and their keys leave the key sheet.

Alternatives: keeping `useReviewing` as the gate and adding a status check beside it (two predicates every surface must remember, the bug this replaces); disabling controls with a reason (an archived journey would be a page of dead buttons); letting the engine's level or snapshot carry a read-only flag (the screens already hold the header, and the generated table is the engine's own rule).

What would change it: a mode of the layer that should allow live writes beside the proposal (a side-by-side edit), or a status between active and archived that accepts some writes and not others, which would make the table per mutation rather than per status.
