# CI keeps only the newest cache entry of each kind

Question (from keeping GitHub's Actions cache from evicting the live entries): the four check parts each save a rust-cache entry on main, keyed by part, profile hash, toolchain environment hash and lock file hash, plus one mise entry per platform. Every Cargo.lock change, and every runner image that changes which Rust toolchains are installed (rust-cache hashes them all), saves a whole new set and leaves the superseded one. The repository's limit is 10 GB, evicted least recently used first; the set sat at 7.8 GB with two generations and an earlier trial evicted main's live entries, so the next run built cold. How does CI keep the live set safe?

Call: a `prune-caches` job runs on main after the parts have saved and, for each kind of entry (a part's rust-cache entry whatever its profile, environment and lock hash; the mise entry per platform), keeps the newest and deletes the rest. Entries on tag refs go too: main never restores them. The job alone holds `actions: write`; the workflow's default stays read-only. Measured on the repository's real entries: 7.8 GB before, 2.6 GB kept (rust 1.2 GB, lint, web and browser 0.4 GB each, mise 0.1 GB).

Alternatives: deleting by age (keeps entries nothing restores, and a quiet week would empty the live set); a key per run with restore keys (every run saves, ~2.5 GB each, worse); shrinking the rust entry instead. Measured on a trial branch, the rust entry (0.85 to 1.25 GB) is the root target (0.27 GB compressed), the multiplayer testbed (0.35 GB), the durability testbed (0.14 GB) and the registry (0.09 GB). rust-cache already drops the workspace crates' artifacts and cargo runs without incremental state; what is left is dependencies a restore needs. Chained restores keep superseded copies of a dependency rebuilt with a new hash (a third of the root target's rlib files), but telling a superseded copy from a second live one (build and target dependencies with different features) needs more than file names, would save about 0.1 GB compressed, and is not kept. Turning off rust-cache's environment hash was tried and also drops the lock file hash from the key, so the entry would never be replaced; not kept.

What would change it: a second kind of entry that must outlive the newest (a release branch with its own caches), or the live set growing toward the limit by itself (then the rust entry's superseded copies are worth removing).
