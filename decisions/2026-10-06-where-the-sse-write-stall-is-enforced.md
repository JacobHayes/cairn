# Where the SSE write stall is enforced, and how it is measured

- Question: PRACTICES disconnects an SSE subscriber "that cannot take a write" for 15 s. The API's stream hands frames to the response body through a one-frame channel and drops the subscription when a send waits out the stall, but hyper keeps taking frames while the kernel's socket buffers have room, so a peer that stops reading (or vanishes without a FIN) is not caught until about a megabyte of ticks or the TCP retransmission timeout (about 15 minutes) later, holding one of the 256 subscriber slots meanwhile. Review round 1 of 4.2 reproduced it.
- Call: the stall is enforced in two places. The API keeps its channel stall (it catches a server-side writer that is stuck, and a peer whose buffers are full). The listener, which 4.7 owns, sets `TCP_USER_TIMEOUT` to `SSE_WRITE_STALL` (with TCP keepalive, so an idle connection is probed): unacknowledged data older than the stall closes the connection, hyper drops the body, and the pump, which watches the channel close, drops the subscription at once. 4.7's brief carries it in scope with an acceptance case. The listener also turns on keepalive with its idle time at `SSE_WRITE_STALL` and its probes at `SSE_HEARTBEAT_INTERVAL` (nearest named limits, as the limits table names none), and `TCP_NODELAY`; on a kernel without `TCP_USER_TIMEOUT` the binary still runs and warns at startup. The kernel starts the user-timeout clock only once the subscriber stops taking data (its receive window closes after its buffer fills), from its first zero-window probe one retransmission timeout later (Linux's minimum is 200 ms); measured on loopback, the slot is freed 15.24 to 15.28 s after the window closes. So the acceptance (a subscriber that stops reading loses its slot "within the write stall plus one coalescing interval") is measured from the moment the bytes waiting in the client stop growing, allowing the stall, one coalescing interval, and the 200 ms before the first probe, and also checks the slot is not freed before the stall.
- Alternatives: a per-connection timer in the API that writes and measures acknowledgment (it cannot see the kernel's buffers); smaller socket send buffers (delays detection by the buffer size, not a time); leaving it to the retransmission timeout (a vanished peer holds a slot for 15 minutes); a user timeout below the stall, to meet the bound from the moment reading stops (it would no longer be the stall).
- What would change it: a listener that cannot set `TCP_USER_TIMEOUT` (non-Linux hosts, a unix socket behind a proxy), where the proxy's own idle timeout must stand in; or a bound that must hold from the moment a client stops reading regardless of its buffers, which no socket option gives.
- History: the HTTP API brief (4.2) set where the stall is enforced; the binary brief (4.7) then measured the socket-level clock, added the keepalive values, and fixed how the acceptance counts from the window closing (first recorded as "the socket-level write stall is measured from the subscriber's window closing").
