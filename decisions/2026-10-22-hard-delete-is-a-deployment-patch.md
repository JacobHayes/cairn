# Hard delete is a deployment patch, for journeys and for unused routes

Question (from the hard-delete work): deleting several journeys at once needs one atomic write, and routes nobody uses need a way to go. A patch targets one domain; a journey's own delete wrote to the journey and needed exemptions (the archived write ban, the deletion event logged outside the patch's domain, a domain that may be gone after its own commit). Where does a hard delete belong, and when is a route unused?

The call:

- A hard delete is a deployment mutation: `delete_journey { journey, revision }` and `delete_route { route, revision }`. One deployment patch carries any number of them and commits all or none. Each names the revision it was read at; a journey or route that moved since, or is already gone, makes the patch stale, naming it. Every deletion's event is in the deployment log, as the patch's own events always are. The journey-domain delete, and every exemption it needed, are gone. This is the one exception to "atomicity is within one domain", and the requirement says so.
- A route is in use while a journey follows any of its versions. The engine checks this once on the records the whole patch leaves, so a patch deleting a route and the journeys on it passes in any order. The service loads the users it finds, up to the limit on what a rejection names, and counts the rest, as identity deletes do. The commit checks again that nothing outside the patch uses each deleted route, so a journey started after the read makes it stale.
- Deleting a route removes its draft, every version, its proposals and its events. The deleted id goes in one record of deleted ids for journeys and routes; a create at it, or a proposal to create it, is refused. Route versions are never deleted on their own.
- The engine deletes a journey in any status, as before; the screens offer it only once archived. The web header and the journey index share one confirmation that asks once with the count, replacing the typed-name confirmation. A route's `⋯` offers deletion only when its detail says nothing uses it.
- The SQLite migration rewrites stored JSON of the old shapes (the deleted-journey record and its address in receipts, and a journey proposal's bare delete, which now names its destination and revision so it reads back; applying it is refused, since a proposal's mutations are its destination's).

Alternatives: keep deletion in the journey domain and add a bulk call that commits several journey patches together (a second write primitive, and the exemptions stay); route deletion as a route-domain patch (it would need the same cross-domain checks against journeys and other routes, with the event in the route's own log that the deletion removes); allow deleting a route whose versions only old journeys follow (it would orphan their lineage).

What would change it: a need to delete a journey through a proposal (deployment proposals would have to carry deletions), or a route whose users are too many to load for a rejection, which would move the in-use check entirely into the store.
