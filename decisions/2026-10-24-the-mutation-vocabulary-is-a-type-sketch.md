# The mutation vocabulary is a type sketch

- Question: work cutting the MCP context cost found the tool list at about 36,300 tokens, `apply_patch` alone 15,500 of them: the whole mutation vocabulary as JSON Schema, 59 operations and 75 shared definitions, a third of it descriptions. An agent loads that list on connecting, and the in-app assistant sends it on every provider exchange. How should the vocabulary be spelled out so an agent can still write every structural change correctly?
- Call: The tools that take a patch spell the mutations out, as before, but as compact type signatures generated from the same schema: one line per `op` with its fields and the first sentence of its description as a comment, then each shared type once, then the key prefixes (`NodeKey n_...`). Required (`field: T`), optional (`field?: T`) and nullable (`T | null`) are told apart, so a required field that takes `null` as a value, such as clearing a node's condition with `{"relevant_when": null}`, still shows it; an optional field's `null` means the same as leaving it out and is not written. A property group of which exactly one is required reads `one of a: T | b: U`, a map reads `{[k_key]: T}`, and the node's per-kind and per-answer-type rules (which fields a decision, a milestone or a single-choice question takes, and which it needs) are written in a comment beside its type. The generator supports exactly the constructs Cairn's schemas use and panics on any other keyword or shape, so a new construct fails the tool listing's tests instead of producing a wrong sketch. The `mutations` items become objects with an `op` from the op names, described by the sketch; parsing is by the same typed schema as before, as strict, and a mismatch still names its path. The other tools that take mutations keep citing the vocabulary. The sketch is about 11.6 KB, about 3,000 tokens, against about 11,700 for the compacted JSON Schema. An open `{op}` object cannot go unchanged to a provider's strict structured-output mode, which needs closed objects; Cairn's adapters do not use that mode.
- Alternatives:
  - Keep the mutations as JSON Schema, compacted: `apply_patch` stays near 11,700 tokens.
  - Serve the mutation schemas from a read tool: the smallest list, at the cost of a call before the first structural write; the sketch costs about 3,000 tokens and some clients already defer a tool's schema until it is used.
  - Loose `object` mutations with no description: agents guess shapes and are refused by path; refused on 2026-10-06 and still wrong.
- What would change it: a model that misreads the sketch in practice would bring the mutations back as JSON Schema; clients that keep tool schemas out of the model's context until a tool is used would make each tool's size matter more than the list's; a provider adapter that needs strict mode. This replaces the "spelled out" half of the decision of 2026-10-06 (the tool list carries the mutation vocabulary once); its "no output schemas listed" half stands.
