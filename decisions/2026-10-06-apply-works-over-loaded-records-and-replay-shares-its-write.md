# Apply works over loaded records, and replay shares its write semantics

- Question: ARCHITECTURE writes `apply(domain, patch, inputs)` with derive inputs, and runs the J3 harness "with the memory store". A patch can read more than its domain (a journey create copies a route version; an entity create rides in a journey patch; applying a proposal reads it; a merge checks the journeys that reference its entities), the memory store is 3.1's and is being built beside this brief, and nothing in 2.1 derives.
- Call: `apply(records, patch, inputs)` takes `Records`, the records the host loaded for the patch (the target domain or none, the deployment, the route versions it reads, the proposal it edits or applies, the journeys a merge is checked against), and `ApplyInputs` (today, the commit time, the actor, an optional note). Mutation handlers turn each mutation into the writes 1.2's change set already describes, and the candidate is built by applying exactly those writes with `Records::write`, the store's semantics in memory; `Records::advance` moves revisions once per patch (the domain by one, the deployment by one more when another domain's patch writes deployment records: an entity create or a deleted journey id). `replay` uses the same two functions, so replay equals apply by construction and the J3 harness runs over `Records`. A stale revision is answered with an empty intervening touched set: the engine sees no history, and the host fills it in.
- Alternatives: apply over one domain type per target with the extra reads as more arguments (one signature per target); building the candidate by mutating documents directly and checking the writes separately (two code paths that replay compares, at twice the code); waiting for 3.1's memory store (the order forbids it).
- What would change it: 2.4 adds the derive inputs apply needs (time zone, rank constants) to `ApplyInputs` when the derived-guard stage arrives; a store whose rows need writes the change set cannot express.
