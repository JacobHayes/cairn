# The caller's identities are in `GET /users/me`, and the browser host serves the screens' reads and route files

- Question: the identity screen shows the identities a user signs in with and the emails each verified (ARCHITECTURE, Auth: users and identities; H3), but `GET /users/me` answered only the user, agent, entities, and merge offer. The in-browser host had no filtered journey index, route index, route detail, export, import, or caller, so the route and entity screens could not run without a server; and a route file arrives from disk as YAML while the API's import and export carry JSON (ARCHITECTURE, File format).
- Call: `Viewer` (service and API) gains `identities`: provider, subject, verified emails, and when each was linked, in provider and subject order. `crates/wasm`'s root gains `journeyIndex` (the API's journey filters as JSON), `routes`, `routeDetail`, `exportFile`, `importFile`, and `viewer`, each answering the API's JSON through the same service calls, and `readRouteFile` and `routeFileText` turn a file's text into the file document and back into canonical YAML, so both hosts read and write files through the page's engine and an export is saved as the YAML kept on disk. The fixture server the app's browser tests run against also signs in through an OIDC provider over 3.2's stub issuer, which gains a sign-in form at its authorization endpoint.
- Alternatives: a separate identities endpoint (one more read for one screen); YAML on the wire (ARCHITECTURE keeps JSON there); identity linking tested only in `crates/auth` (the brief asks for it through the app on the server host).
- What would change it: an identity record gaining fields a viewer should not see, or token management joining the identity screen (its endpoints exist; 5.5 does not show them).
