# How the multiplayer testbed makes commits overlap

- Question: on one current-thread runtime (1.3's condition) a request runs to its end unless something waits, and a commit takes no virtual time, so no two commits ever overlap and the commit-race paths (the service's `reachable!` sites for a patch lost at commit and a resubmission racing its original) never run. Over HTTP a resubmission cannot meet its original either: axum drops a request's handler when its connection closes, and the client closes the connection when its attempt times out.
- Call: (1) the store gains a commit point, `CommitPoint::BeforeBegin`, paused before a commit takes its connection, in both backends; the testbed's `buggify!` sites hold commits there and at `BeforeCommit` (`testbeds/multiplayer/src/faults.rs`), inert outside a buggify run and before setup ends. (2) Beside the HTTP clients, one agent client calls the service in process, as MCP and the assistant will, with the same `client::retry` logic, each attempt on its own task so an attempt it stops waiting for keeps running. (3) `crates/service/tests/in_flight.rs` uses the same commit points to set up each minimized race deterministically, over both stores where the race allows.
- Alternatives: a store wrapper in the testbed delegating all 34 `Store` methods to add a wait (written, then dropped for the commit point, which the service tests can use too); a multi-thread runtime (patina gap 1); leaving the two oracles unmet and waiving the campaign's coverage gate (hides every other unmet oracle).
- What would change it: patina running multi-thread tokio (gap 1), when real concurrency might reach the races without fault sites.
