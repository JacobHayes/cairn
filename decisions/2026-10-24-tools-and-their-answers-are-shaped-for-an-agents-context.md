# Tools and their answers are shaped for an agent's context

- Question: the work cutting the MCP context cost found the tool list at about 36,300 tokens (144 KB, up from the 110 KB the decision of 2026-10-06 recorded), `apply_patch` alone 15,500 of them, a snapshot of a 200-node page at 45,000, and the in-app assistant sending the list, the whole guide, every workflow and a snapshot on every provider exchange. How should the list and the answers shrink without losing what an agent needs to act correctly, and what does that mean for the HTTP API, which shares the types?
- Call:
  - **The list is compacted where it is built, not where the types are documented.** One pass over each tool's generated input schema drops what an agent cannot act on: the `$schema` and `title` keys, the arguments type's own doc line, `anyOf [T, null]` on a property that is not required (absent and null mean the same there; a required property that takes null keeps it, since null is then a value, such as clearing a field), defaults that say nothing (null, empty, zero, false), integer formats and the zero minimum of a count, and length, count and uniqueness bounds (the server enforces them and a refusal names the one broken). Shared scalar types (ids, keys, text, revisions) are written where they are used, keeping an id's `pattern` so its prefix stays visible. Unions of constants become an `enum`. Shared types keep only their union variants' first sentence. The doc comments stay as they are, because the OpenAPI document and its readers use them; the pass works on a copy made for the list, which the assistant shares. Output schemas are not listed, as before. A value range (a weight's maximum, an offset's) stays.
  - **The mutation vocabulary, the descriptions and the guide** are the type sketch, the short tool descriptions and the guide that leads with the write rules (`2026-10-24-the-mutation-vocabulary-is-a-type-sketch.md` and the commit that shortened descriptions). A tool's argument descriptions do not repeat the revision and retry rules the guide states once.
  - **Answers carry what the agent asked for, once.** Rows and the snapshot's parts are lean (`2026-10-24-snapshot-and-list-rows-are-lean.md`), date chains are compact and held to the explanation entry limit (`2026-10-24-date-chains-are-compact-and-held-to-the-explanation-limit.md`), and history, search and the level give only what is acted on. A write answers `{status, revision}` plus `over`, `consequences` and `notices` only when there is something in them; a proposal write echoes no draft; an error is one block with a message saying how to recover.
  - **The HTTP API keeps its shapes except where it is the agent's read.** The snapshot is the agent's read on both transports; the other HTTP reads answer the full projections clients render from, and the MCP tools map them to the agent shape. The date-chain cap applies on both.
  - **Budgets are limits.** The tool list (48 KiB), one tool's definition apart from the mutation sketch (4 KiB), the mutation sketch (14 KiB), and the bytes per listed node row on each fixture journey (320) are rows in the limits table, measured as compact JSON bytes (about four bytes a token here), and tests fail past them. The list is measured as the endpoint sends it, annotations included.
- Result: the list went from 81,160 bytes (21,500 tokens) to 48,900 bytes (12,800 tokens, a 40 percent cut); `apply_patch` is 15,300 bytes of which the sketch is about 12,000, and the largest other tool is 2,300.
- Alternatives:
  - Keep the mutations as JSON Schema, compacted: `apply_patch` stays near 11,700 tokens.
  - Serve the mutation schemas from a read tool: the smallest list, at the cost of a call before the first structural write.
  - Shrink the shared types' doc comments: shrinks OpenAPI too, for no gain there.
  - Lean shapes on every HTTP read: those reads serve clients that render the full projections.
  - Merge overlapping tools: after the cut a tool costs about 100 to 200 tokens of fixed overhead, so a merge saves little and makes one tool do two things.
  - A real tokenizer in the budget tests: a dependency carrying a large vocabulary, for a ratio bytes already track.
- What would change it: a model that misreads the type sketch in practice would bring the mutations back as JSON Schema; clients that keep tool schemas out of the model's context until a tool is used would make each tool's size matter more than the list's; a client that needs output schemas; a provider adapter that needs strict mode.
- For the owner: the list has little room under its limit; a new tool or a longer description has to be paid for elsewhere. Lowering the page of 200 to 50 for node lists would hold a 200-node journey's reads near a quarter of their size.
