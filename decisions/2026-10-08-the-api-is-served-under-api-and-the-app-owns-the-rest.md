# The API is served under /api and the web app owns the rest of the origin

- Question: the owner asked for every API endpoint under `/api/` and the rest of the root URL space for the web app, with real paths for its screens (`/journeys/<id>`) in place of hash addresses. Which top-level paths must the server still keep, and how does a screen's address reach the app?
- Call: the server keeps three things on the origin and the app owns every other path.
  - `/api/`: every endpoint in the endpoint table, the revision stream (`/api/events/stream`), MCP (`/api/mcp`), metrics (`/api/metrics`), and auth's own routes: OIDC sign-in and callback (`/api/auth/<provider>/sign-in`, `/api/auth/<provider>/callback`), sign-out (`/api/auth/sign-out`), and the built-in OAuth server's registration, authorization, and token endpoints (`/api/oauth/...`). MCP clients and scrapers take a URL, and OAuth clients find their endpoints through the server's metadata, so nothing about them needs the root.
  - `/.well-known/`: RFC 8615 fixes it, and RFC 8414 and RFC 9728 put the OAuth server and protected resource metadata there, at the issuer's root.
  - `/healthz`: the edge's and the deployment's probes call it by that path, and it is the one anonymous endpoint, so it stays where infrastructure looks for it.
  `cairn_api::endpoints` spells the prefix (`PREFIX`) and the kept prefixes (`RESERVED`). A path under a kept prefix that no endpoint serves is answered as no endpoint (404 problem JSON), never with the page. Every other request goes to the host's app: the binary answers `GET` and `HEAD` on any such path with `index.html` (no-cache), except under `assets/`, where a missing bundle is not found; other methods are not found. The app uses React Router's `BrowserRouter`, so a screen's address is a real path that loads directly and survives a reload. `?host=server|browser` still chooses the tab's host; the tab keeps the choice in session storage and takes the parameter out of the address, since the screens' own queries rewrite it. Vite's dev server proxies the three kept paths and answers every other path with the page.
- Alternatives: keeping `/mcp`, `/metrics`, `/auth/`, and `/oauth/` at the root (four more names the app can never use, for clients that are configured with a URL or discover it); `/api/healthz` (breaks the deployed probes for no gain); an OpenAPI `servers` entry of `/api` with relative paths (the document and the endpoint table would not show the paths a client calls, and the health check would sit under the prefix); keeping hash routing (addresses that are not paths, and a page that cannot tell the server which screen it is).
- What would change it: a standard or probe that needs another root path; a static host for the in-browser demo that cannot answer every path with the page, which would need its own rewrite rule.
