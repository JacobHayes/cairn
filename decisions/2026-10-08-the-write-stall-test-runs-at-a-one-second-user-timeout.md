# The write-stall acceptance test runs the listener at a one-second user timeout

- Question: the binary's acceptance test that an SSE client that stops reading loses its slot (brief 4.7) waited out the real 15 s write stall in every check, the longest single test in rung 4. Can it prove the same thing faster without a configuration knob (AGENTS.md, Limits, not knobs)?
- Call: the listener's user timeout is a parameter of `listener::serve_with_user_timeout`; `listener::serve`, the only entry the binary uses, passes `UNACKNOWLEDGED_DURATION_MAX` (the write stall). The acceptance test serves the assembled app through `serve_with_user_timeout` at 1 s and keeps its bounds relative to that timeout: freed no sooner than the timeout, and no later than the timeout, one coalescing interval, and the first zero-window probe after the window closes. It now also fails if the slot is not freed before the write stall itself, so the API's own stall cannot be what freed it. The listener's unit test still checks that an accepted connection carries the write stall as its user timeout. Measured: freed 1.22 s after the window closed (15.22 s at the stall before, the same 0.22 s past the timeout); the test takes 1.7 s instead of 15.7 s. With the user timeout not set, it fails at 15 s, "the slot was not freed at the socket".
- Alternatives: running the full-length test in CI only (the kernel mechanism and its bound do not depend on the timeout's length, which the two measurements agree on); a configuration value (a knob the binary does not need).
- What would change it: a kernel whose handling of the user timeout differs with its length, for instance one that does not clamp the zero-window probe to it.
