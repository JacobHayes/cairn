# Tailscale trusts the proxies it lists

- Question: a deployment runs Cairn behind an authenticating proxy (`tailscale serve` on this machine, or a reverse proxy on another) that strips inbound `Tailscale-*` headers and sends `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-Node-Name`, and `Tailscale-Node-Tags` upstream. How does Cairn trust the proxy without trusting anyone who can reach the listener?
- Call: the provider takes `trusted_proxies`, a required list of IP addresses or CIDR networks (`tailscale serve` on this machine connects from 127.0.0.1). It trusts the headers only from a peer inside a listed source (an IPv4 address mapped into IPv6 counts as its IPv4 address) and starts on any listener. A request carrying any header whose name starts `Tailscale-` from a peer it does not trust is refused (403), so a forged header never passes as a user or as anonymous; one with no such header is anonymous to this provider. From a trusted peer, a request with `Tailscale-Node-Tags` signs no one in (a tagged node is a machine), and one with no login is anonymous, which is how the proxy's health check arrives. Matching uses `ipnet`, already in the tree under reqwest. The list sits with the provider's security settings (PRACTICES, No configuration by default).
- Alternatives: treating forged headers from an untrusted peer as anonymous (it hides a misconfigured or hostile client behind a 401 that looks like a missing sign-in; refusing names the problem); trusting `X-Forwarded-For` to find the original client (the proxy is the peer that matters, and a forwarded chain is client-written); a direct mode that asks the local tailscaled who the peer is (two ways to do one job, and neither deployment needs it); an implicit trust of this machine when the list is left out (a listener reachable by others would then need its own rule).
- What would change it: a proxy whose source address is not stable, which would call for authenticating the proxy itself (mutual TLS or a shared secret header).
