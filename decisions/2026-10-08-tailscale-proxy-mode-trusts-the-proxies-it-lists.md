# Tailscale proxy mode trusts the proxies it lists

- Question: a deployment wants Cairn behind an authenticating reverse proxy on another machine, which strips inbound `Tailscale-*` headers, asks tailscaled who the peer is, and sends `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-Node-Name`, and `Tailscale-Node-Tags` upstream. Proxy mode trusted the headers only from this machine, on a loopback or unix-socket listener, so the proxy could not reach it, and direct mode would see the proxy's node, not the user. How does proxy mode trust a proxy elsewhere without trusting anyone who can reach the listener?
- Call: proxy mode takes an optional `trusted_proxies`, a list of IP addresses or CIDR networks. Absent, nothing changes: the proxy is `tailscale serve` on this machine and the listener must be one only this machine reaches. Present, it must list at least one source; the provider starts on any listener and trusts the headers only from a peer inside a listed source (an IPv4 address mapped into IPv6 counts as its IPv4 address), loopback included only if listed. A request carrying any header whose name starts `Tailscale-` from a peer it does not trust is refused (403), so a forged header never passes as a user or as anonymous; one with no such header is anonymous to this provider. From a trusted peer, a request with `Tailscale-Node-Tags` signs no one in (a tagged node is a machine, as in direct mode), and one with no login is anonymous, which is how the proxy's health check arrives. Direct mode never reads the headers, and `trusted_proxies` there is a configuration problem. Matching uses `ipnet`, already in the tree under reqwest. The list sits with Tailscale's other security settings (PRACTICES, No configuration by default: proxy mode is one of them), since two real deployments, `tailscale serve` on the box and an edge proxy elsewhere, need different values.
- Alternatives: treating forged headers from an untrusted peer as anonymous (it hides a misconfigured or hostile client behind a 401 that looks like a missing sign-in; refusing names the problem); trusting `X-Forwarded-For` to find the original client (the proxy is the peer that matters, and a forwarded chain is client-written); refusing a non-loopback listener unless it is bound to the proxy's interface (the peer check already decides, and binding is the host's choice); a second listener so direct mode on the tailnet and proxy mode behind the edge serve at once (it needs a list of listeners, each with its own providers and `Host` names, and a shared in-flight limit across them: more than the deployment needs while the edge serves the tailnet too).
- What would change it: a proxy whose source address is not stable, which would call for authenticating the proxy itself (mutual TLS or a shared secret header); a deployment that must serve the tailnet directly and through the edge at once, which would bring the listener list above.
