# DNS-rebinding protection is a Host allowlist of names in front of the whole router, built by 4.7

- Question: the review found that turning rmcp's `Host` allowlist off leaves a gap the API shares: the dev provider without a token and Tailscale in direct mode authenticate on the peer, so a page whose name an attacker rebinds to the server's loopback or tailnet address can drive `/mcp` and the API as that user. The session cookie (host-scoped, `SameSite=Lax`) and the JSON content type do not help once the browser believes the request is same-origin. No brief carried a `Host` check.
- Call: one `Host` allowlist in front of the whole router, built by the binary from the public URL's authority (and loopback names when the listener is bound to loopback), refusing any other `Host` before the auth layer; MCP keeps rmcp's own check off, since the listener's covers it. Added to 4.7's scope and acceptance. Until 4.7 nothing is served outside tests. The allowlist matches names, not ports: a request is served when the host name in its target's authority, or else its `Host`, equals the public URL's host or, on a loopback-bound listener, `localhost`, `127.0.0.1`, or `[::1]`, compared case-insensitively with a trailing dot ignored; any port is accepted, and a malformed port or credentials are refused. A rebinding page can choose its port but never a name other than its own, so the name is what protects the peer-trusting providers. A refused request is answered 421 Misdirected Request in plain text and logged with the host it named, before the request id, the auth layer, the limits, or any handler; the layer wraps the API, `/mcp`, auth's routes, `/metrics`, and the UI alike.
- Alternatives: rmcp's check on `/mcp` only (the API stays open to the same attack); a check inside the auth providers that trust the peer (each would need the public URL, and the UI's routes would stay exposed); matching name and port (breaks proxies that forward or drop the port, and Vite's development proxy, which forwards its own `127.0.0.1:<port>`); refusing with 403 or 400 (421 says the server does not answer for that name, which is what happened).
- What would change it: a deployment reached under several names, which would make the allowlist a list in the configuration (public URL aliases).
- History: the MCP review (4.3) placed the allowlist in front of the whole router; building it, the binary brief (4.7) settled that it compares names only and refuses with 421 (first recorded as "the Host allowlist matches names, not ports, and refuses with 421").
