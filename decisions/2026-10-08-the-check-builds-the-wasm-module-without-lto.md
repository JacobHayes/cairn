# The local check builds the browser host's module without LTO, and CI builds it as it ships

- Question: the browser host's module was built in the `wasm` profile (release, LTO, one codegen unit) for every use, so any change to the engine, schema, or service cost about 50 s of LTO link in `mise run check` (rung 5's `gen`, then rung 6). Brief 4.5 kept one profile because "the bindings depend on how the module was compiled" (plain release bound differently from the LTO build). Does the check need the optimized module, and do the committed bindings?
- Finding: the bindings depend on stripping, not on LTO, codegen units, or opt-level. An unstripped module keeps its `target_features` section, and wasm-bindgen 0.2.129 then binds with multiple return values; a stripped one binds through the stack. Built stripped at opt-level 0 and 1 (dev) and at opt-level 3 without LTO (release), the module binds to files byte-identical to `web/wasm/generated/`; unstripped dev builds do not.
- Call: a `wasm-dev` profile (dev, opt-level 1, no debug info, stripped) is the default of `mise run build:wasm`, so a local `check`, `gen`, and `serve` build it. `CAIRN_WASM_PROFILE=wasm` selects the optimized build: `mise run build` (the release binary) always sets it, and CI sets it for the whole ladder, so on every push rung 5 checks the committed bindings against the module as it ships and rung 6 tests that module. A difference between the two profiles' bindings therefore fails one of the two checks, never passes silently. After an engine change the module rebuilds in about 14 s instead of about 50 s; the browser tests take the same time with it (opt-level 0 builds in 4 s but triples the wasm package's test time).
- Alternatives: generating the bindings from the fast build while the check also built the optimized one (still pays the link); opt-level 3 without LTO (about 21 s, no faster at run time in the tests); running the optimized build only in `gen` (then the check's rung 5 runs the slow build anyway, since it runs `gen`).
- What would change it: a wasm-bindgen version whose output depends on more than stripping (CI's rung 5 fails on it), or a browser test that only fails optimized (CI runs that module).
