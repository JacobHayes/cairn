# Sent edits are kept as versioned tab records

Question (from the write identity work; PRD H5, H6): a write that got no answer, or was rejected, lived in a component and a map on the sync chip, so leaving the screen or reloading the page lost it, though it may have committed. What does a tab keep of an edit, where, and what happens to it across a reload and a new build?

Call: the tab keeps one record per write that may still matter, in `sessionStorage` under `cairn:edit:<patch id>`, so a record survives a reload and not closing the tab. A record is plain data: the command (the patch and its note), what the edit is about (the control's edit key, its label, the screen it was made on), how far delivery got (`sending`, `unconfirmed` with its failure, `rejected` with its rejection, `stopped`, `gone`), and the automatic resubmissions it used. It is never an XState snapshot. The record schema version is one integer in code, bumped by hand when a record's shape or a command's meaning changes, and exactly one version is accepted; a record of another version, or one this build cannot read, is dropped with a visible note and counted. Records of the current version survive a new build, so a version-skew reload, and a deploy that only changes the build digest, keep unsent edits. A record restored in `sending` or `unconfirmed` may have committed: it becomes an `unconfirmed` write and resends at once with its patch id, which the API answers idempotently; a rejected, stopped or gone record is held for the person. If storage refuses a record, the tab says once that edits are kept only until reload. This is draft recovery, not an offline queue: a record that was refused or never sent (`stopped`) is not resent by itself.

Alternatives: persisting XState snapshots (they tie storage to the machine's shape and the library's version, so every change to a state is a migration); `localStorage` (edits would outlive the tab and reappear in another, long after the revision they were drafted against); an offline queue (the PRD names none, and a queue would resend edits drafted against revisions long gone); versioned records accepting older versions (a permanent branch in the loader for data that lives one tab session).

Known limit: duplicating a tab copies its `sessionStorage`, so both tabs restore the same records and both resend the same patch id. The API's idempotence makes that safe: one commits and the other is answered `already_applied`.

What would change it: an offline queue, a record that must outlive the tab, or a record shape that churns often enough that a dropped record becomes a common surprise.
