# What a domain patch reports, and when it is worked out

- Question: D7 asks every accepted patch to report what it newly caused in derived state, but neither D7 nor ARCHITECTURE says which journeys a deployment patch reports on, whose viewer the two sides are derived for, or whether they are derived before or after the commit. The engine answers a stale patch with an empty intervening touched set (DECISIONS.md 2.1: the host fills it in), and the store had no way to ask for one outside a commit. A journey patch whose riding entity create moves the deployment revision computes that revision from the records it loaded, which another riding create may have passed meanwhile.
- Call: (1) Consequences are reported per journey, for the patch's own journey and, for a deployment patch, for every journey an entity merge was checked against (aliases change what a condition comparing entities evaluates to, E6); a route patch reports none, since it never touches a journey (Journey durability). A journey the patch creates is compared with an empty graph; one it deletes reports nothing. (2) Both sides are derived at the request's today with no viewer: what a patch caused is the same for everyone. (3) They are derived before the commit, inside the same caught engine call as `apply`, so an engine panic commits nothing, and a committed patch always answers with its consequences. (4) The `Store` trait gains `intervening(conflicts)`, the touched set a stale commit would report, which both backends already computed for their own stale answers; the service adds it to the engine's stale rejection (conformance: `what_intervened_since_a_revision_is_reported_on_request`). (5) After a commit the service announces its domain at the receipt's revision and, when an entity create riding in the patch moved the deployment, the deployment at the revision read back from the store, never the one the engine's records computed (they also move it for a hard delete, which the store does not: review round 1); when the read fails, the computed revision is announced, which a riding create makes this commit's or an earlier committed one (review round 2).
- Alternatives: (1) consequences only for journey patches (a merge that makes work relevant would report nothing); (2) the caller's viewer (the same patch would report differently to different people); (3) derived after the commit (a panic would answer an error for a committed patch, and its resubmission is answered from the receipt with no consequences); (4) the service replaying the event log to find what intervened (O(history) per stale patch); (5) announcing the computed deployment revision (a subscriber already told of a later one would ignore it, and one told of a revision never committed would ignore the real one when it comes).
- What would change it: rank (2.5) needing the viewer for something D7 reports; a host that cannot afford two derives per journey patch, which 4.8's memoized reads would make one.
