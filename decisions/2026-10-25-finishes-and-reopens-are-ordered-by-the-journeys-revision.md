# Finishes and reopens are ordered by the journey's revision

The question, from a property test that failed on main: finished work is stale when a dependency it relied on is reopened after it finished. Finishes and reopens recorded only their day, so on one day the engine could not tell which came first, and read a tie as "relied on". Work finished after its dependency was reopened that same day was stale the moment it was finished. Swapping the tie the other way would instead miss work finished before a same-day reopen. What should order them?

The call: the journey's revision. A finish records the revision it was written at alongside its day, always both or neither. A reopen record is two revisions: its own and that of the finish it undid. Its days are gone, since nothing read them. Staleness compares revisions only: a dependency was relied on when it finished no later than the work did and was reopened after. Writes in one patch share a revision and are not ordered, so work finished in the patch that reopens what it waits on does not count as relying on it: a finish is never stale on the graph its own patch produced, and the other reading would flag work finished just after a reopen in the same patch, the bug this fixes. Finish days stay as the actual dates people see and edit. Staleness no longer reads them, so editing an actual date cannot change what is stale. The one exception is a milestone that marks itself done on its date. It is satisfied only from that day, and is compared by day against the work's actual finish date.

Existing data is migrated once, from the log. Each journey's events are walked in order, and each finish and reopen takes the revision of the patch that first wrote it, from that patch's receipt. Events and receipts are never pruned while their journey exists. The events' JSON is rewritten with the same values the table takes, so replaying the log still gives the stored state. A finish or reopen with no event behind it, or first written by a patch without a receipt, fails the migration rather than being guessed.

Alternatives: timestamps (`finished_at`), which a person can read but which a clock stepping back can misorder, and which tie whenever two writes share a time (every test does). Keeping days and adding the revision only to break same-day ties (two clocks and a fallback rule for the price of one). Flipping the same-day tie (wrong for the other order). Leaving old records without revisions and giving "none" a fixed place in the order: it keeps a second meaning in the code forever, and misorders old history (an old finish after an old reopen would read as before it).

What would change it: needing to order events across journeys, which one journey's revision cannot do.
