# [turso] Turso is embedded through the `turso` crate, C-ABI libraries and all

- Question: every build compiles Turso's two C-ABI crates, `turso_sdk_kit` and `turso_sync_sdk_kit`, as static and shared libraries (about 450 MB a target directory) that nothing links. Is there a cleaner way to embed Turso in the Turso backend?
- Call: keep `turso` (default features off) as the one Turso dependency, and accept the libraries until Turso stops building them for Rust users. `turso` 0.8.2 is a thin async layer over `turso_sdk_kit`'s Rust API (`rsapi`) and depends on both C-ABI crates unconditionally, with no feature that drops them, and `turso_sdk_kit` declares `crate-type = ["lib", "cdylib", "staticlib"]`. Cargo builds every crate type a dependency declares, and a consumer cannot turn that off. The engine crate, `turso_core`, is reached through `turso`'s own re-export (`turso::core`), so the test seam names the same version `turso` uses.
- Measured on a cold build of the Turso backend with its tests and no build cache (12 cores, a shared host): with the libraries 2.25 GB of target directory, with `turso_sdk_kit` and `turso_sync_sdk_kit` patched to `lib` only 1.79 GB, and the same compile time within noise (127 CPU seconds either way; the libraries link in about 2 seconds because dependencies carry no debug info). A release build of the backend: 1.03 GB against 0.81 GB, and 355 against 346 CPU seconds. The cost is mostly disk, once per target directory and profile, plus `bindgen` and `clang-sys`, which `turso_sdk_kit` lists as build dependencies its build script does not use on Linux.
- Alternatives: depending on `turso_core` alone (its API is a synchronous step loop with no documentation for applications; the store would reimplement `turso`'s statement stepping, I/O wakeups, busy and dangling-transaction handling, and error mapping, which the durability decisions were measured against; Turso's documentation and both C-ABI crates' descriptions direct Rust applications to `turso`); `turso` with fewer features (its defaults are already off, and no feature gates either C-ABI crate); a `[patch]` to a fork with `crate-type = ["lib"]` (a fork to rebase on every pinned upgrade, for disk only).
- What would change it: a Turso release where the Rust SDK depends on an rlib-only crate. The upstream issue should ask that `turso_sync_sdk_kit` become an optional dependency of `turso` behind its `sync` feature (only `sync.rs`, already behind that feature, uses it); that the C ABI (`capi`, and the `cdylib`/`staticlib` crate types) move to a crate of its own that bindings build, leaving `rsapi` as an rlib `turso` depends on; that `turso` depend on `turso_sdk_kit` and `turso_core` with default features off and forward its own, so a consumer can drop encryption and `simd` (decisions/2026-10-06-patina-turso-links-symbols-the-shim-refuses-to-run-beside.md); and that the unused `bindgen` build dependency go.
