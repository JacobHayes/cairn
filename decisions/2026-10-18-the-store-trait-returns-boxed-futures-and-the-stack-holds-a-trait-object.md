# The Store trait returns boxed futures and the server stack holds it as a trait object

- Question: the 2026-10-06 call made `Store` return `impl Future + Send` and the service, auth, assistant, MCP and API layers generic over it, so every one of those crates, and every host and test binary, was compiled again for each backend (the `cairn` binary builds two). A timing probe on the inner loop (the build-time work that precedes this change) found that doing so is the largest cost left in a build: an edit in an API crate cost about 240 CPU-s, a fresh test build about 930. Should the generics stay?
- Call: no. `Store`, `AuthStore` and `ConversationStore` return `StoreFuture<'a, T>`, a boxed `Send` future, so they are object-safe; the service, auth, assistant, MCP and API layers, the composition roots and the test support hold `Arc<dyn Store>` and lose their store parameter. Both backends implement the traits directly (the memory backend completes every call at once, so its futures are `Send` and the browser host still builds). There is no second trait and no `async-trait`. The notifier was already a trait object; PRACTICES' "No dynamic dispatch" now names the store as an exception in fact, not only in intent. The conformance suite stays generic over the concrete backend it exercises through its own entry points; its helpers take `&dyn Store`.
- Alternatives: a twin object-safe trait with a blanket impl over every `Store` (backends untouched, but a second copy of the trait and a wrapper type to keep in step); an enum over the two backends (it puts the Turso driver in front of the API, MCP and assistant crates and into the browser host); keeping the generics.
- What would change it: a measured per-call cost on the server that matters (one allocation and a small wrapper per store call; a request makes a handful of calls and Turso already boxed its commit), or a host that cannot afford the allocation.
