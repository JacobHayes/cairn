# Object-safe async traits use async-trait and the server stack holds the store as a trait object

- Question: the 2026-10-06 call made `Store` return `impl Future + Send` and the service, auth, assistant, MCP and API layers generic over it, so every one of those crates, and every host and test binary, was compiled again for each backend (the `cairn` binary builds two). A timing probe on the inner loop (the build-time work that precedes this change) found that doing so is the largest cost left in a build: an edit in an API crate cost about 240 CPU-s, a fresh test build about 930. Should the generics stay?
- Call: no. `Store`, `AuthStore` and `ConversationStore` are declared with the `async-trait` crate: implementations write plain `async fn`, and the macro boxes each call's future as `Send`, so the traits are object-safe; the service, auth, assistant, MCP and API layers, the composition roots and the test support hold `Arc<dyn Store>` and lose their store parameter. Both backends implement the traits directly (the memory backend completes every call at once, so its futures are `Send` and the browser host still builds). There is no second trait. The auth provider (`AuthProvider`, and the `Authenticate` trait its routes use) is a trait object with hand-boxed futures behind `BoxFuture` and `Answer` aliases; they use `async-trait` too, so the codebase has one idiom for an object-safe async trait and the aliases and their `Box::pin` wrappers are gone. `async-trait` is a direct dependency of the auth crate as well. `async-trait` is a direct workspace dependency of the store crates; it was already compiled in the tree through rmcp. (The first form of this call hand-wrote the boxed futures behind a `StoreFuture` alias; the owner chose the macro the same day for plainer code: no `Box::pin(async move { .. })` wrapper in a backend.) The notifier was already a trait object; PRACTICES' "No dynamic dispatch" now names the store as an exception in fact, not only in intent. The conformance suite stays generic over the concrete backend it exercises through its own entry points; its helpers take `&dyn Store`.
- Alternatives: hand-written boxed futures behind an alias (no dependency, but every implementation wraps each body by hand); a twin object-safe trait with a blanket impl over every `Store` (backends untouched, but a second copy of the trait and a wrapper type to keep in step); an enum over the two backends (it puts the Turso driver in front of the API, MCP and assistant crates and into the browser host); keeping the generics.
- What would change it: a measured per-call cost on the server that matters (one allocation and a small wrapper per store call; a request makes a handful of calls and Turso already boxed its commit), or a host that cannot afford the allocation.
