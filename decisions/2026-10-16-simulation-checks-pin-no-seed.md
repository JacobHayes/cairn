# Simulation checks pin no seed

- Question: the durability testbed's leg 6 pinned `--seed 5 --fs-error-permille 5` as the regression for a commit whose log fsync fails (the store must fail closed), and leg 7 pinned seeds 27, 3 and 6 for the Turso gaps. When the crash-sweep fix shifted the sequence of filesystem operations, the pinned run moved from seed 2 to seed 5 and its failure message read "find a new seed". Should a check be allowed to depend on one seed producing one outcome?
- Call: no. A seed reproduces a run on one exact binary and configuration; after any change to the code, the compiler or the dependencies it names a different run, so a check that passes or fails by what one seed happens to do tests luck. A simulation check either names the event it injects or states a property that holds on every binary. Concretely:
  - The failed commit fsync is a deterministic store test through the I/O seam (`log_sync.rs`, already there), and the testbed judges every run: a write that fails at a sync, landed (its receipt is visible), and leaves the store answering is a violation (a sync can also fail on Turso's temporary database before the commit, when nothing landed and the store rightly answers on), and a `sometimes!` oracle on the failed sync that did close the store makes leg 4's campaign require that the case happened. The pinned run is gone.
  - Two Turso gaps (a size error on the log panics the open; a short read of the log header fails it) are cases of the store's tests (`open_faults.rs`) that inject exactly that fault and assert Turso still misbehaves. The third (a retried open panics in the page cache) needs a failure at a point only a run's fault draws reach, so leg 7 sweeps seeds 1 to 64 and passes if any reproduces it. (That sweep is removed: decisions/2026-10-17-simulation-runs-no-known-gap-checks.md.)
  - Sweeping seeds as sampling, recording one run twice for determinism, and `--seed 1` on a gap that holds for any seed stay as they are. The campaign's fault scale (100 per mille) is a rate whose coverage the oracle gate checks, not a seed range, so it stays. No `proptest-regressions` files exist; had one been needed it would be an explicit hand-built case.
- Alternatives: re-pinning a new seed on each break (the status quo: noise on every unrelated change); a bespoke "seeds 1..K, at least one hit" loop for the failed sync (the campaign's `sometimes!` gate already does that job); patina failing the Nth sync of a file by name (not supported at the pinned revision; it would make the third gap and the sync case sim-level named events).
- What would change it: patina learning to fail a named operation (the Nth sync of a path), which would turn the remaining sweep into a named injection.
