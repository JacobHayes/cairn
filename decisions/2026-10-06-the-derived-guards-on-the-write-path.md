# The derived guards on the write path

- Question: D4 lists relevance among the completing guards ("relevant") without saying whether `undecided` passes; ARCHITECTURE runs the guards against one derive of the final candidate but not what happens when the candidate breaks a structural invariant; the brief wants a failure to name the mutation that caused it; a stored bypass outlives the completion it covered; and B6's "transitively depends" does not say over which edges or how often it is checked.
- Call: (1) the relevance guard refuses only a node that is not relevant (force include is the escape hatch). Undecided work is completed, answered, or reached with a non-blocking warning: the patch's consequences (D7) list each finished node newly undecided with the unanswered decisions its relevance reads, so clients say "this may not apply, since <decision> is unanswered". The node stays undecided and is never forced into scope; if the answer later makes it not relevant, it is finished work that does not apply. For an undecided node, `deps_done` (as a guard and as `stale` reads it) leaves out the node's condition gates, which hold it only until its relevance is known; every other dependency still holds it and is still bypassable. The warning rides in the consequences because they are already D7's channel for non-blocking reports (a shortfall is a warning there) and reach the API, MCP, the in-browser host, proposal previews, and the assistant unchanged; so reopening a deciding decision under finished work reports the same warning instead of `stale`. (2) The derived stage runs only when the patch's journey holds every graph invariant (derive asserts them), like the plan check; the structural violations are reported instead. (3) Each failure carries `Violation.caused_by`: the patch's other mutations whose writes shaped the node, the open dependency, or the ancestor, condition, or stage that carries it (structure), the dependency's or a read decision's state, or their overrides. (4) Reopening a node clears its guard bypass, so a recorded failure is never accepted for a later completion. (5) A `deps_done` bypass records each open dependency as `OpenDependency` on the stored bypass and its event, beside 2.1's artifact and breakdown failures. (6) Snooze wait cycles are a graph invariant: each node snooze is a wait from the snoozed node's start to its target's finish over the full set's gate edges, so a target that depends on the snoozed node, is its ancestor, or waits on it through another snooze is rejected on every patch, independent of answers. (7) Beyond the ruling's terminal and not-relevant cases, a snooze on an effectively skipped node is also rejected, since an effective skip is a terminal state for every other purpose.
- Alternatives: (1) refusing undecided work until the decision is answered or the node is force-included (the first call); allowing it by forcing it into scope automatically (a later answer could no longer drop it); keeping the condition gates in `deps_done`, so finishing undecided work needs a bypass every time; a separate warnings list on the patch answer (a second channel beside the consequences, threaded through every host); (3) naming only the completing mutation; (4) bypasses kept until removed by hand; (6) the pruned set (an answer could then make an accepted snooze illegal, or the reverse) or a check only on snooze mutations (an edge added later could close the cycle unseen).
- What would change it: people surprised that finished undecided work was dropped by a later answer, which would argue for a confirmation step before finishing it; a need to keep a bypass across a reopen.
- History: the engine brief (2.4) first refused completing, answering, or reaching undecided work (the node also failed `deps_done` on its deciding decision); the owner then chose to allow it with a warning only, keeping the snooze rules and the bypass cleared on reopen.
