# Every write goes through the edit manager

Question (from moving the remaining write paths onto the edit manager; PRD H5, H6, A11, A13, E6, C19, B13): the manager owned a section's rename, but a screen's write, authoring, proposals, an import, a merge and the stepper's insertion each kept a write of their own, with their own rejection state, their own clearing rule and their own loss on a reload. What does a write look like when every control hands it to the manager, and what is left to the control?

Call:

- A command has three kinds, plain data like the patch before it: a patch, a proposal write (a tagged call: create, edit, discard, refresh, apply, upgrade, save as route, re-link, each with its request, which names the patch id), and a route import (the request with its file). A stale answer to any command is a rejection for a person to review again, because what they saw has moved. The record version goes from 1 to 2, since a record now holds one of three command kinds; a version 1 record is dropped and counted as any other.
- A control finds its write by a stable edit key made from what it is (`node:<journey>:<scope>`, `author:<domain>:<scope>`, `proposal:<id>`, `import:route:<id>`, and so on), never from `useId()`, so a control that is shown again finds its write, and a rejection survives leaving the screen. Two controls that show the same refusal would list it twice, so they have different keys (the resource form and the resource list of a node).
- One clearing rule for every path: a rejection stays until the person discards it, or until the next write of the same edit starts, which replaces it. The control's own `dismiss` discards only a rejected, stopped or gone write, never one still out.
- A pre-send check is the first phase of the write (`checking`, busy), not a step before it. Authoring's engine preview runs there: a refusal becomes the write's rejection, kept and listed like the host's, and nothing is sent. This removes the case where a stale "unanswered" state from an earlier stopped write sat beside a fresh preview rejection.
- Workflows are machines their component owns: the import (read the file, discard an open draft, import), the merge (read the journeys referring to both entities, then one deployment patch naming each at the revision read) and the stepper's insertion (choose, place, map). Their delivery steps are writes of the manager, found by the workflow's edit keys; stopping a workflow (the component going away) stops waiting for the answer and never the write. An import that is refused for an open draft carries its file in the refused command, so replacing the draft works after a reload, and the flow reads the route as it is then (a discard that landed meanwhile is not sent twice). The stepper keeps its choices as a plain draft whenever they change and corrects a restored draft on the way in; its insertion key is minted once.
- The edge drawing is a machine the page owns, with a stable edit key per edge, and checks the pick with the engine itself so a refusal returns the drawing to choosing with its reason; only a pick the engine accepts reaches the manager. It is the one authoring path whose pre-send check is not the write's first phase, because a refused pick is not a write that needs a person: nothing is held, and the pick can simply be made again.
- A proposal write that drafts a proposal (create, upgrade, save as route, re-link) records a save with the way to it, shown in Recent as Review it. The screen that would have opened the proposal may be gone (a write resent after Retry lands with no control waiting), and the app has no proposal index, so without the link a landed proposal would be unreachable and drafting again would make another.
- The browser host answers a failed proposal write or import with status 0, which the write treats as a lost answer: a refusal by the in-browser root is resent a few times before it asks for Retry. A lost answer is the same request with the same ids, so the resend is harmless.

Alternatives: keeping a hook per path with its own rejection state (the defects this removes: a rejection lost on navigation, a stale `unanswered` after a refused preview, a rejection that stays under one control and clears under another); one manager command kind with an optional flag (it hides the difference between a patch and a proposal behind a boolean, and the record would not say which it is); making the pre-send check a separate request before the write (the write would not be held while it runs, so a second submit could start a second check); `useId()` for edit keys (a remounted control would not find its write).

What would change it: a host that reports a real status for the in-browser root, which would remove the resends of a refusal there. Wish, not applied: every form follows the rename's model (the typed text is kept apart from the write, so a landing never clears text typed after the save); today some forms clear their draft when the write they sent lands.
