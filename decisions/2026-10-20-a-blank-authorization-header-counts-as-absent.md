# A blank Authorization header counts as absent

- Question: on the reference deployment behind IAP, every MCP call from a signed-in client was refused with `invalid_token`. IAP accepts the client's Google ID token from `Authorization`, then passes the request on with `Authorization` present but empty beside a valid assertion (observed on the wire; the fake IAP passed the header on unchanged, so the tests never met it). The layer refuses any `Authorization` that is not a bearer token some provider claims (`2026-10-06-a-provider-answers-a-verdict-and-every-provider-hears-every.md`), so the assertion was never weighed. What does the layer make of an empty header (MCP sign-in behind IAP)?
- Call: an `Authorization` header whose values are all empty or only whitespace holds no credential and counts as absent; the session and the providers decide the request as if it were not there. Any other value that is not a claimed bearer token (`Basic ...`, `Bearer` with no token, an unclaimed token), alone or beside a blank one, is still refused. The fake IAP now blanks `Authorization` when it took the Google ID token from it, as IAP does.
- Alternatives: have the IAP provider claim an empty header (the layer's check runs before any provider and is about credentials in general; a provider claiming "nothing" bends `claims_bearer`); strip the header at the load balancer (it may run before IAP reads the token, and every deployment would need it); send the token in `Proxy-Authorization` (MCP clients send what the token endpoint returns as a bearer in `Authorization`, and cannot be told otherwise).
- What would change it: a client or proxy that sends a blank `Authorization` meaning something (none is known), or IAP passing the token on instead of blanking it, which the layer already accepts.
