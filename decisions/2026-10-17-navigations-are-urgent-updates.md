# Navigations are urgent updates, not transitions

Question (from sweeping the browser tests that failed only on a loaded machine): the router wrapped every change of address in `React.startTransition`, so the page kept drawing the old address while the new one rendered at low priority. A click or key that came in meanwhile was handled against the old address: Escape then `v` switched the view of the node Escape had just closed, a click on a card then a shift-click on another selected only the second, and a row opened by its title then another row checked made a set without the first. On a fast machine the window is a few milliseconds; on a loaded one or a slow phone it is long enough for a person to hit it, and three tests did, most of the time with the page's CPU slowed four to six times. Should every handler read the live address instead, or should the address stop lagging?

Call: the app's router runs without transitions (`<BrowserRouter useTransitions={false}>`). A navigation from a click or key is then rendered before the next input event is handled, so every handler that derives the next address or selection from the current one sees the move before it. The cost: the first visit to a screen whose code is still loading shows the shell's "Loading..." in place of the previous screen for that moment, instead of holding the previous screen.

Alternatives: keep transitions and have each handler read `window.location` (and the selection track the address it last asked for) at event time, which spreads a second source of truth for the address over every key, click and selection handler; or keep transitions and wait in each test for the visible result before the next action, which hides the bug from the tests and leaves it for people.

What would change it: a screen that must hold the previous screen while its code loads (then preload that screen's code, or wrap only that navigation in a transition), or React offering transitions that input events cannot overtake.
