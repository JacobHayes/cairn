# [turso] an open under injected I/O faults panics or fails where it could recover

- Question: does Turso 0.8.2 handle the filesystem faults patina injects at open?
- Call: three gaps, each with a leg in `testbeds/durability/sim.sh` (leg 7) that fails once it stops reproducing. An I/O error on the logical log's size check panics (`mvcc/persistent_storage/logical_log.rs:1674`, `expect("failed to get file size")`; seed 23, `--fs-error-permille 50`); the testbed treats exactly that panic at open as a store that did not open. A short read of the log header fails the open (`Logical log short read: expected 56, got 36`; seed 3, `--fs-short-permille 200`) instead of reading on. An open retried in the process a failed open ran in panics in the page cache (`Attempted to insert different page with same key`, then `end_write_tx called while write lock not held` while unwinding; seed 6, `--fs-error-permille 20`, `-- --open-attempts 64`), so the binary (4.7) must exit on a failed open rather than retry. Separately, `EINTR` from a read, write, or sync is reported as an error rather than retried. None of these loses data; each makes the store unavailable.
- Alternatives: retrying opens in-process in the testbed (it reaches the third panic); waiving the campaign's failures (it would hide new ones).
- What would change it: a Turso release that fixes them; then the gap legs fail and this entry and the testbed README are updated.
