# [turso] an open under injected I/O faults panics or fails where it could recover

- Question: does Turso 0.8.2 handle the filesystem faults patina injects at open?
- Call: three gaps, each with a check that fails once it stops reproducing (two as cases in `store_turso/open_faults.rs`, the third in leg 7 of `testbeds/durability/sim.sh`, which sweeps seeds for it). An I/O error on the logical log's size check panics (`mvcc/persistent_storage/logical_log.rs:1674`, `expect("failed to get file size")`); the testbed treats exactly that panic at open as a store that did not open. A short read of the log header fails the open (`Logical log short read: expected 56, got 36`) instead of reading on. An open retried in the process a failed open ran in panics in the page cache (`Attempted to insert different page with same key`, then `end_write_tx called while write lock not held` while unwinding, under `--fs-error-permille 20` and `-- --open-attempts 64`), so the binary (4.7) must exit on a failed open rather than retry. Separately, `EINTR` from a read, write, or sync is reported as an error rather than retried. None of these loses data; each makes the store unavailable.
- Alternatives: retrying opens in-process in the testbed (it reaches the third panic); waiving the campaign's failures (it would hide new ones).
- What would change it: a Turso release that fixes them; then the gap legs fail and this entry and the testbed README are updated.
