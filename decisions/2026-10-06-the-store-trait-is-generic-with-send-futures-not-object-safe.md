# The Store trait is generic, with Send futures, not object-safe, and the service is generic over it

- Question: ARCHITECTURE asks for an async trait that names no runtime, with the composition root picking a backend. Async trait methods are not object-safe, and a multi-threaded server needs the futures to be `Send`.
- Call: `Store` (with `AuthStore` and `ConversationStore`, its supertraits) declares each method as returning `impl Future + Send`; the service layer (4.1) is generic over `S: Store`, and each composition root names its backend's type. No `async-trait` or boxing dependency. The Turso backend boxes its commit internally, since a commit's state machine is tens of kilobytes. The service is `Service<S: Store>`, holding the store as `Arc<S>`, shared with the auth layer, whose `Accounts<S>` already takes an `Arc<S>`, and the notifier as `Arc<dyn Notifier>`: the notifier's methods are synchronous, so it stays a trait object as PRACTICES (No dynamic dispatch) intends. Every operation's future is `Send` when the store's are, which a test asserts over both stores; `MemoryStore`'s futures are `Send` too (a `std` mutex), so the same service builds for `wasm32-unknown-unknown` (rung 1).
- Alternatives: `async-trait` boxing every call (a dependency and an allocation per call, for a choice made once per process); an enum over the two backends (the browser host would carry Turso); a generic notifier (a type parameter for a seam with one implementation per host, and tests could not swap it).
- What would change it: a host that must choose among more backends at run time without generics.
- History: the service brief (4.1) first planned the store, notifier, and auth provider as trait objects, as PRACTICES lists them; when it was built it followed this store call instead, keeping only the notifier a trait object (first recorded as "the service is generic over its store and holds its notifier as a trait object").
