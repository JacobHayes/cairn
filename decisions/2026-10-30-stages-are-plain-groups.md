# Stages are plain groups

Question: a stage (a top-level group) carried four fields of its own, an opening milestone and a closing milestone, each with a switch for whether it gated or closed. Every one of them said what an ordinary requirement and an ordinary due-by already say. Do they stay (work: simplifying the model)?

Call: they go. A stage is a group like any other.

- An opening milestone becomes a requirement of the group on that milestone, so everything inside inherits the wait. A closing milestone becomes the group's `due_by` before that milestone. Where the group already has a rule of its own, a zero-offset rule takes the milestone as one more source, a rule already before that milestone is left alone, and any other rule cannot say both: the migration then refuses, listing every such group, and writes nothing. A group that would pass the edge limit by gaining the requirement refuses the same way. The live deployment has none of these cases; the derived dates, blockers, and lists of every fixture and of a copy of the live data were equal before and after, apart from the moves a shortfall offers (the old "let the stage run past its close" is now "loosen the deadline rule" or "drop the requirement").
- The switch that let an opening date a stage without making it wait is dropped, with the hidden edge kind it needed. Every edge gates. What is lost: a planning-only opening that bounded when a stage's unstarted contents could start without ever blocking them. A not-before rule on the work can say a date, but it also holds the work back from the frontier; no stored data used the switch. "Not before" covers "do not start until a date", and a due-by covers "finish by".
- A skipped milestone's pin, and a date answered for it, bound nothing, wherever they are named: a stage's deadline, a task's, a rule's. This was already the rule (only pending pins feed dates); the code let a skipped milestone's pin through. It is also how a person drops a stage's date now: skip the milestone.
- The stored history is converted so every stored event still reads back. Proposals that held a stage edit lose those mutations and review items; an open one is discarded with a reason saying so (the deployment has none), a settled one keeps the rest.
- A route file that still carries the four fields no longer imports; the file format stays at version 1 and files are re-exported.

Alternatives and what each costs: keeping the fields (four fields, a second edge kind, a bar marker, a stage-only editor, and stage-only wording in every explanation, for what two ordinary fields say); keeping only the switch that stops a stage gating (the whole second edge kind stays for a case no data used); letting a group's own `not_before` hold its contents (it would change what that field means for every group); "unpin to drop a date" instead of the skip rule (leaves a skipped milestone still bounding work).

What would change it: a route that needs a stage to date its contents without making them wait, which a milestone with a not-before rule on the work would then have to stand in for.
