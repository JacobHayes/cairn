# Snapshot and list rows carry what an agent acts on

- Question: the work cutting the MCP context cost found a snapshot row at 177 to 218 tokens, a third of it the rank's breakdown, and a full page of 200 nodes at 45,000 tokens; the in-app assistant also reads a snapshot on every provider exchange. What does a snapshot or list row carry, and what does that mean for the HTTP API, whose snapshot shares the type?
- Call:
  - **A row is what an agent acts on.** A snapshot or list row is the node's key, title, kind, both states, its parent (on the frontier, its ancestors as the breadcrumb), owners, dates, the flags that hold, and its rank as one number to three significant figures. The rank's terms, the node's path, its gravity and unlocks, and its latest start (slack says it) are left to the node's own read, which keeps priority's full breakdown.
  - **A container's blockers leave out its own children.** A container waits on its open children by definition; naming each one was the largest repeated list in a snapshot. Every other blocker stays.
  - **A settled node keeps its row.** A finished, skipped or ruled-out node keeps its dates, shortfall, flags (so a finished node made stale still says so) and containment, but drops slack (room left to start) and rank (the order of work still to do).
  - **The snapshot's own parts.** Its node entries add participations other than the owners (the owners are on the row), blockers, the ancestors that block, and the earliest start when it is after today. A node no one owns is listed once, in the snapshot's `unassigned` list, not flagged on each row. The acting frontier lists each item's key, title, kind, display state, breadcrumb and rank in rank order: enough to say what is next, with the full row in the node list or in `list_frontier`. The journey's today (the answer already carries it) and a scope that is the whole journey from the first page are not repeated.
  - **The HTTP snapshot is the same type.** The snapshot is the agent's read on both transports, so `GET /snapshot` answers the lean shape and the generated OpenAPI document and client follow. No screen reads it: the app derives from the document in the browser. The next list, node detail, the level and history keep their full shapes, since clients render from them; `list_frontier` maps the next list's rows to the lean row.
  - **The page stays 200.** A smaller page for the node list, the frontier and list pages would hold a 200-node snapshot near 6,000 tokens; it changes an existing limit and awaits the owner.
- Alternatives:
  - Lean rows only in the MCP tools, the HTTP snapshot unchanged: two shapes for one projection, and the schema the agent is told would not be the one the server computes.
  - Keep slack and rank on settled rows: they measure work still to do and mean nothing for finished work.
  - Drop settled nodes' dates and flags too: a stale finished node and its containment would disappear from the agent's view.
  - Leave owners off rows that inherit them: an agent that does not walk up the tree would read that as no owner.
- What would change it: an agent that needs the rank's terms on every row (it would ask `get_node`, or the row would grow); a client of the HTTP snapshot that renders the full row.
