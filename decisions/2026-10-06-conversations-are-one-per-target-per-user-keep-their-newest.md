# Conversations are one per target per user, keep their newest 200 messages, and replay the dialogue only

- Question: the brief leaves context construction and conversation retention to the implementer. The store keeps a conversation whole by id and user, with no target; a conversation that grows without bound would outgrow the store's size cap and any provider's context; replaying an earlier turn's tool traffic would show the model state that has since moved.
- Call: a conversation's id is `cv_` and a digest of its target (a journey, or a route's draft) and its user, so each user has one per target and no one else reads it. It keeps the user's words, the assistant's replies, and Cairn's one-line report of each write and of how a turn ended without a reply; tool calls and results are not kept. It keeps its newest `page_item_count_max` (200) messages, a borrowed limit: each message is a Markdown body (64 KiB), so a conversation at its cap stays under `graph_bytes_max`, which a `const` assertion checks. Each turn starts from a fresh read of its target as the user (the journey's I3 snapshot, or `get_route` for the draft; a route that does not exist yet reads as such, since its first proposal creates it), placed in the system prompt after the shipped guide and workflows (I4) and the write policy; the dialogue follows as alternating user and assistant messages.
- Alternatives: keeping tool traffic (stale between turns, and large); a separate context budget in tokens (a new limit, which needs sign-off, and providers count tokens differently); one conversation per user across targets (the panel is per journey or draft).
- What would change it: a provider context overflow in practice, which would call for a named limit on the dialogue replayed; a panel (5.8) that lists or resets conversations.
