# Browser tests wait on a settled page, never on time

- Question: from the work to make the browser tests wait on events, not time. The Playwright suite failed now and then under load with no change to blame: a save sent at the revision before the test's own previous save had reached the page (a conflict instead of the refusal the test checked), reads compared before a refetch landed, a box measured while a screen was still loading. Each fix so far patched one wait. What removes the class?
- What made a test depend on time:
  - The page had no notion of "done". The sync dot's states are filtered by time (SAVING only after 300 ms, SAVED for 2 s), so no attribute said that nothing was under way.
  - A write's own commit reached the page's reads only with the server's next tick, which is coalesced for up to 250 ms. Between a save's answer and that tick, the page showed the revision before it, and a second save was sent at that base.
  - Over a hundred reads in the specs and helpers (`count`, `getAttribute`, `boundingBox`, `evaluate`...) take the page at one moment and do not retry; several were kept and compared later, or chose a branch.
- Call:
  - One settled fact. The session root keeps the set of reads at work: a keyed read registers while it settles or reads, and a screen's code while it loads (its Suspense fallback). Settled is a pure function of facts read from their owners: no read at work, no write in flight, and the stream not connecting or reconnecting. The sync dot carries it as `data-settled`. It has no timer, so it turns true the moment the work is done. What only the clock changes (SAVED fading, a toast, a failed read's next attempt) is not work: a page waiting out a failure is settled on what it shows.
  - A write's receipt is heard as a tick. When a patch lands, the session sends its receipt's revision to the tick subscription, which hands it to every watcher as the stream would. The page refetches its own commit at once instead of after the server's coalesced tick, so it shows a person's save sooner, and settled stays false until it does.
  - Tests read only a settled page. `settled(page)` in `e2e/shell.ts` waits for `data-settled` and for it to hold across two turns of the page's event loop (a render that settles may run effects that key new reads). Opening a screen and the write helpers end settled. A read that does not retry goes through `whenSettled(page, read)`, or sits inside `expect.poll` or `toPass`. Timer-driven displays stay under `page.clock`.
  - Reduced motion in the browser tests (`contextOptions.reducedMotion`): the app turns its motion off under it, so no box is read mid-transition, and the one wait for an animation's end goes.
  - eslint holds it. In `web/app/e2e`, `waitForTimeout`, `setTimeout`, `requestAnimationFrame`, `networkidle` and a `timeout` option are errors, and a non-retrying read on a Locator, Page, Frame or ElementHandle (by type, so a DOM element's `getAttribute` in page code is not one) outside `whenSettled`, `expect.poll` or `toPass` is an error. An `evaluate` whose answer is dropped is an action, not a read. The containment and internal-id checks, which run on whatever state a test leaves, are exempt.
- Alternatives:
  - A global paused `page.clock` in every test. It would also freeze the page's own settle and retry timers and the worker's, so every test would have to run the clock by hand; Playwright recommends the clock for timer-driven UI, which is where the suite already uses it.
  - `networkidle`. Playwright discourages it, it says nothing about a worker's derivation or a pending effect, and a live stream keeps the network busy.
  - Longer timeouts or retries. They hide the race and make a slow failure slower.
  - A settled signal outside the app (a test-only global). It would be a second owner of the same facts; the dot already reads them, and a person's "is it saved?" is the same question.
- What would change it: a read or work the session root cannot see (a fetch outside the keyed reads, a timer that changes data rather than display) would have to register as work, or the tests reading it would wait on what it shows. If Playwright gains a way to wait for an app-defined quiet state natively, `settled` becomes that call.
