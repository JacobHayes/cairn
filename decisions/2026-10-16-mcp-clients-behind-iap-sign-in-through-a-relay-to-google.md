# MCP clients behind IAP sign in through a relay to Google

- Question: behind Google Cloud IAP a local MCP client cannot connect. IAP answers every request before Cairn does, and IAP accepts only a Google-signed ID token whose audience is an OAuth client on its programmatic allowlist, while an MCP client sends whatever a token endpoint returns as `access_token`, and Google's own token endpoint returns an opaque access token there. From brief 9.1 (MCP sign-in behind IAP).
- Call: the `gcp_iap` provider, given a Google OAuth client (`client_id`, and the secret from the environment), relays the standard MCP OAuth handshake to Google and answers the token request with Google's ID token as the access token. Google stays the only issuer; IAP keeps deciding who reaches Cairn on every MCP call; Cairn mints and stores nothing for the flow.
  - Paths: the built-in server's (`/.well-known/oauth-protected-resource` and its suffixed form, `/.well-known/oauth-authorization-server`, `/api/oauth/register`, `/api/oauth/authorize`, `/api/oauth/token`) plus `/api/oauth/callback`, Google's redirect. The well-known paths can name only one server, so one provider owns them: configuration refuses `builtin_oauth` beside a relay, as it refused a second `builtin_oauth`. The shared pieces (metadata, registration, redirect checks, error answers) live in `oauth` and serve both.
  - Placement: discovery, registration, and token are reachable without IAP; authorize and callback stay behind it. Cairn does not check the assertion there itself: authorize only redirects to Google with a public client id, and callback only forwards a Google code to loopback, so a misrouted one leaks nothing; keeping them behind IAP keeps strangers from using the organization's Google client through Cairn.
  - PKCE passes through: the client's S256 challenge goes on Google's authorize URL, its verifier on the exchange, and Google enforces it. Cairn checks only that they are present.
  - The round trip rides in Google's `state` (base64url JSON of the client id, its redirect URI, its state, and a fresh random attempt), and a cookie holding its digest binds it to the browser that started it, on the callback path, for the browser step's lifetime. The callback refuses, with no redirect, a state the cookie does not match, a client id that does not decode, or a redirect it did not register; registration takes only http loopback redirects. The destination always comes from the state Google returns, never the cookie. A cookie tossed from a sibling subdomain grants nothing a link to authorize does not (authorize is a GET any page can start); against the person's own attempt it can only make its callback be refused. Loopback-only redirects and the starter's PKCE challenge bound both.
  - The bearer: with a relay, a bearer shaped as an ID token is claimed by `gcp_iap` and counts only beside a valid assertion; without one it is refused and never falls through to another provider. The identity is the assertion's; the bearer is never read for identity, since IAP already verified it. The layer's precedence is unchanged: the session, then the first provider in configured order with a credential, names the actor, and any refusal refuses. An MCP client sends no session cookie, and a provider that names someone regardless is local only, so this grants nothing new.
  - No challenge: IAP's 401 carries no `WWW-Authenticate`, and clients go to the well-known paths without one (Claude Code does), so `gcp_iap` adds none.
  - One deadline per relay request: auth's routes sit outside the API's request duration, and the outbound client's timeout starts only at the Google call, so a body that trickles in would hold its slot forever. The relay's router answers 503 `temporarily_unavailable` once a request, its body read included, passes the outbound identity call limit (10 s; same value, its row now names this use).
- Alternatives:
  - The built-in server on paths without IAP: Cairn would mint long-lived tokens, and MCP calls would lose IAP.
  - A stateful broker holding people's Google refresh tokens: Cairn would store long-lived credentials.
  - A local helper sending `Proxy-Authorization`: a program on every machine. Dropping IAP: group membership would move into Cairn.
  - Separate `/api/oauth/iap/*` paths: two path sets to document and route, and the well-known paths collide anyway.
  - Public authorize and callback: more public surface for no gain.
  - Cairn's own PKCE toward Google: Cairn would have to remember or carry the client's challenge, for no added protection.
  - An HMAC'd state (needs a key), server-side pending state (stores something), or a `__Host-` cookie (needs https and path `/`, so plain-http deployments and the tests could not sign in).
  - Verifying the bearer against Google's keys and matching subjects: a second key set to fetch, protecting nothing IAP does not.
  - The API's 5 s request duration for the relay (shorter than one Google call may take), or a new limit (a second number for the same judgement).
- Limits: one sign-in in flight per browser (a newer authorize replaces the cookie, so an older attempt's callback is refused). The built-in server's routes still read a body without this deadline; they make no outbound call.
- What would change it: Google issuing ID tokens to public clients, or IAP accepting another token; a need for cloud connectors (which would need Cairn to hold refresh credentials); a slow-body bound wanted on the built-in server's routes too.
