# The multiplayer testbed runs a multi-thread runtime with four workers

- Question: with Patina's tokio multi-thread fix in the pinned revision, which runtime does the multiplayer testbed serve on (patina-bump)?
- Call: `new_multi_thread().worker_threads(4)`, the constant `WORKER_THREADS` in `testbeds/multiplayer/src/main.rs`. The binary serves on tokio's multi-thread runtime with one worker per CPU (`crates/cairn/src/main.rs`), but Patina presents one CPU (`getaffinity`), so the default starts a single worker: the probe's default build spawned only main plus one worker. Four workers let requests run on several threads and PCT reorder them, reaching interleavings of the store's pool, the notifier and SSE that one thread never makes. The count is a property of the testbed's world (a four-core host), not configuration. No current-thread leg is kept: it is not what ships, and the spike's removal record already said a multi-thread check would be the multiplayer testbed itself. Probe evidence at the pin: 20 of 20 fault-free seeds, 8 of 8 faulted seeds (views caught up within 239 ms of the 450 ms budget), a 16-generation buggify plus PCT campaign with every in-reach oracle fired, a byte-identical repeat and a clean replay; the trace is 4.3 MB against 3.3 MB for one worker.
- Alternatives: keep one current-thread runtime and the ticker (what the pin made unnecessary; never reaches multi-thread interleavings); tokio's default worker count (one worker under Patina, so a multi-thread runtime in name only); a leg per runtime (a second configuration nothing ships).
- What would change it: Patina presenting the host's CPU count (then tokio's default can replace the constant), or a multi-thread run that stops being reproducible.
