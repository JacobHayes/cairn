# An acknowledged commit is lost after a failed log fsync (product bug, fixed by the log sync fix above)

- Question: the durability testbed found a run where an acknowledged commit is missing after a crash-restart. Is it the store, the service, or the testbed's model?
- Call: a store bug, recorded and not fixed here (the fix is not small and local). The interleaving, minimized to `cargo patina run <bed> --seed 31 --fs-error-permille 5 --fs-crash-at write:40` (`testbeds/durability/sim.sh` leg 6 pins it): (1) step 2's commit appends its frame to Turso's logical log and the log's `fsync` fails; (2) Turso's `COMMIT` returns the error, and `crates/store-turso/src/commit.rs:139-152` rolls back and answers `CommitError::Failed`, which the service passes on as `WriteError::Failed`; (3) Turso has nonetheless left the transaction visible: the `ROLLBACK` undoes nothing, so the receipt, the revision, and the events read back (Turso 0.8.2, `mvcc/database/mod.rs:3537`, the `SyncLogicalLog` step returns the sync error after the frame was appended and the versions published); (4) the client resubmits the same patch id (H5), and `crates/service/src/write.rs:139` / `:199-203` answers it `AlreadyApplied` from that receipt, so the client records the commit as acknowledged; (5) the process crashes before the next successful log sync, the unsynced frame is lost, and on restart the acknowledged commit has no receipt, no events, and the journey is a revision behind. The model is faithful: patina makes durable only what a successful `fsync` covered, as Linux does (and Linux may drop the dirty pages after a failed `fsync`, so a later successful one need not save it). The deterministic test is `crates/store-turso/tests/conformance/log_sync.rs` (`a_commit_whose_log_sync_fails_leaves_nothing_visible`, ignored with this entry as its note): it wraps the platform I/O through a new test seam, `TursoStore::open_with_io` behind the `io-seam` feature, fails one log `fsync`, and shows the receipt of the failed commit at revision 2. Fix direction: a `COMMIT` that fails other than by a conflict leaves the commit's fate unknown, so the store must not answer from what Turso holds in memory until it knows. Either make it durable or fail closed: after such a failure, commit a no-op barrier (a revision-row rewrite) whose own successful log sync covers the earlier frame, and only then let reads and receipts through; if the barrier fails, mark the store failed so every call errs until the process restarts and recovery reads the log from disk. Turso fixing `SyncLogicalLog` to roll the transaction back on a sync error would also close it, upstream.
- Alternatives: count it as a testbed modeling error (it is not: the client did only what H5 allows); have the service stop answering resubmissions from receipts after a failed commit (it would turn every retry after a transient error into a conflict, and the receipt would still be served to readers).
- What would change it: the fix lands; then un-ignore the test and leg 6 of `sim.sh` fails until its pinned reproduction and this entry are updated. Done: the log sync fix (above) took the barrier direction, the tests run, and leg 6 pins a regression run (seed 12, since the fix moved seed 31's faults).
