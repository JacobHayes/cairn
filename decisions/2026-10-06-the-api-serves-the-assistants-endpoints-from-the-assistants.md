# The API serves the assistant's endpoints from the assistant's service, outside the request duration

- Question: ARCHITECTURE has an optional subsystem contribute a router and a service and mount itself in the API; MCP contributes its own router. The assistant's two endpoints answer the API's problems, live in its OpenAPI document and TypeScript client, and a turn waits on a model for up to two minutes a call, past the API's 5 s request duration.
- Call: `crates/assistant` contributes the `Assistant` service, and the API serves its endpoints (`handlers/assistant.rs`, in the endpoint table and the OpenAPI document) through `cairn_api::router_with_assistant(service, auth, Option<Assistant>)`; `router` is that with `None`. The router asserts the capabilities' `assistant` flag matches what is mounted. The endpoints sit behind the auth layer and the body and in-flight limits but outside the duration layer; a turn is held to its own limits (120 s a provider call, 10 min a turn, 32 iterations, 32 turns in flight, answered 503 past it) and runs on its own task, so a client that goes away never cuts a write off. A turn ends with a status (`replied`, `provider_timed_out`, `provider_failed`, `iteration_limit`, `turn_timed_out`) and reports every write made before it. The assistant acts as `ag_assistant` (the bake-off fixture's agent id) for a signed-in user; a request carrying an agent token is refused 403, since an agent has the tools over MCP and an actor holds one agent.
- Alternatives: an axum router in the assistant crate (it would repeat the API's error bodies and stay out of the OpenAPI document); changing `router`'s signature (every API test and testbed would change for an optional part); a 504 for a provider timeout (the writes before it would be lost to the caller).
- What would change it: streaming replies (out of scope here), which would make a turn a stream rather than one JSON answer.
