# The write wrapper decides on the patch a tool would submit, the ten-node limit holds across a turn, and what "touched" reaches

- Question: I5 and ARCHITECTURE say structural changes become proposals, state changes apply directly unless one change would touch more than ten nodes, and the decision is by mutation kind and destination. The wrapper sits in front of 20 write tools with different argument shapes; it has to know what each would write before anything is written, what "touch" counts, and what to do with the writes that are neither a state change nor a proposal (applying a proposal, importing a route file, creating a journey or a route). Review round 1 of the assistant then found the limit held per tool call: a model splits "mark these fifteen done" into fifteen single-node calls (or is talked into it by text in the journey), and each applied; removing notes counted no nodes; skipping a container counted one node, though D1a skips its whole subtree.
- Call:
  - The MCP tool set gains one public method, `ToolSet::drafted_patch(name, arguments)`, which works out the domain patch a direct-write tool would submit, exactly as `call` would, without writing; `call` now goes through it. The wrapper classifies that patch with the schema's own `Patch::change_class` (a route patch is always structural; a journey weight override is state). Structural becomes one `create_proposal` of the same mutations against the same destination and base revision (a journey or route that does not exist yet is created by the proposal, A12), under an id derived from the patch id, so a write asked again answers the same proposal (H5, I6); the note becomes its title and description. The proposal tools pass through. `apply_proposal` (the user's click, I7) and `import_route` (whose patch the service builds from the file, so the wrapper cannot see it) are refused, and so is any write tool the wrapper cannot see a patch for, so a tool added later fails safe; the policy tests iterate every write tool the set lists and fail on one with no case.
  - The ten-node limit is per turn. The turn keeps a ledger of the nodes its direct writes touched (by domain and node). A write that would carry the turn past ten is drafted instead, into one overflow proposal per destination, against the destination's current revision. Every later overflowing write in the turn is added to that same proposal by `edit_proposal`, so the overflow is seen whole and reported once, with the count the turn's writes would have touched. A single patch over ten is still its own proposal.
  - Touched nodes start from `Patch::touched` (H5's touched set: each distinct node any record the patch writes hangs off; a whole-domain or whole-graph touch counts as unbounded) and are resolved against the stored journey. A removed note or link counts the node it is on; moving a note or link counts the node it leaves as well as the one it lands on. Skipping or reopening a node counts its subtree.
  - Derived effects (owners a role fill moves, nodes that turn stale) are consequences, reported, not counted. A role fill or role clear counts no node, by explicit reading: who holds a role is one answer, as a decision that fills the role is. This reading is the owner's to confirm.
  - Replies are capped at `TOOL_LOOP_ITERATION_COUNT_MAX` (32) tool calls each, a borrowed limit; calls past it are refused to the model. The turn deadline is checked before every tool call.
  - A conversation runs one turn at a time; a second submission is answered 503 (busy).
  - The replayed dialogue is held to the newest 256 KiB (4 x `body_bytes_max`), and a provider answer to `request_bytes_max`. Both are borrowed or derived limits, pending sign-off as named limits.
  - A route that does not exist keeps no conversation until a turn drafts something. Discarding a proposal is reported as a discard.
- Alternatives:
  - The wrapper parsing every write tool's arguments itself (a second copy of 14 parsers that drifts from the tool set); deciding by tool name alone (`apply_patch` and `resolve_date_conflict` carry either kind); converting an import into a proposal (the service mints its keys from the patch id while importing, so the wrapper would have to repeat the import).
  - Counting nodes from the applied result (too late: the write has landed); counting derived effects, or a role fill as every node whose owner it moves (unbounded, needs a derive per write, and contradicts how a filling answer counts).
  - The limit per call, as first built, or per reply only: a model can spread the calls over replies.
  - Refusing the overflow outright: the user would lose what they asked for, rather than review it.
  - A lock that queues the second turn: it would hold an in-flight slot for up to ten minutes.
- What would change it: the owner reading "touch" to include derived effects (then role fills and condition-driven relevance would be counted from a derive before and after); the owner naming different values for the borrowed limits; a request to let the assistant import a file the user attached (the import would then go through a proposal drafted by the service).
- History: the assistant brief (4.4) first applied the limit to each tool call's patch alone, counting only the nodes its records hang off; its first review made the limit hold across a turn and widened what "touched" reaches (first recorded as "the ten-node limit holds across a turn, and what touched reaches"), and the assistant panel brief (5.8) added the count for a moved note or link.
