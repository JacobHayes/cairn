# The write wrapper decides on the patch a tool would submit, and "touched" counts the nodes it writes

- Question: I5 and ARCHITECTURE say structural changes become proposals, state changes apply directly unless one change would touch more than ten nodes, and the decision is by mutation kind and destination. The wrapper sits in front of 20 write tools with different argument shapes; it has to know what each would write before anything is written, what "touch" counts, and what to do with the writes that are neither a state change nor a proposal (applying a proposal, importing a route file, creating a journey or a route).
- Call: the MCP tool set gains one public method, `ToolSet::drafted_patch(name, arguments)`, which works out the domain patch a direct-write tool would submit, exactly as `call` would, without writing; `call` now goes through it. The wrapper classifies that patch with the schema's own `Patch::change_class` (a route patch is always structural; a journey weight override is state) and counts touched nodes from `Patch::touched` (H5's touched set): each distinct node any record it writes hangs off; a whole-domain or whole-graph touch counts as unbounded. Structural, or over ten, becomes one `create_proposal` of the same mutations against the same destination and base revision (a journey or route that does not exist yet is created by the proposal, A12), under an id derived from the patch id, so a write asked again answers the same proposal (H5, I6); the note becomes its title and description. The proposal tools pass through. `apply_proposal` (the user's click, I7) and `import_route` (whose patch the service builds from the file, so the wrapper cannot see it) are refused, and so is any write tool the wrapper cannot see a patch for, so a tool added later fails safe; the policy tests iterate every write tool the set lists and fail on one with no case. Derived effects (owners a role fill moves, nodes that turn stale) are consequences, reported, not counted.
- Alternatives: the wrapper parsing every write tool's arguments itself (a second copy of 14 parsers that drifts from the tool set); deciding by tool name alone (`apply_patch` and `resolve_date_conflict` carry either kind); counting nodes from the applied result (too late: the write has landed); counting derived effects (unbounded and only known after applying); converting an import into a proposal (the service mints its keys from the patch id while importing, so the wrapper would have to repeat the import).
- What would change it: a reading of "touch" that counts derived effects, or a request to let the assistant import a file the user attached (the import would then go through a proposal drafted by the service).
