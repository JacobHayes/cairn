# The library crates' integration tests are one test binary

Question (from the inner loop's cost of fresh executables): endpoint-security agents scan every new executable on its first run, and an engine edit relinked 14 test binaries, 27 with the unit-test and bin ones. The scan scales with bytes more than count (first run of 27 binaries, 915 MB: 69 to 104 s against 8 to 10 s warm). Each crate's `tests/integration` was its own binary, linking its own copy of Turso, tokio, axum, and the rest. Can they be one?

Call: yes for nine of the eleven. `crates/tests` (package `cairn-tests`) holds one integration binary with a module per crate (api, assistant, auth, engine, mcp, service, store, store_turso, wasm), each the crate's old `tests/integration` moved as it was: its `main.rs` became the module's `mod.rs`, and its `crate::` paths became `crate::<crate>::` (the only edits in the test files). `scripts/ladder-tests` counts a test of that binary for the crate named by its first path segment, so every rung's suites and counts are unchanged (683 tests in rung 2, 56 in rung 3); the property and cost suites are labelled `<crate> <file>` where they were labelled by file path. The binary holds 480 of the 683 tests, so it runs with half the cores. Measured after an engine edit that adds a pub fn, on a loaded machine (load 7 to 11), with the unit-test binaries left alone: 27 binaries and 915 MB become 19 and 654 MB (the merged one is 265 MB where its nine were 525); cargo test --no-run 19 to 27 s becomes 16 to 23 s; the first run of the fresh binaries 69 to 104 s becomes 53 to 66 s; `check:fast` 239 to 292 s becomes 152 to 199 s (rung 2 128 to 208 s becomes 64 to 108 s, rung 3 7 to 8 s becomes 3 s). Noise is large, but every pair points the same way.

The two crates whose tests run a binary of their own, `cairn` (`CARGO_BIN_EXE_cairn`) and `cairn-schema` (`CARGO_BIN_EXE_cairn-document`), stay as they were: Cargo names a binary only to the tests of its package, and moving those tests would mean finding the binary by path. Costs: the linker warns that the binary's `__eh_frame` is over 16 MB (only the speed of unwinding), a change to any crate relinks and recompiles the one binary (an edit to one crate's tests recompiles all nine crates' tests, where it rebuilt one), the tests are built at the default opt-level rather than the computing crates' 2 (they call optimized code; the measured rungs were not slower), the clippy lints rung 1 raises for some crates (`cairn-engine`'s indexing and `missing_docs`, the panic lints of api, mcp, assistant) no longer apply to their integration tests, and the dev-dependencies the nine crates declared for those tests are still declared (their unit tests and examples use some).

Alternatives: `test = false` on the unit-test targets that hold no test (a test added there later would silently never run), one crate per directory kept and only the heaviest merged (a second rule to remember), and `#[path]` modules from an unmoved tree (two places for a test file).

What would change it: a test of one crate that needs another opt-level, a merged binary whose link time passes the time the nine took in parallel, or a crate whose integration tests need a feature the others must not have (features are workspace-wide under `--all-features`, so none does today).
