# The health check asks no credential and reads the store's state

- Question: a proxy in front of Cairn checks its health with an anonymous request, and every endpoint sits behind the auth layer. What does a health check answer, to whom, and what does it read?
- Call: `GET /healthz` is served outside the auth layer, the one endpoint that is, but inside the `Host` allowlist, the request limits, and request observation. It answers 200 with `{"status": "ok"}` while the store answers, and 503 with `{"status": "store_failed_closed"}` once the store has failed closed (decisions/2026-10-07-the-log-sync-fix-nothing-is-answered-from-a-write-until.md), which only a restart clears. The store trait gains a synchronous `health`: the Turso store reports its durability state, and the memory store, which cannot fail, reports a failed-closed fault a test arms. It touches no storage, so a probe costs nothing and cannot queue behind the connection pool. The `Host` allowlist still applies: a proxy forwards the public name (the hayworks edge does), and the endpoint says nothing a rebinding page could use, so neither need nor harm argues for exempting it. The OpenAPI operation declares no security.
- Alternatives: a trivial read through the pool (it would also catch a database the process can no longer reach, but it waits on the pool when the server is busy, so a loaded server looks down); keeping it behind auth and letting the probe use an agent token (a credential in the proxy's health configuration for a check that reveals nothing); exempting it from the `Host` allowlist (only needed by a probe that sends another name, which no current deployment has).
- What would change it: a store failure the durability state does not record, which would argue for a read through the pool; a probe that cannot send the public name.
