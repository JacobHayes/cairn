# Applying a proposal needs the reviewer's confirmation at the revision it is at, so a refresh asks for it again

- Question: I6 says a stale proposal is refreshed against the new base and "require[s] renewed review". The server checks only that the apply names the proposal's current editing revision, which a page holding the refreshed proposal would always send, so nothing on the server tells a reviewed proposal from one nobody looked at after the refresh redrafted it.
- Call: the review screen keeps the revision the reviewer confirmed reviewing ("I have reviewed this proposal as it stands", per tab across reloads), and applies with that revision as `reviewed_revision`. A refresh, a save, or anyone's edit moves the revision and leaves the confirmation behind, so apply is offered again only once the reviewer confirms the proposal as it now stands. Apply is also held while the destination is stale, while an item needs a choice or the candidate breaks a rule, and while the reviewer's own edits are unsaved; the screen lists whichever hold it.
- Alternatives: treat opening the refreshed preview as the renewed review (nothing a person does marks it, so a refresh followed by a click on apply would satisfy it); a server-side review record (a new stored field and mutation, outside this brief).
- What would change it: a stored review on the proposal (who reviewed which revision), which would move the confirmation to the host and let another person's review count.
