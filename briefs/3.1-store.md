# 3.1: Store trait, memory and Turso backends, conformance suite

| | |
|---|---|
| Id | 3.1 |
| Crates or packages | `crates/store`, `crates/store-turso` |
| Depends on | 1.2 (runs beside phase 2) |

## Goal

The store the service talks to, proven by a conformance suite every backend passes: `load` by typed target (journey, route with its draft, published version, deployment), atomic commit of a change set and its events under revision checks, proposal records with their own revision, index and history queries, and the out-of-domain records (conversations and auth state). The memory backend is the reference; Turso is the default.

## Governing

- PRD: A14, A17 (one transaction), A19, E6 (aliases; same-transaction entity create bumping the deployment revision), H5, J1, J2, J5, C16, C17; Non-functional: Structured storage.
- ARCHITECTURE: Storage (all of it: Store trait, Backends, Schema outline, Concurrency and notification); Engine > Model (Proposal).
- PRACTICES: Testing > Shell (conformance suite); Explicit limits (domain size, store connections, store connection acquire).

## Scope

In: the `Store` trait as ARCHITECTURE describes it, including the current-revisions query a new subscriber starts from, the journeys referencing an entity, cross-journey text search, and the auth records as ARCHITECTURE's schema outline lists them (users, identities, sessions, transient OAuth state, agent token hashes, the auth log) with plain record operations, which 3.2's providers build on; change-set mapping per backend (the change set is 1.2's schema type; the store has no engine dependency, and the conformance suite builds change sets directly because it tests persistence, not validation); patch id resubmission and the deleted-ids record; the per-graph size cap at commit; the memory backend; the Turso backend with embedded numbered migrations, STRICT tables, CHECK constraints, foreign keys, and MVCC commits (any feature Turso lacks enforced by the backend inside the commit transaction, tested by the suite, and recorded in `DECISIONS.md`); the conformance suite as a function over a store factory.

Out: the notifier (4.1); any engine call.

## Acceptance

- Conformance cases: a revision conflict is rejected and leaves state untouched; a failure between state rows and events leaves nothing; a commit with two preconditions fails whole when either is stale; a first commit from base 0 creates the domain and a second conflicts; an oversize commit names the limit; alias resolution; every index and event filter; paging; hard delete removes events and leaves the deployment event; a proposal's revision is independent of its destination's; text search hits notes and resources; an entity create in a journey patch bumps the deployment revision, and one whose key is already an entity or alias is rejected; a resubmitted patch id with the same content returns the original revision and with different content is rejected; a create at a hard-deleted journey's id is rejected; a route with many published versions still loads its draft under the cap; auth records round-trip.
- A14: a reviewer finds every glossary concept as a table or column.
- Planted bug: in the memory backend, append events outside the commit's all-or-nothing step and show the conflict case leave orphaned events.
- Concurrency: a long commit to one journey does not block reads or a commit to another journey; two commits to one journey yield one success and one revision conflict.
- Adds rung 4.
