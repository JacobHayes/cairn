# 3.1: Store trait, memory and Turso backends, conformance suite

| | |
|---|---|
| Id | 3.1 |
| Crates or packages | `crates/store`, `crates/store-turso` |
| Depends on | 1.2 (runs beside phase 2) |

## Goal

The store the service talks to, proven by a conformance suite every backend passes: `load` by typed target (journey, route with its draft, published version, deployment), atomic commit of a change set and its events under revision checks, proposal records with their own revision, index and history queries, and the out-of-domain records (conversations and auth state). The memory backend is the reference; Turso is the default.

## Governing

- PRD: A14, A17 (one transaction), A19, E6 (aliases; same-transaction entity create bumping the deployment revision), H5, J1, J2, J5, C16, C17; Non-functional: Structured storage.
- ARCHITECTURE: Storage (all of it: Store trait, Backends, Schema outline, Concurrency and notification); Engine > Model (Proposal).
- PRACTICES: Testing > Shell (conformance suite); Explicit limits (domain size, store connections, store connection acquire).

## Scope

In: the `Store` trait as ARCHITECTURE describes it, including the current-revisions query a new subscriber starts from, the journeys referencing an entity, cross-journey text search, and the auth records as ARCHITECTURE's schema outline lists them (users, identities, sessions, transient OAuth state, agent token hashes, the auth log) with plain record operations, which 3.2's providers build on; change-set mapping per backend (the change set is 1.2's schema type; the store has no engine dependency, and the conformance suite builds change sets directly because it tests persistence, not validation); patch id resubmission and the deleted-ids record; the per-graph size cap at commit; the memory backend; the Turso backend with embedded numbered migrations, STRICT tables, CHECK constraints, foreign keys, and MVCC commits (any feature Turso lacks enforced by the backend inside the commit transaction, tested by the suite, and recorded in `decisions/`); the conformance suite as a function over a store factory.

Out: the notifier (4.1); any engine call.

## Acceptance

- Conformance cases: a revision conflict is rejected and leaves state untouched; a failure between state rows and events leaves nothing; a commit with two preconditions fails whole when either is stale; a first commit from base 0 creates the domain and a second conflicts; an oversize commit names the limit; alias resolution; every index and event filter; paging; hard delete removes events and leaves the deployment event; a proposal's revision is independent of its destination's; text search hits notes and resources; an entity create in a journey patch bumps the deployment revision, and one whose key is already an entity or alias is rejected; a resubmitted patch id with the same content returns the original revision and with different content is rejected; a create at a hard-deleted journey's id is rejected; a route with many published versions still loads its draft under the cap; auth records round-trip.
- A14: a reviewer finds every glossary concept as a table or column.
- Planted bug: in the memory backend, append events outside the commit's all-or-nothing step and show the conflict case leave orphaned events.
- Concurrency: a long commit to one journey does not block reads or a commit to another journey; two commits to one journey yield one success and one revision conflict.
- Adds rung 4.

## Decisions left to the implementer

- Column layout within the schema outline; pool sizing within the limits.

## Decision log

Appended by the implementer.

- Crates: `cairn-store` (the `Store` trait with its `AuthStore` and `ConversationStore` supertraits, the commit rules every backend shares in `backend`, the memory backend, and, behind the `conformance` feature, the suite and the change-set builders in `build`) and `cairn-store-turso`. Neither depends on the engine or names a runtime in `cairn-store`; only `cairn-store-turso` uses tokio (the pool's semaphore and acquire timeout) and `turso` (`=0.8.2`, default features off: no mimalloc, no full-text search).
- The memory backend stages a commit on a copy of the domains and swaps it in with the events and the receipt in one critical section; nothing it does awaits, so it runs on any executor. Its write semantics are the reference ([`decisions/2026-10-06-what-a-change-sets-writes-mean-to-the-store.md`](../decisions/2026-10-06-what-a-change-sets-writes-mean-to-the-store.md)).
- Commit order, both backends: lock (Turso writes the domain's revision row first), receipt, revisions and preconditions (every one that moved is listed, with the touched set of the events of every commit that moved it), deleted journey id and taken entity keys, the writes, the checks on what they produced (graph cap, sibling ids, entity keys, alias targets, emails, each graph held by a journey, draft, or version), revisions, events, receipt. A commit's violations are listed together, each once.
- `Commit` names the `PatchTarget`, the base revision, and `Precondition`s: a revision of any domain or proposal, or an entity merge's referencing journeys (a journey that newly references the entities is reported as a conflict from revision 0). The receipt's revision must be the base plus one; the store checks the change set's shape (its writes stay in its domain except riding entity creates and the deleted-journey record) before reading anything.
- The conformance suite is one async function per case over a `Backend` that opens fresh stores; `conformance_suite!` expands it to one test per case inside `mod conformance`, which rung 2 skips by name and rung 4 runs, one suite per backend. The memory suite runs on a tiny std-only `block_on`; Turso's on a current-thread tokio runtime. Turso's databases live under cargo's `CARGO_TARGET_TMPDIR`, one directory per test, removed afterwards. Test code (the suite and `build`) may unwrap.
- Turso: graph rows are keyed by text ids (`journey/<id>`, `draft/<route>`, `version/<route>/<n>`); a node's columns are its written fields (one layout table; a written field without a column is an error, tested); structured values are JSON columns; timestamps are integer nanoseconds and dates ISO text; values load back through their serde form, so a row that no longer parses is an error rather than a wrong value. Reads run in a `BEGIN` transaction so a load sees one commit; record operations outside the domains run in `BEGIN CONCURRENT`. `PRAGMA journal_mode = mvcc` is set at every open (it persists), `PRAGMA foreign_keys = ON` on every pooled connection (tested). Turso rejects a bound parameter a statement does not use.
- A Turso commit copies a graph by loading it and putting each record, the same path a put takes, so a copy means what it means in memory.
- Queries: "mine" (C16) narrows to journeys referring to the given entities (through aliases); the service derives the rest. Referencing counts answers, role fills, explicit participations, and condition values shaped like an entity key. Events by node are those whose subject or writes are on the node (an edge counts for both ends); by user is the actor. Text search matches a substring with ASCII letters compared case-insensitively (SQL `LIKE` with its wildcards escaped; the memory backend does the same), over journey names and descriptions, node titles and descriptions, notes and links (title and content), and resources (title and content); results page by journey.
- Records outside the domains are 3.1's plain row types in `cairn-store` (readiness ruling): users, identities (provider, subject, verified emails), sessions and OAuth state by digest with an expiry (expired ones are not returned; `take` removes), agent tokens by agent id and found by digest, the auth log, and conversations stored whole. `ConversationId` (`cv_`) joins the schema's ids, the one schema change.
- Fault injection: `Faults` holds one-shot failures and a pause hook at named commit points, inert unless armed; the suite fails a commit between its state rows and its events, and Turso's own cases pause one to race another against it or abort the process inside it.
- The Turso backend change is larger than a change should be (about 2,900 lines beside its migration): the `Store` trait is one unit, and a backend implementing part of it would be dead code or stubs.
- Planted bug: appending the memory backend's events before the revision check fails `conformance::a_revision_conflict_is_rejected_and_leaves_state_untouched` (`panicked at crates/store/src/conformance/commits.rs:151:5`, `test result: FAILED. 0 passed; 1 failed`); restored, it passes.
- Review round 1 (`gpt-6.1-sol`), fixed in one change on top: a Turso commit writes the revision rows of the domains it depends on (preconditions, a proposal's destination, the deployment when it writes an entity reference), log rows are numbered by a per-process sequencer and read below the lowest position in flight ([`decisions/2026-10-06-a-turso-commit-writes-the-revision-row-of-every-domain.md`](../decisions/2026-10-06-a-turso-commit-writes-the-revision-row-of-every-domain.md)), a proposal to a deleted journey's id is rejected, and an alias query resolves to its entity before gathering the entity's other aliases (a journey holding a sibling alias was missed). Three new Turso cases reproduce the races and fail with the fixes removed.
- Review round 2 (`gpt-6.1-sol`), fixed in a second change on top: a receipt keeps the revisions its commit left the proposals it wrote at (applying a proposal moves the proposal from its destination's patch) and what it wrote in the deployment (a riding entity create's event goes with its journey's hard delete), so a stale proposal edit or deployment patch is still told what intervened (a third migration adds the two receipt columns). The extended conformance cases fail with the fix removed.
- Review round 3 (`gpt-6.1-sol`), fixed in a third change on top: a Turso commit that loses both attempts looks its receipt up again before answering stale, so a resubmission is never mistaken for a stale patch (H5); a receipt records the proposals a hard delete takes with its journey (as removed), so a stale edit of one is told what intervened; a node's history includes a removal of a node it required, whose edge the removal took (the nodes are found in the graph before the commit and stored with the event); and violations of one code on one subject are kept when their messages differ (two emails held by two other entities are two violations), only a taken key found twice is listed once. Each fix's case fails with the fix removed. No fourth round (the loop's limit).
