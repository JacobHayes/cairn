# 5.5: Journey index and overview, route screens, entities, identity

| | |
|---|---|

## Goal

The screens around a journey: the journey index with its filters and the cross-journey "mine" list; the journey overview with status, lineage, journey-level notes and links, and complete and archive; journey creation from a route version or empty, landing in 5.3's walkthrough; route list and route detail with versions, their journeys, and upgrade availability, plus draft open, publish, discard, retire, import, and export; entity management, including entity emails and the offer to merge duplicates; the user's identity screen.

## Governing

- PRD: C16, C17, B1, B3, B11, A11, A13, A19, E6, H3, G1 (journey-level); Success criteria.
- ARCHITECTURE: Web UI (Screens); Auth (users and identities); Terms (Capabilities document).
- PRACTICES: Code conventions (TypeScript).

## Scope

In: the screens above and the application's navigation; "upgrade available" rendered from 3.1's index filter, never computed in the UI.

Out: the canvas and acting surfaces; the upgrade, save-as-route, and re-link flows (5.7 adds their entry points here).

## Acceptance

- Behavior by id: C16, C17 (a route with three versions, journeys on each, and a retired route still offering upgrades), B1, B11, A11, A13, A19 (hard delete needs a typed confirmation), B3, E6, H3, G1.
- Playwright: create a journey from the fixture route and land in the walkthrough; complete and archive; import the fixture file and export it identically; merge two entities with history intact; link an identity against the server host with 3.2's stub issuer.
- H6 in Playwright on the server host: a new journey appears in another page's index; an entity merge changes an owner shown on another page.
- Earlier work changed: 5.1's notes and links list takes a node or none (the journey's own, with no artifact type); 5.1's answer editor names a new entity for an entity answer, made in the same patch (B3); 4.6's index store is replaced by the live reads; the journey screens' row gains the overview.
- Review fixes: the journey index also refetches on route ticks (a published version changes "upgrade available" with no journey tick) and deployment ticks (a merge changes which journeys refer to the caller), and a tick that asked is held at its revision once fetched, so the same revision never asks twice. An entity edit is drafted against the deployment revision seen when it opened, and entity and new-entity names are drafts that survive a reload. A new journey whose chosen route is no longer offered asks for a new choice instead of starting empty. An import is not sent once the tab latched version skew. "Mine" says when nothing is yours, and the index shows a failed read of the caller.
- Planted bug: hide "upgrade available" on retired routes and show the C17 retired-route case fail. Separately, a client contract test asserts the screen reads the server's field.

## Decisions left to the implementer

- Navigation structure; the overview's layout.

## Decision log

Appended by the implementer.

- Navigation: a header row (Journeys, Mine, Routes, Entities, You) for the screens across journeys; a journey's own screens keep the row of journey screens, with the overview first. An index row's name opens the journey's canvas, as before; its "Overview" link and the journey screens' row reach the overview.
- Addresses: the index at `/` with its filters in the query (status, route, version, `mine`, `upgrade`), the cross-journey list at `/mine`, the new-journey form at `/new` (a route and version in the query preselect them), the overview at `/journeys/<id>/overview`, the route index at `/routes`, route detail at `/routes/<id>/versions` (the route canvas keeps `/routes/<id>`, and links to it), entities at `/entities` (`?merge=<a>,<b>` preselects a merge), the caller at `/me`.
- The index opens on active journeys; a status select offers completed, archived, or any. B11 has completed journeys leave the lists of work, and archived ones are out of the way until asked for.
- Overview layout: the journey's facts (status, lineage with the host's upgrade mark, the day it started, description, and the name and description editor), its status and what it accepts next, and its own notes and links (the node detail's list with no node and no artifact type). Hard deletion is offered once the journey is archived, behind its name typed back.
- Live reads: the index, the route index, route detail (the route, its versions' journeys, and the journeys' summaries filtered by the route, which carry "upgrade available"), and the caller each refetch on a tick newer than they hold (`data/live.ts`); the 4.6 index store is replaced. The caller is refetched whenever a newer deployment is held, since entity emails decide who they are.
- New ids: a journey's and an entity's are made from the name as a slug and eight random hex digits, within the 64-byte id limit.
- The in-browser host's local identity is verified for every fixture's lead, so the identity screen offers to merge those entities (H3 working as written); the browser tests leave them unmerged.
- A route file is exported as the canonical YAML kept on disk (`<route>-v<n>.yaml` or `<route>-draft.yaml`). The browser test imports the hiring loop's fixture file as a new draft and checks its export is byte for byte version 1's: the fixture files are not in the export's sorted node order, so the file itself is not what an export writes.
- The fixture server takes the app's origin as a second argument, the base its OIDC provider sends the browser back to through Vite's proxy.
- Planted bug: "upgrade available" hidden on a retired route in `routes/model.ts`'s `versionRows`; C17's retired-route unit test failed: `FAIL src/routes/model.test.ts > route detail (C17) > still offers upgrades to the journeys of a retired route (A19) AssertionError: expected [ …(3) ] to deeply equal [ …(3) ]`. The contract test (`journeys/JourneyIndex.test.tsx`) shows an index row reading the host's field where the versions say otherwise.
