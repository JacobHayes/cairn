# 5.8: Assistant panel

| | |
|---|---|
| Id | 5.8 |
| Crates or packages | `web/app` |
| Depends on | 5.7, 4.4 |

## Goal

The conversational panel on a journey or route draft: messages to 4.4's endpoints, replies rendered, created proposals opened in 5.7's editor, direct changes reported with links to the affected nodes and the panel absent when capabilities say there is no assistant.

## Governing

- PRD: I5, I7; Success criteria (route draft and ad-hoc structuring).
- ARCHITECTURE: Assistant; Terms (Capabilities document).
- PRACTICES: Code conventions (TypeScript).

## Scope

In: `AssistantPanel` mounted on the canvas, overview, and draft screens; a conversation per target per user; "review proposal" per created proposal.

Out: streaming; provider configuration UI (the provider is deployment configuration).

## Acceptance

- Behavior by id: I5 (proposal path and direct path both visible), I7, capability gating (the in-browser host never shows the panel).
- Playwright on the server host against 4.4's scripted provider: ask for a breakdown, get a proposal, open it, apply.
- Planted bug: show the panel without the capability and show the gating test fail.

## Decisions left to the implementer

- Panel placement and message rendering.

## Decision log

Appended by the implementer.

- Placement: an Assistant toggle in the header of the journey canvas, the overview, and the route canvas opens a panel docked at the window's right edge below the shell header. On a wide window the screen makes room for it; on a narrow one it lies over the screen. The notices move left of it. Open or closed is kept per tab across screens; the message being typed is a draft that survives a reload.
- The route canvas mounts the panel whichever graph it shows, since a turn about a route is about its draft, which the assistant can open.
- Rendering: the user's words as a bubble; replies as Markdown; a direct change as a card with its tool, revision, the nodes it wrote (titles from the screen's graph, linked to the node's detail), and its consequences linked the same way; a proposal as a card with why it is one and "Review proposal" to proposal review; an ending without a reply as a callout. A busy conversation (503) says to try again and keeps the message.
- The fixture server the browser tests run against mounts the assistant over the scripted provider. A test sets the next answers with `PUT /fixture/assistant/script`, outside auth, on that test host only.
- `consequenceLines` in the notices now builds on `linesOf`, which the panel shares.
- Planted bug: the panel offered without the capability. `AssistantPanel.test.tsx > the assistant panel's gating (I5, capabilities) > is absent when the capabilities offer no assistant, whatever the host could reach` failed with `expected '<button type="button" class="button a…' not to contain 'data-testid="assistant-toggle"'`; restored, it passes.
- Review fixes: the panel is keyed by its target, so a message typed about one journey never shows on another. Each conversation is held for the tab per host and target (`assistant/conversation.ts`), not by the mounted panel: a turn in flight, its answer, and a turn the host answered but did not keep survive the panel closing; a read begun before an answer arrived is dropped rather than replacing it; and a turn the host did not keep is shown after the messages kept when it was answered, before later turns.
- Earlier work changed: the assistant's applied action names the nodes it wrote, the API gains the conversation reads, and the turn reports late writes and survives a failed save (`crates/assistant`, `crates/api`); the fixture server mounts the assistant; the host gains `assistant`; the acting frame takes header extras; the notices share `linesOf`.
- Calls that matter: `decisions/2026-10-08-the-panel-reads-its-conversation-back-from-the-host.md`, `decisions/2026-10-08-a-write-the-turns-deadline-overtakes-is-reported-when.md`.
