# 7.3: The `requires_note` guard

| | |
|---|---|
| Id | 7.3 |
| Crates or packages | `crates/schema`, `schema/`, `crates/engine`, `crates/store`, `crates/store-turso`, `openapi/`, `web/client`, `web/app` |
| Depends on | 5.6; its screens 8.7, 8.9 |

## Goal

Give work whose output is something written down, rather than a linked document, the same completion guard artifacts have. A deliverable or action marked `requires_note` cannot be marked done until it carries at least one journey note of its own; `has_note` is a guard like `has_artifact`, bypassable with a reason, and its loss after completion shows as `stale` with "missing note".

## Governing

- PRD: A1a (`requires_note` on deliverables and actions), A16, D4 (`has_note`, bypass, stale reason), G4, Invariants (kinds that take the flag), Core concepts (Guard, Stale, Required note).
- ARCHITECTURE: Schema outline (`nodes` flags), Generated artifacts.
- PRACTICES: Bounds and assertions; Code conventions.

## Scope

In: the node flag in the schema, the route file format and its JSON Schema, and the store; the guard, its bypass, and the stale reason in the engine; upgrade and save-as-route carry the flag like `requires_artifact`; the flag in the node form's Completion needs section beside `requires_artifact` (8.11, or today's form until it lands); the done action wherever it appears (a Next page row, a card, the inspector), which reads Done... while the guard would fail and opens a note field in the action row, sending note and completion as one patch, as is done for an artifact link; "Note required" as the row's one secondary fact and a flag on the card; "Stale: missing note" with Add note in the Next page's Needs a look fold. The model parts do not wait for the screens.

Out: requiring a note on decisions or milestones (a decision's rationale is 7.2's), and requiring a particular kind of note.

## Acceptance

- Behavior by id: A1a and Invariants (the flag on a decision, milestone, or group is rejected with its path), D4 (done refused without a note; a link or a child's note does not satisfy it; bypass records the failure), G4 (removing the last note after done sets `stale` with "missing note"; adding one clears it).
- Scenario over the product launch fixture, with one action marked `requires_note` in a route-file variant: completion is refused, then accepted with a note in the same patch, then goes stale when the note is removed.
- The route file round-trips with the flag; an upgrade that sets it on a completed node leaves the node done and stale (D4).
- Playwright: Done... on that action in a Next page row and in the inspector opens a note field and completes in one patch.
- Planted bug: count the journey's notes rather than the node's own, and show the guard test fail.

## Decisions left to the implementer

- Whether Done... carries over a note draft already being typed on the node.

## Decision log

- The flag is a field of both the deliverable and the action, off by default and written to a
  route file only when on. On the wire the guard is `has_note` and the stale reason
  `missing_note`; both are additive. In the store it is a nullable `nodes.requires_note`
  column (new migration): existing rows load with the flag off.
- Only a note (not a link, reference or conversation) on the node itself satisfies the guard;
  a child's note and the journey's notes do not. It is read once per pass beside the artifact
  index, so completing is a lookup.
- Upgrade, save-as-route and authoring carry the flag through the generic node-field paths,
  so no merge code changed; an upgrade that turns it on for finished work leaves the node done
  and stale.
- The done action, on a card or a next-list row, opens an inline note field (and the artifact
  address too when both are required) and sends the note and the completion as one patch. Node
  detail keeps its own Complete: the guard failure and its bypass show there, and the note is
  added in its Notes section. The authoring form puts the flag right after "Requires an
  artifact".
- The phone screen of the hiring-loop fixture requires a note, so the browser host has a real
  action to try it on (its scenario skips the screen, which is not guarded). The product launch
  scenario of the acceptance runs over a variant built in the test from the fixture's route
  file, so the fixture itself is unchanged.
