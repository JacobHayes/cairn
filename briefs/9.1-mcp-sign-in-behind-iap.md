# 9.1: MCP sign-in behind IAP

| | |
|---|---|
| Id | 9.1 |
| Crates or packages | `crates/auth`, `crates/cairn` (config), `docs/` |
| Depends on | 3.2, 4.3 |

## Goal

Let a person connect a local MCP client to a Cairn deployment behind Google Cloud IAP with one command and one browser sign-in: no helper program, no gcloud, no hand-copied token. Today a client cannot connect at all: IAP answers every request before Cairn does, and Cairn cannot issue a credential IAP accepts. After this, Google stays the only issuer, IAP keeps deciding on every MCP call who may reach Cairn (authentication, access, group membership), and Cairn only helps the client through the standard MCP OAuth handshake so that the bearer it ends up holding is a Google ID token IAP accepts. Cairn mints and stores no credential for this flow.

## Governing

- PRD: I2 (a hosted remote MCP server needing no local install), H1 (pluggable auth), H2 (an actor on every mutation), H3 (identity by verified email).
- ARCHITECTURE: Auth; MCP endpoint.
- PRACTICES: Explicit limits.
- Decisions: [`2026-10-08-behind-iap-cairn-verifies-the-signed-assertion.md`](../decisions/2026-10-08-behind-iap-cairn-verifies-the-signed-assertion.md), [`2026-10-06-the-built-in-oauth-server-stores-no-clients-and-issues-agent.md`](../decisions/2026-10-06-the-built-in-oauth-server-stores-no-clients-and-issues-agent.md).

## Why this shape

IAP's programmatic access accepts a Google-signed ID token, in `Authorization` or `Proxy-Authorization`, whose audience is an OAuth client on the backend's programmatic allowlist; MCP clients send whatever the token endpoint returns as `access_token`, and Google's own token endpoint returns an opaque access token there, which IAP rejects. So something must stand between the client and Google and return Google's ID token as the access token; that is Cairn's only job here. IAP stays in front of every MCP call, so a bug in Cairn's OAuth code cannot let in anyone IAP would refuse, and removing someone from the IAP access group cuts off their clients with no change in Cairn. Set aside: the built-in server on paths without IAP (Cairn would mint long-lived tokens, and MCP calls would lose IAP); a stateful broker holding Google refresh tokens; a local helper sending `Proxy-Authorization`; dropping IAP.

## Scope

In:
- Client experience: `claude mcp add --transport http --scope user cairn https://<host>/api/mcp` then one browser sign-in with the person's Google account; the person supplies no client id, secret, header or helper. The client refreshes the hour-long ID token silently through the refresh grant for as long as Google's grant lasts. `claude mcp login <name> --no-browser` works (open the printed URL elsewhere, paste the final redirect back). A person authorizes a client only for themselves: the identity that signs in at Google is the one whose token the client receives.
- Security: IAP still guards everything else; only discovery, registration and token are reachable without it, and they return no Cairn data and change no state. Nothing durable is stored: no tokens, codes, grants or registrations; Google's refresh token lives only with the client. Cairn issues no credential of its own: a request whose `Authorization` holds a Google ID token is accepted only beside a valid IAP assertion for this deployment, and without one it is refused and never falls through to another identity. The Google client secret stays on the server, and Cairn calls only fixed Google endpoints. Redirects back go only to loopback, and the round trip through Google cannot be altered to send a code elsewhere. No ID token, no success. The public endpoints are bounded like the rest of the API (size, time), and credentials never appear in logs.
- Protocol: discovery without a challenge (IAP's 401 has no `WWW-Authenticate`); Cairn is the issuer the client hears (RFC 9207), never Google; `resource` is checked locally (RFC 8707) and not passed to Google.
- Configuration: the relay is part of `gcp_iap`, enabled by giving it the Google OAuth client; without one `gcp_iap` is as before. One provider owns the OAuth endpoints: a relay beside `builtin_oauth` is refused. Shared OAuth pieces (metadata, registration parsing, redirect checks, error answers) are reused, not duplicated; consent, stored codes and token minting stay in `builtin_oauth`.
- Attribution: MCP mutations made this way are recorded as the signed-in user (H2).
- `docs/running.md`: the Google client, the allowlist, the load-balancer split, the one-line client setup. ARCHITECTURE's Auth section.

Out: cloud agents (claude.ai and similar connectors, which would need Cairn to hold refresh credentials); the device authorization grant; agent attribution; Cloud Armor; the deployment's infrastructure.

## Acceptance

- End to end against test doubles for Google and IAP (a fake IAP in front of Cairn that answers a bare 401, accepts only a Google ID token for the allowlisted client, passes `Authorization` on and adds a signed assertion), a local MCP client completes discovery from a bare 401, registration, sign-in, code exchange, refresh, and an MCP call whose bearer is the returned ID token.
- Issuer: the `iss` the client receives matches the metadata; a test fails if Google's `iss` reaches the client.
- Bearer rule: a Google bearer with no valid IAP assertion is refused; with a valid assertion, it resolves to the assertion's user.
- Coexistence: a configuration with both the relay and `builtin_oauth` is rejected.
- Redirect tampering: tampering with the client redirect carried through Google is refused.
- Missing ID token: a token response without an ID token fails rather than returning the access token.
- Planted bug: accept any bearer when an IAP assertion is present without checking it, and show the invalid-assertion test catch it.
- Reference deployment (the owner's check, after the deployment work): `claude mcp add` plus one sign-in connects, tools list, and a refresh after an hour keeps working.

## Decisions left to the implementer

- Whether authorize and callback sit behind IAP or with the public endpoints; either meets the requirements.
- What registration returns, as long as the person supplies nothing and the Google secret is never returned.

## Decision log

- The design calls are in [`decisions/2026-10-16-mcp-clients-behind-iap-sign-in-through-a-relay-to-google.md`](../decisions/2026-10-16-mcp-clients-behind-iap-sign-in-through-a-relay-to-google.md) (authorize and callback stay behind IAP) and [`decisions/2026-10-16-behind-iap-mcp-serves-local-clients-only.md`](../decisions/2026-10-16-behind-iap-mcp-serves-local-clients-only.md).
- Registration grant types: a request's `grant_types`, when given, must include `authorization_code`; others the policy does not offer are dropped and the answer lists the policy's (RFC 7591 lets the server replace values). The built-in server offers `authorization_code`, the relay also `refresh_token`. This lets the built-in server register Claude Code, which asks for both; an empty list is now refused.
- Registration returns a stateless client id under the relay's policy, as the built-in server does, and never the Google client or its secret.
- Relay redirects are http loopback only and match ignoring the port (RFC 8252 section 7.3); the built-in server keeps exact matching.
- Redirect URIs may not pre-set a response parameter (`code`, `state`, `iss`, `error`, `error_description`, `error_uri`), for both servers: the answer appends them, so a pre-set `iss` would deliver two issuers.
- Google's authorize URL is built on the fixed endpoint with `scope=openid email`, `access_type=offline` and `prompt=consent` (Google re-issues a refresh token only on consent), no `resource` or `login_hint`, and held to the link length limit.
- The token answer carries Google's ID token as `access_token`, Google's `expires_in`, and a refresh token only when Google sent one, `no-store`. No ID token or any other upstream failure is a 502 `server_error`; Google's `invalid_grant` is passed on as 400 `invalid_grant`; descriptions are fixed, never Google's text.
- `RelayClient` prints its secret as redacted; the provider's `Debug` shows only whether a relay is on.
- The planted bug (a claimed bearer beside an assertion read the assertion's claims without checking its signature) failed `a_google_bearer_counts_only_beside_a_valid_assertion` at its "another key's assertion" row: 200 where 401 was expected.
- The log test captures every target at TRACE; nothing narrows it. While it captures it holds a second, silent dispatcher: with only one in the process, tracing works out a callsite's interest from the thread that first reaches it, so another test's thread would cache Cairn's callsites as unwanted.
- An older attempt's callback is refused without clearing the cookie, so it cannot spoil the newer attempt the cookie belongs to.
