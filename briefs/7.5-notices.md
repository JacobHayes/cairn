# 7.5: Notices: work the final milestone cannot see

| | |
|---|---|
| Id | 7.5 |
| Crates or packages | `crates/engine`, `crates/service`, `crates/api`, `crates/mcp`, `openapi/`, `web/client`, `web/app` |
| Depends on | 5.6; the draft card 8.11 |

## Goal

Tell a route author, without blocking them, about work cut off from the rest of the process. In a graph with a `final` milestone, a node with no chain to or from it gets neither gravity nor dates from it, so it ranks low and carries no deadline in every journey however much it matters; that is usually a missing edge. Importing a route file, publishing a route draft, and the authoring view list each such node as a notice. Notices are Cairn's first advisory finding; this brief builds the shape every later one uses.

## Governing

- PRD: A20 (the notice, what counts as a chain, the role-filling exemption), A15 (notices never stand in for violations), A13 (import), A11 (publish), A12 (authoring), Core concepts (Notice), Priority (why the node gets no gravity from the final milestone).
- ARCHITECTURE: Engine > Date network and Conditions (the chains a notice follows); HTTP API; Requirement map (A20).
- PRACTICES: Code conventions.

## Scope

In: an engine function that returns notices for a route graph, following chains in both directions through dependencies with implicit gates and through date constraints, with every condition treated as relevant; notices in the import and publish responses, the API and OpenAPI, the TypeScript client, and MCP, in one wire shape later notices reuse: `Notice { code: NoticeCode, node: NodeKey, path: Path, message: String }`, the one code being `unanchored`. "Notice" names only this domain concept (the app's save feed is called activity, 8.5). On screen, the draft card, the detail column's empty state on a route draft (8.11): "Notices 2, advisory: publishing is not blocked", each naming a node with its path and Show, which selects and traces it; a hollow warning chip "No path to final" on that node's card; updating live as the draft changes. Import and publish results list notices under their own steel label, apart from violations. The engine and API parts do not wait for 8.11.

Out: notices on segments and journeys (A20: on a journey the signals lens and trace serve), storing notices, and any setting to silence one.

## Acceptance

- Behavior by id: A20 (the vendor evaluation's work inside the final-review stage is not listed, since the stage closes at the decision meeting, and its role-filling decisions are exempt; whatever it does list is recorded in `fixtures/README.md` and checked by hand to have no chain to or from the decision meeting; a route-file variant adds a deliverable with no edges or date rules and lists only it; a variant with the partner-led branch cut loose lists that branch though its condition is unanswered; a graph with no `final` has no notices), A15 (the variant still imports and publishes), A13, A11.
- Playwright: in a route draft's draft card, adding an edge from the listed deliverable to the final report clears its notice without a reload.
- Planted bug: follow explicit edges only, and show the vendor evaluation's stage-bounded work listed by mistake.

## Decisions left to the implementer

- The message wording.

## Decision log

- Wire shape: `Notice { code, node, path, message }` in the schema crate, `code` a `NoticeCode`
  (`unanchored` today); later advisory findings add a code. Notices are additive everywhere: absent
  when empty.
- Where they ride: `notices` on an applied route patch's answer (API `PatchAnswer`, MCP write
  output) when it imports or publishes, listing the graph it leaves (the draft, or the new version);
  `notices` on a proposal preview for a route destination (the review `get_proposal` returns and
  the proposal screen reads), which is the draft's validation output before anyone publishes; and
  `routeNotices` in the wasm host, which the authoring view calls on the draft it holds, so a draft
  edit updates the panel with no server round trip. A draft patch's own answer lists none.
- A chain is read over the dependency graph's full structural edges, plus date rules, stage closes
  and `feeds_milestone` pins as links from the instant that comes first to the one that follows;
  `journey.created_at` is one shared slot. A date decision's answer is its own slot, so a rule naming
  it does not chain the decision to what it merely gates; a pin links the answer and the milestone
  both ways, being one date. Directed otherwise: a node is listed unless the final milestone is
  reachable from it or reaches it.
- The vendor evaluation lists `purpose` and `setup/workload`; checked by hand and recorded in
  `fixtures/README.md`, which a test reads back. The partner-led branch is not listed (it sits in
  Testing, which Reporting requires).
- Messages are English sentences for display, like violations'; clients key on `code`.
- No store migration: notices are recomputed, never stored, so existing databases load unchanged.
- The app's toast store keeps its name (`data/notices.ts`); its rename belongs to the sync-chip
  rework. Import and publish show their notices as a line of the saved toast.
