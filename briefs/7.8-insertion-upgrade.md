## Goal

Let an improved segment reach the places it is used, one insertion at a time, through the upgrade review people already know. An insertion keeps no markers, so its local edits are read as its members' differences from the version it is on. The upgrade translates that version and the target into the graph's keys and runs the existing three-way merge over them: edits made here are kept, changes they did not touch apply, nodes new in the target are added under the keys the insert's minting gives, and nodes the target removed become orphans to keep or remove. Renaming or moving the insertion's root is never an edit, and the graph's roles are never changed by an upgrade.

## Scope

In:

- `Mutation::UpgradeInsertion { insertion, to, roles, kinds }`, the `insertion_upgraded` event, and a draft function returning a proposal; it reaches a journey or route only through an applied proposal, with `open_draft { edit }` first for a route with no draft open.
- Translation: a segment key with a member becomes that member's key, and any other becomes the minted key; the version's root takes the root member's current parent, id, and title (or the recorded parent once that member is gone); mapped roles and kinds and `default_owner` carry the graph's values on both sides; a role or kind new in the target maps by the mutation's choice, with insert's defaults.
- Merge: `merge::merge` over the translated base and target, with a view whose local edits for members are their differences from the translated base; the graph's real markers restored before `changes()`. `Merger::add` takes a provenance (`from_segment` in a journey, none in a route graph), and `changes()` writes no node state for graphs without state. Orphans leave the insertion (`orphaned` in a journey), new nodes join it, its version becomes the target, and items about edges to non-members are dropped as wiring.
- Review items are B7's, so `proposal::resolve` and review are reused; a new filling decision for a role already filled here shows as a violation item.
- API `POST .../insertions/{key}/upgrade { to }` and the MCP `upgrade_insertion` tool; a line in `instructions/SKILL.md`.
- Screens: `Review upgrade` from Origin, a member's overflow menu (Upgrade insertion, only when available), and each segment detail row; review titled "Update Security review to version 3", with kept edits under an "Unchanged here" fold; Origin's "Edited here: title, owner" from the differences; the journey card's one sentence counting route and insertion upgrades, only when non-zero.
- Fixture: a v2 of the 7.6 segment that changes one field, adds a node, and removes one.

Out: upgrading many insertions at once, and contributing an insertion's edits back to its segment (PRD Later).

## Acceptance

- B14: a local edit is kept; an unedited changed field applies; a removed node is orphaned with keep or remove; a node new in v2 is added under its minted key; a renamed and moved root is not an edit; a role new in v2 is added; a conflict is surfaced; a route upgrade leaves members alone.
- J3: the scenario "insertion upgrade with orphans and local edits" replays field by field.
- Playwright: from segment detail, review and apply the upgrade of one insertion, keeping its local edit; Origin then reads version 2 with no upgrade available.
- Planted bug: mark every member edited, and show an unedited change not applied.
