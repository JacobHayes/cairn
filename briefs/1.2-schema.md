# 1.2: Schema and fixtures

| | |
|---|---|
| Id | 1.2 |
| Crates or packages | `crates/schema`, `fixtures/`, `schema/` (generated) |
| Depends on | 1.1 |

## Goal

Turn the PRD's data model into the serde types every other crate shares, define the file format and wire form as one schema, generate the JSON Schema, and write the fixtures every later brief tests against. Shapes, serialization, and value-level limits only; graph-level validation is 2.1's.

## Governing

- PRD: Core concepts (the glossary is the type list); How the pieces fit; Identity and references; A1, A1a, A14, A17 (patch shape), J1 (event shape); Invariants (the per-field ones); Illustrative example.
- ARCHITECTURE: Engine > Model (newtypes, closed enums, proposals outside the graph); Conditions; File format; Storage > Schema outline; Generated artifacts.
- PRACTICES: Explicit limits (every value-level limit enforced at deserialization); Code conventions.

## Scope

In:

- Identifier newtypes (node, role, kind, entity, and user keys; id slug; path; graph, route, journey, patch, and proposal ids; revision) with fixed key prefixes.
- The graph document with one node struct of shared fields and a kind-specific payload enum (ARCHITECTURE, Model), so a field a kind cannot have is unrepresentable; conditions; date rules; stage bounds; participations (including explicit empty); attachments with message drafts stored as parsed segments.
- Journey state, the patch and its closed mutation enum with one exhaustive structural-or-state classification (PRD glossary, Structural change), the remove mutation naming its subtree, incident edges, and attachments (A18), the patch receipt, verified emails on an identity, the change set, the conflict and rejection shapes, the event, the proposal record, the derived shapes, and the derive inputs.
- The file document (unresolved, as written) and the graph document (resolved) as two types; the `KeyAllocator` trait; deterministic YAML and JSON.
- The touched-set function over mutations and event deltas (H5).
- `limits.rs`; `testing` strategies for every type.
- Fixtures: the vendor evaluation (every mechanism in the PRD's illustrative example), a hiring loop (small, deep containment, a multi-valued role), a product launch (many milestones, several date rules, no conditions), each with a journey scenario as a list of patches, plus one journey with no route (the PRD's ad-hoc sibling); a `fixtures/README.md` with a paragraph per fixture.

Out: graph-level validation (2.1, 2.3); API envelopes beyond shared payloads (4.2); store rows (3.1).

## Acceptance

- Every fixture parses and round-trips byte for byte; two serializations of one document are identical.
- A1a's kind restrictions are unrepresentable; a violating document fails to parse with a path. Each limit has a test at the limit and one past it that names the limit.
- A patch with every mutation variant and an event of every type round-trip; a key and an id cannot be swapped in a reference; paths serialize slash-joined.
- Planted bug: remove one limit check and show its test fail.
- Adds rungs 2, 3, and 5 (the JSON Schema in `schema/`).

## Decisions left to the implementer

- Field spellings and serde representations, provided the YAML reads as the PRD's examples do.
- Whether journey state is on the graph document or a sibling type joined by key.
- The JSON Schema generator crate.

## Decision log

Appended by the implementer.

- Crate `crates/schema` (`cairn-schema`); 1.1's throwaway `crates/scaffold` is deleted in the same change. `briefs/proof/1.1/prove.sh` now plants its rung 1 violations in `crates/schema`, plants its zero-test rung as a rung 4 (rung 2 now has tests), and writes the planted engine crate's manifest inline.
- Identifiers: id slugs are `[a-z0-9][a-z0-9_-]*` (the PRD's own ids use `_`, as in `eval_owner`). Every key and client-generated id has a fixed prefix followed by a slug: node `n_`, role `r_`, kind `k_` (built-in `owner` is `k_owner`), entity `e_`, attachment `a_`, journey `j_`, patch `p_`, proposal `pr_`, user `u_`, agent `ag_`. Route ids are plain slugs, since route files carry them for people to read. Paths are `Vec<Slug>` that serialize slash-joined and order segment by segment (depth first, siblings by id).
- Dates and timestamps are `jiff` (`civil::Date`, `Timestamp`), the engine's one date dependency (PRACTICES, Dependencies are deliberate), with default features off so nothing reads the OS time zone database.
- Limits: `limits.rs` holds the value-level limits and a `Limit` enum whose `name()` is what errors print, so a test checks that an error names its limit by comparing against `Limit::name`, not by wording. Emails are stored trimmed and lower-cased (H3 compares them that way), so an email does not round-trip byte for byte unless written normalized.
- Rung 2 is `cargo test` over the workspace with property tests skipped by name, one suite per crate. Rung 3 is the `tests/property_*.rs` files (each inside `#[cfg(test)] mod property`, which also lets the helpers there unwrap), one suite per file, at `PROPTEST_CASES` (256 locally, 4096 in CI's nightly job). Neither writes a temporary file.
- One schema, two forms: the graph types are generic over `References` (`FileRefs`: nodes by path, roles and kinds by id, own keys optional; `KeyRefs`: everything by key, keys required). A key slot is `Option<Key>` in the file form and `Key` in the graph form, so serde's missing-field handling makes keys optional in one and required in the other without a second set of types. JSON Schema names carry the form (`Node`, `NodeResolved`).
- Collections hold their limits: `BoundedVec` (written order), `BoundedSet` (sorted, a duplicate is an error, not dropped), `Keyed` (a map serialized as a list sorted by each value's own key; a repeated key is an error), `OneOrMany` (one item written bare). Collections the limits table does not name use the `ByDocumentSize` marker, which points at `graph_bytes_max` ([`decisions/2026-10-06-values-the-limits-table-does-not-name-take-the-nearest-named.md`](../decisions/2026-10-06-values-the-limits-table-does-not-name-take-the-nearest-named.md)).
- Conditions: externally tagged, as ARCHITECTURE writes them (`equals: {decision, value}`, `answered: <decision>`, `all`, `any`, `not`). A compared value is a boolean or text (a choice id, date, entity key, or text, which the decision's answer type gives meaning, checked by the engine), bounded by the title limit; `in` takes at most `entity_count_per_fill_max` values. Clauses are the leaf predicates; depth counts a lone clause as 1; an empty `all` or `any` is rejected. Serde parses the tree recursively (bounded by the format's own nesting limit); the limit check after it is iterative.
- Attachments: resources (`tip`, `template`, `example`, `reference`, `message_draft`) and annotations (`note`, `artifact`, `reference`, `conversation`) are written flat with exactly one content field named after the type, which reads as the PRD lists them. Message drafts are written as templates (`{{journey.name}}`, `{{roles.<role>.name}}`, `{{answers.<decision>}}`) in both forms and held as parsed segments; an unknown placeholder or an unclosed `{{` fails to parse. An annotation is its body (what an add or edit carries: key, node, title, content) plus `created_by`, `created_at`, and `edited_at` from the patch (G1: attributed and timestamped).
- `KeyAllocator` mints key bodies (object-safe, one method); `mint::<K>()` adds the prefix; `SequentialKeys` counts per prefix for tests and fixtures. Uniqueness against a graph's live and retired keys is the caller's check.
- The node is written flat, as A1a lists its fields, and parsed through `NodeWire` (every field any kind may carry, `deny_unknown_fields`) into `Node { shared fields, payload: Payload }`. One table, `KindField::allowed_on` and `allowed_for_answer`, drives both the parse check (an error names the field, the kind, and A1a) and the JSON Schema's `if`/`then` rules, so they cannot disagree. Answer-type fields are part of the decision payload (`AnswerSpec`): `choices` only on choice decisions (at least one, ids unique), `fills_role` only on entity decisions, `feeds_milestone` only on date decisions.
- Node identity is `key` (slot), `id`, and `parent` (a reference), the same three fields in both forms; a file writes `parent: setup` rather than a full path, and the path is derived. Weight is `Option<Weight>` (absent means the kind's default, A9) and flags at their defaults are not written, so a canonical file has one spelling per node. `final` is `is_final` in Rust.
- A date rule is `{before|after: <source or list>, offset: <days>}` with exactly one direction; offset 0 is not written. Sources are node references or `journey.created_at` (a path cannot contain a dot, so they never collide). Sources per rule are bounded by `edge_count_per_node_max`, since each is one constraint edge.
- Participations are `{kind: source}`, where a source is a role reference (a string) or explicit entities (a list; `[]` is explicit none, E2), at most `kind_count_max` kinds and `entity_count_per_fill_max` entities. A node's own `requires` list holds `edge_count_per_node_max`; in plus out is the engine's.
- Editable fields: `NodeField` and `NodeFieldValue` name each field a single edit changes (the touched-set and local-edit granularity). Changing a node's kind or a decision's answer type replaces the whole node rather than being a field edit. `NodeFieldValue::write` returns false and leaves the node alone when the kind lacks the field, for the engine to report.
- Journey state sits on the graph document (`Graph.state`, empty and unwritten for route versions and drafts), as ARCHITECTURE's Model says (readiness ruling). The journey's own fields (`JourneyHeader`: name, status, lineage, `created_at`, and `created_on`, the deployment-local day date rules measure from, stored so the engine never converts time zones) sit beside the graph in `Journey`, with the revision. Routes are `Route` (header, revision, published version numbers, optional draft) and `RouteVersion` (immutable, loaded alone); the deployment is `Deployment` (entities with normalized emails, aliases, revision).
- The file document is `RouteFile` (`format: 1`, route id, name, `extends`, roles and kinds by id, nodes); it carries no state and no retired keys, which belong to the stored graph. The graph document is `Graph` (roles, kinds, nodes as `Keyed` lists, `retired_keys` for nodes, roles, and kinds, and state).
- Stored state per node is one `State` enum over every kind's values (`derived` is a group that is not skipped), with `State::legal_for(kind)` and `State::initial(kind)`; a per-kind enum would have needed the node's kind to deserialize. Role fills from a filling decision and pins from a `feeds_milestone` answer are derived from the answer, not stored (E3), so `role_fills` and `pins` hold only direct ones. Journey participations and weight overrides are edits to the journey graph's node fields, marked by `LocalEdit` (B5), not a separate table; local edits are their own map beside node states, so an edit and a transition on one node touch different records (H5). A guard bypass is stored on the node's overrides with the guards bypassed, the reason, and the specific failures present (D4).
- YAML is `serde-saphyr` (panic-free, budgeted against alias bombs, no unsafe), read with YAML 1.2 booleans only (so `no` is text: a choice id may be `no`) and repeated keys rejected; `serde_path_to_error` gives every parse error its path (`nodes[3].estimate`), and the YAML reader adds line and column. Every parse checks `request_bytes_max` first (a patch around a graph at its cap is larger than the graph); the 16 MiB graph cap applies to the graph a patch produces, which the engine's validation checks (review round 1).
- The patch: `{id, target, base_revision, deployment_revision?, mutations}`, where `target` is a journey, a route, the deployment, or a proposal within its destination; at least one mutation, at most `mutation_count_per_patch_max`. Mutations are internally tagged by `op` and cover every change the PRD defines (journey and route lifecycle, drafts and their sources, graph structure, journey state, lineage, entities, proposals). Field edits are `set_node_field` (one field each); a kind or answer-type change is `replace_node`. Start and reach take no date: the engine records today and `set_recorded_date` edits it (F1, F2). A guard bypass is an override applied in the same patch as the transition it covers, so it is its own event (J1 lists "guard bypassed"). F5's shift is `shift_pin` (signed days within `offset_days_max`); repin is `set_pin`; unpin is `clear_pin`.
- `change_class`: one exhaustive match. Structural: node, edge, role, kind, default owner, resource, and route changes, removals, journey create and delete, upgrade, re-link, provenance and local-edit markers, entity merge, proposal apply (its content is unknown to the patch). State: transitions, answers, recorded dates, role fills, pins, snoozes, overrides, atomic, notes and links, participations, the weight field (B5), journey name and status, entity create and edit, proposal create, edit, and discard. Every patch to a route is structural.
- A removal names the node, its descendants, every incident edge, and the resources, annotations, and participations on them (A18), as sets.
- Proposals: `ProposalDraft` (title, description, destination revision, mutations, review items) is what create and edit carry and cannot hold a proposal mutation, which bounds the recursion at one level; `Proposal` adds id, destination, editing revision, status, proposing agent, creator, and creation time. Review items are conflicts (journey and route values, with a resolution: keep, take the route's, map a choice, clear state, reopen), kept local edits, orphans (keep by default), participation mappings (B8), exclusions, and removal cascades.
- YAML writes dates quoted (`"2026-10-02"`), as a YAML 1.1 reader would otherwise take them for timestamps; the canonical files and fixtures are written that way.
- Event deltas and the change set: a delta is the list of `Write`s its mutation made, each the after-state of one stored record (`Put`), a removal by address (`Remove`, which may name a whole domain, graph, or node), or a whole-graph copy (publishing a draft). Replay applies writes in order and re-derives nothing, so it is exact by construction (J3), and a `ChangeSet` is the patch's receipt plus its events, whose writes are everything a store persists; the store never needs the engine. Records mirror ARCHITECTURE's Schema outline: graph-scoped records (`Record::Graph { graph, record }`) and domain records (journey and route headers, drafts, versions, deleted journey ids, entities, aliases, proposals). An event's type is derived from its mutation (`Mutation::event_type`), as is its subject; `log` is the patch's domain except a journey deletion, which the deployment log keeps (A19).
- Touched sets: a `TouchedSet` is a set of record addresses (`RecordKey`), by key and, for node fields, by field. A whole domain, graph, or node address overlaps everything under it, and an edge belongs to both its ends, so a removal overlaps any change on the nodes it removes. `Mutation::touched` is computed from the mutation alone (a removal names its reach, A18); a mutation whose effect depends on content it does not name (create, delete, publish, upgrade, re-link, apply a proposal) touches its whole domain, as does any mutation the per-group functions do not list, which is safe because a coarse touch only stops an automatic retry. A transition or answer also touches the node's snooze and answer (B6, D1); a field, edge, participation, or resource edit also touches its local-edit marker. A proposal edit touches only the proposal (H5: drafting does not advance the destination). `Event::touched` reads the delta.
- Receipts: `Patch::content_hash` is SHA-256 over the patch's canonical JSON (the deterministic wire form, id included), lower-case hex. `PatchReceipt` is patch id, domain, content hash, and the revision produced.
- The dispatch functions over the mutation set are split in two to stay under the 70-line limit, with the second half's fallback unreachable; the test over a patch holding every mutation (checked against the variants the JSON Schema declares) calls them on every variant, so a variant left out fails that test.
- Rejections: `Stale` (the revisions that moved on, domain or proposal, and the intervening touched set, H5), `PatchIdReused` (H5), and `Invalid` (at least one `Violation`, A15). A violation has a closed `ViolationCode` (one per invariant, guard, state-machine rule, and lifecycle rule the PRD names), a location (mutation index, subject key, node path, field), a display message, related keys, the limit for `limit_exceeded`, the guard a bypass would accept it past (D4), the specific guard failures, and, for `contradictory_chain`, a `ChainList` of at most `chain_count_per_rejection_max` chains and whether there were more (F5). The two limits that bound response sizes (`chain_count_per_rejection_max`, `explanation_entry_count_max`) joined the `Limit` enum; `Limit` serializes by name.
- Chains (F2 to F7): a `Constraint` is `after >= before + offset_days` between two instants (a node's start or finish, or `created_at`; a container's entry is internal and has no form), with its source (a rule, a dependency and how it arose, an estimate, containment, a stage close) and whether it is conditional. A `Chain` is constraints plus the pins and actuals on it; a `ShortChain` adds the days short. Bounds and rejections share them.
- Derived shapes (readiness ruling: what crosses a crate or the API): `Derived` (today, per-node `NodeDerived`, the ranked frontier and acting frontier, the stalled diagnostic), `Consequences` (D7), `DeriveInputs` (today, time zone name, `RankConstants` defaulting to the PRD's, viewer entities, the deployment context as a `Deployment`), and `DomainDocument` (journey, inputs, engine version). Gravity and leverage are `Score`s in half-weight units written as numbers (`2.5`), exact under the undecided discount; rank is an `f64`. Explanation lists are `Explained { entries, total }`, complete in the engine; `for_response` keeps the first `explanation_entry_count_max` (the engine orders them largest first) and the total.
- `serde_json` reads floats with `float_roundtrip`, so a rank survives the wire exactly: a property test found the default parser off by one unit in the last place.
- JSON Schema: `schemars` 1.x (already a dependency since the first change, for every type's schema), draft 2020-12, generated from `RouteFile` by the `cairn-schema-gen` binary in the schema crate (`mise-tasks/gen/schema`, which writes only `schema/`) into `schema/route-file.schema.json`, marked generated by a `$comment`. A test validates a route file using every field against it and checks that the kind restrictions and unknown fields the parser rejects, the schema rejects too. Rung 5 records the path and SHA-256 of every file under the generated paths that exist (`openapi`, `schema`, `web/client/generated`, `web/wasm/generated`), runs `mise run gen`, and fails on any difference, printing the changed lines.
- YAML is written with the serializer's defaults: literal blocks for multi-line text, folded blocks for single lines over 80 characters, so canonical files and fixtures use those forms.
- Fixtures: `fixtures/<name>/route.yaml` (a route file carrying every key, standing in for the route's version 1) and `fixtures/<name>/journey.yaml` (a `Scenario`: the journey id, a description, and steps, each a patch with a note, today, a commit timestamp, and an actor). Keys in fixtures are readable (`n_access`) rather than random, so scenarios read. Entities are created inside journey patches (E6), so fixtures need no deployment file. Every fixture file is in canonical form (written by the serializer), which the fixture tests check along with sequential journey revisions, routes matching lineage, every touched node existing, and the vendor evaluation's coverage of the illustrative example. Writing the bake-off fixture, the parser caught a role id where the graph form needs a role key, with its path and line.
- `cairn-document <route-file|scenario|patch|graph> <file>` (a second binary in the schema crate) parses a document and prints its canonical YAML or the error with its path; route authors can check a file before import, and the proof script uses it.
- Planted bug: removing the condition depth check fails `condition::tests::depth_at_and_past_its_limit` with `panicked at crates/schema/src/condition.rs:282:38` (`test result: FAILED. 3 passed; 1 failed`); restored, it passes (`briefs/proof/1.2/README.md`, generated by `prove.sh`).
- Review round 1 (bake-off: `gpt-6.1-sol` and `gpt-6-luna`), fixed in one change on top: rungs 2 and 3 force `CARGO_TERM_COLOR=never` before reading cargo's output (CI sets `always`, which hid every property suite); rung 3 rejects a zero or non-numeric `PROPTEST_CASES`; parses check `request_bytes_max` rather than the graph cap; rank and rank coefficients are a finite, non-negative `Real` (YAML's `.nan` and `.inf` no longer reach the JSON wire); `TouchedSet::overlaps` indexes the covering addresses instead of comparing every pair (a property test holds it equal to the pairwise definition); and the parser and JSON Schema agree on the cases found: a kind-restricted field written `null` is rejected (it is non-nullable in the schema), string schemas carry `minLength` and `maxLength` from their limits (in characters, so necessary rather than sufficient beyond ASCII), date rules and attachments require exactly one of their alternatives, and choices are non-empty. Not changed: the hiring-loop fixture, which the PRD's Domain-free requirement names as one of its own generic examples.
- Review round 2 (`gpt-6.1-sol`), fixed in a second change: the YAML reader's budget (250,000 nodes by default) is set from the request cap, so every document within Cairn's limits parses; text condition operands may be empty or multi-line, as text answers may (body limit); explicit `null` is rejected in the exactly-one forms (resources, annotations, date rules) as in kind-restricted fields; the path schema bounds each segment and the segment count; `all` and `any` require a clause in the schema. Fixtures: the product launch's multi-valued `writers` role is reached through a multi-valued `contributor` kind rather than `owner` (A7); the vendor evaluation finishes the workload and baseline before the findings, since reporting requires testing; patches that refer to entities created earlier name the deployment revision ([`decisions/2026-10-06-entity-creates-in-another-domains-patch-advance.md`](../decisions/2026-10-06-entity-creates-in-another-domains-patch-advance.md)), which a fixture test now checks.
- Review round 3 (`gpt-6.1-sol`), fixed in a third change: participations are read entry by entry, so a kind written twice in JSON is an error rather than the last one silently winning; a labeled choice rejects unknown fields; the schema gives participations `maxProperties` and each `all` or `any` `maxItems` (`condition_clause_count_max`). Left to the parser: the tree-wide clause count and depth limit of a condition, which JSON Schema cannot express; the clause schema's description says so.
