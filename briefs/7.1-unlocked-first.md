# 7.1: Unlocked nodes first in a pass

| | |
|---|---|
| Id | 7.1 |
| Crates or packages | `web/app` |
| Depends on | 8.2, 8.9 |

## Goal

Make a triage pass on the Next page's cards, and the decision walkthrough in particular, follow a line of work before moving on: after any action on a card, the nodes that action brought onto the acting frontier come next, ahead of the cards already waiting, each labeled with the card that unlocked it. Answering one decision then leads straight to the decisions it opened, the way a flowchart walks its branches, while the shared rank stays what every other surface shows.

## Governing

- PRD: C11 (the ordering after an action, including one taken in a node's detail opened from the card), D7 (the `unlocked` consequence), C10 and Priority (the shared rank the pass leaves alone), C5 (rank tags unchanged).
- ARCHITECTURE: Web UI (Screens; a pass is client state).
- PRACTICES: Code conventions (TypeScript).

## Scope

In: the pass order in `acting/pass.ts` and the Next page's cards (8.9): what one action unlocked is the `unlocked` list in its patch's consequences (D7, 8.2), computed by the server at one revision, never a client diff of the frontier, which could credit another person's concurrent change to this action. Those nodes come next in rank order among themselves, ahead of the waiting cards, and a later action's unlocks go ahead of an earlier action's. Passed cards still go to the back. Any write made from the pass counts as a pass action: one on the card, and one in a linked node's inspector opened from the pass before returning to it, whose unlocks are labeled with the node acted on. Writes made elsewhere (another tab, another page) never reorder the pass. Each unlocked card's band reads "Unlocked by <title>" (a link, cut short on a phone so Pass stays on the band), and the pass rail shows it indented with a marker; the "new to act on" notice names only what surfaced from someone else's change; "Done in this pass" includes the unlocked cards finished in it; the label is dropped once the card is acted on or passed and stays dropped across a refetch. The order survives a refetch within the pass, and Start a new pass returns to plain rank order.

Out: the shared rank and its tags (Priority, C5), the Next list's order (C10), the graph, and the agent snapshot (I3): none of them change, and no "unlocked" mark appears on graph or list cards. Elsewhere, unlocks appear only in the sync chip's Recent (8.5).

## Acceptance

- Behavior by id: C11 (order after an action; label; pass emits no event), C10 (next list order unchanged by a pass).
- Playwright on the Next page's cards and in the inspector, over a route-file variant of the vendor evaluation that adds a follow-up decision relevant only when a partner runs the testing (8.1 uses the same variant): with decisions on, answering the partner decision puts the follow-up next, labeled with it, ahead of up-front decisions that outrank it; passing an unlocked card moves it to the back; starting a new pass returns to rank order. Without the decisions filter, completing the test plan's last child action brings the plan next, labeled. Opening a linked node from a card and completing it in that node's inspector puts what it unlocked next, labeled with that node. The Next list in another tab shows the same order before and after.
- Unit tests in `acting/pass.test.ts` for nested unlocks (an unlocked card whose action unlocks more) and for an unlocked card that leaves the frontier before it is reached.
- Planted bug: order unlocked cards by rank among all waiting cards, and show the walkthrough test fail.

## Decisions left to the implementer

- How deep the pass rail indents nested unlocks (an unlocked card whose action unlocks more).

## Decision log

- The tab's save record (`SaveEvent`) now carries `unlocks`: the node the write acted on (the first
  mutation about a node, since evidence annotations and new entities can come first), the patch's
  `unlocked` list (empty for a Start, which still ends that card's place at the front), and when the
  write was sent. The pass reads saves sent while it is on screen, so a write from the card and one
  from a node opened beside it count; one sent on another page (even if it lands after the pass
  opens), before the pass opened, or from another tab never does.
- Acting on an unlocked card, even one that stays on the frontier (Start), ends its place at the
  front along with its label; its own unlocks go first. A card that leaves the frontier before it is
  reached is skipped, not forgotten, so it would lead again if it came back.
- The rail indents an unlocked card one level, however long the chain: by the time a chain has a
  second link the card that unlocked it is done, so a deeper indent would only narrow the column.
- A pass kept in session storage by an earlier version has no `unlocks`; it reads as having none.
- The Playwright test covers the walkthrough (answer, label, pass to the back) and a node
  completed in its inspector from the pass; "Start a new pass returns to rank order" is asserted
  there too. The unit tests carry nested unlocks and the card that left the frontier. Not
  written: the second tab's Next list (the list never reads the pass) and the test plan's last
  child, which is the same path as the inspector case.
