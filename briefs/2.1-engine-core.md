# 2.1: Engine core

| | |
|---|---|
| Id | 2.1 |
| Crates or packages | `crates/engine` (model, validate, apply, transition, event, replay) |
| Depends on | 1.2 |

## Goal

The in-memory graph model and the one write path. After this brief a host can build a graph from 1.2's documents, apply a patch and get either a change set with one event per mutation and the next revision or a complete rejection, and rebuild any graph from its events. Every structural invariant holds on every accepted graph, every state machine allows exactly its table's transitions, and fixtures load through the model. The validation stages that need derived state arrive with 2.2, 2.3, and 2.4.

## Governing

- PRD: Core concepts; Identity and references; Containment (the tree); A2, A3, A4, A6, A7, A11 (publish as copy), A15 to A18, B1 to B5, B10, B11, D1, D1a (the stored side), D4 (`has_artifact`, `broken_down`, bypass recording), E3, E6, G1, G2, Invariants (graph and journey, except the date line), J1 to J3.
- ARCHITECTURE: Engine > Model; Write path: apply; Testing the engine.
- PRACTICES: Rules; Errors, panics, and rejections; Testing > Engine.

## Scope

In: `Graph` and `Deployment`; `apply` with the validation pipeline as an ordered stage list that later briefs extend, and an `Applied` only the pipeline can build; the change set by diffing base and candidate; the A18 removal cascade; the per-kind state machines, with reopen clearing what the D1 tables say, a container skip as one event, and a transition on a snoozed node clearing its snooze in the same event; role fills routed through their filling decision (E3); same-patch entity create (E6); building a graph from a file document with no base version (supplied keys kept, missing ones minted through a host-supplied allocator), so fixtures load; retired keys kept per graph; publish; events and `replay`; the scenario harness (one J3 matrix entry per scenario naming its PRD id and owning brief, checking expected state as well as replay equality); `testing::{arb_graph, arb_ops, Op}`; every structural invariant check and the cycle check over explicit and containment edges.

Out: everything derived (2.2 to 2.6); import against a base version, export, and merge documents (2.7); storage.

## Acceptance

- Behavior by id: A2, A3, A15 (three independent violations report three), A16, A17 (all or nothing; a base revision mismatch is a rejection), A18 (a removal leaving a dangling condition is rejected unless the patch fixes it; a removal whose subtree or edges gained a node or edge it does not name is rejected, including a child moved in, and one whose node gained a note or participation since; a removed key re-added as a new node is rejected), B1, B4 (markers set and reset; tombstone on removal), B5, B10, B11 (archived accepts only un-archive or delete), D1 (every row of every table), D1a (one event; reopen restores), D4 (a bypass records the failures it bypassed), E3, E6, G2, J1 to J3.
- Properties: apply then replay equals apply; a rejected patch leaves the graph unchanged; event count equals mutation count.
- Planted bug: skip the tombstone write on removal, in state and event both, and show the B4 scenario fail on its expected-state check.
- Fixtures: all parse into `Graph`; the vendor evaluation scenario runs through apply and replay.

## Decisions left to the implementer

- Internal indexing and how the candidate clone stays cheap at the node limit.
- The stage list's exact form, provided a later stage is added in its own module and cannot be skipped.
- Scenario harness layout and naming.

## Decision log

Appended by the implementer.

- Crate `crates/engine` (`cairn-engine`): `graph` (`Tree`, an index of any document by parent and path that records a broken tree rather than failing, and `Graph`, a document that passed validation), `file` (`from_file`), `records` (`Records` with `write` and `advance`), `transition` (the D1 tables as data), `pipeline` (`apply`, `ApplyInputs`, `Applied`), `replay`, and `testing` behind a feature; private `validate` (the graph stages), `mutate` (one handler module per mutation group), `stages` (the pipeline's stage list), `edit`, and `entity`. Calls that shape the design are in DECISIONS.md (records and replay; mutation semantics; the cycle check's reach; assertions).
- The stage list is `stages::STAGES`, a fixed array `apply` iterates whole; each stage is its own module (`graphs`, which runs the graph stages `validate::GRAPH_STAGES` on every graph the patch wrote: structure, references, cycles, journey state; `entities`; `deployment`; `guards`). A later stage is a new module and a new array entry. `Applied` has private fields and only `pipeline::apply` builds it.
- Indexing and the candidate: the candidate is one clone of the loaded `Records`; nothing indexes it during mutations (lookups go through `Keyed`'s sorted map), and each validation builds its `Tree` once. Mutation-time checks build a tree only to locate a violation by path.
- Violation locations: a violation found at a mutation's position carries the mutation index (inside an applied proposal, its message names the proposal's mutation); one found on the final graph carries the node's path and subject but no index, since the whole graph is checked once.
- Schema changes (AGENTS: earlier work is not frozen): `ViolationCode::MutationNotForTarget` for a mutation the patch's target does not take (a transition in a route patch); `NodeField::ALL` and `State::ALL`, so the engine and its tests walk every field and state.
- Rung 1 runs clippy with `--no-deps`: without it, a scoped crate's lints (the engine's `indexing_slicing`) were applied to the workspace crates it depends on (the schema crate).
- Tests: `tests/graph.rs` (fixtures build; every invariant reported under its code; three independent violations report three), `state_machines.rs` (every row of every D1 table through `transition::next` and through apply, nothing else; dates; D1a; B6), `apply.rs` (A15 to A18, B4, B5, B10, B11, D4, E3, E6, G2), `domains.rs` (routes, the deployment, proposals; J2: every `op` the patch format's JSON Schema declares applies and emits its event), `matrix.rs` (the J3 matrix: 16 entries, each with its PRD ids and owning brief, its expected state, and replay compared field by field after every step), `property_apply.rs` (apply then replay equals apply; a rejection leaves the records unchanged and lists a violation; one event per mutation and the revision advanced by one; every accepted graph passes `Graph::new`; apply is a function of its inputs). J3 entries that need derived state (dates, contradictory chains, blocking, stale flags, snoozes holding, upgrades, imports) belong to 2.2 to 2.7.
- Planted bug: skipping the tombstone write in `mutate/removal.rs` (state and event both) fails the matrix's B4 entry on its expected state: `assertion left == right failed: route-copied nodes only (B4) left: [] right: ["n_criteria", "n_partner_led", "n_partner_results"]`; restored, it passes (`briefs/proof/2.1/README.md`, generated by `prove.sh`).
- Review round 1 (`gpt-6.1-sol`), eight findings, all valid, fixed in one change on top with a regression test each: clearing a participation on a missing node panicked instead of reporting it; a completion reopened in the same patch escaped its guards (every attempted completion is now checked on the final graph, whatever the node's final state); the deployment record had no 16 MiB check; editing a proposal through another destination panicked; a riding entity create slipped past the archived-journey ban; a skip's reason was lost (it is now `NodeState::skip_reason`, a schema addition, kept while the node is skipped and cleared on reopen, and validation holds a reason exactly on skipped nodes); a message draft whose keys outgrow its paths past the body limit panicked in `from_file` (now a `limit_exceeded` violation); and a removal that cut an incoming edge on a route-copied node left no local-edit marker (B4). Found while fixing them: an entity create riding in a patch to a journey or route that does not exist was accepted (it now needs its target, as everything but a proposal apply does), and an applied proposal that does not create its new destination was accepted with nothing to show for it (now `target_missing`).
- Review round 2 (`gpt-6.1-sol`), six findings, all valid, fixed in a second change with a regression test each (the two cost findings by construction): a replacement that changes a decision's answer type set no marker (a new `LocalEdit::Shape`, a schema addition, now marks a kind or answer-type change, and the schema's touched set for a removal names the markers it sets on nodes that keep a cut edge); a proposal that deletes its existing destination was rejected as not creating it (only a proposal for a new destination must create it, and the event of a proposal that deletes a journey goes to the deployment log, A19); comparing a replaced node's resources and consuming resource keys in `from_file` were quadratic (now by key and by iterator); a bypass's failures were recorded on the last write of the node's overrides rather than on the guard-bypassed event (now on every write that holds the bypass); and `from_file` stopped at the first unresolved reference (it now leaves such references out, still builds the graph, and reports its invariants too, except when two objects share a key). Found beside them: a rejected mutation built a tree to locate itself, so a patch of thousands of failing mutations rebuilt the tree thousands of times; violations are now located once, from one tree of the graph the patch would produce (or the one before it, for a removed node).
- Review round 3 (`gpt-6.1-sol`), four findings, all valid, fixed in a third change with a regression test each (the cost finding by construction): a journey that names an entity only in a condition on an entity decision did not count as referencing it for a merge (conditions are now walked for entity keys; an unknown key in a condition is not itself a violation, so a route can be imported into another deployment); the archived-journey ban rejected a proposal apply before its own unarchive or delete could run (the ban now holds each of the proposal's mutations, and an empty proposal on an archived journey is rejected); handlers copied the whole node, every resource included, for each lookup, quadratic in a node's resources (lookups now borrow); and a message draft reported only its first unresolved placeholder (now each).
- Checks: `mise run check:fast` passed on each change; `mise run check` passed at the end (rungs 1, 2, 3, 5).
