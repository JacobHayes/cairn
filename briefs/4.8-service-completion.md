# 4.8: Service completion: priority, projections, proposals, route files

| | |
|---|---|
| Id | 4.8 |
| Crates or packages | `crates/service` |
| Depends on | 2.7, 4.1 |

## Goal

The service operations that need the whole engine, on 4.1's composition, write path, and notifier: derived reads with priority and every projection, memoized invisibly; proposals as first-class records with client ids and two revisions, previewed with their consequences and applied with the confirming user; upgrade, save-as-route, and re-link as proposals; route import and export.

## Governing

- PRD: A13, B7, B8, B9, C14 (the service half), D6, H2 (the confirming user), I3 (the service half), I6, I7; Non-functional: Journey durability (an upgrade only once confirmed), Portable data.
- ARCHITECTURE: Service layer and composition; Engine > Read path (memoizing `Derived`); Projections; Model (Proposal); Upgrade, save-as-route, re-link; File format; Storage > Store trait (proposals).
- PRACTICES: Errors, panics, and rejections; Explicit limits (request duration, explanation entries per value in a server response, snapshot top-N, history page).

## Scope

In: derived reads over `derive` and 2.6's projections (snapshot, level, trace, decision view, timeline, status summary, next, mine, list, history, node detail with capped, pageable explanations), with the viewer's entities from 4.1; memoization keyed by domain revision, deployment revision, today, the viewer, and the rest of the derive inputs; the proposal lifecycle (create with a client id against any domain, including a new one at revision 0; edit against its editing revision; fetch by id; preview with D7 consequences; apply checking both revisions, with the confirming user; discard; on a stale base, the intervening changes and a refresh that re-runs the merge on the new base, carries resolutions by node and field, and requires renewed review); upgrade, save-as-route, and re-link producing proposals; route import against a base version and export (A13).

Out: HTTP (4.9); MCP (4.3); the review screen (5.7); assistant-drafted proposals (4.4 produces ordinary documents).

## Acceptance

- Behavior by id: I6 (each clause, including idempotent duplicate submission by id), H2 (the confirming user stamped on proposal apply), D6 (cached and uncached reads are identical across an entity merge and across midnight), D7 (consequences on every proposal preview), I7 (an agent applying an upgrade goes through the same confirmation as anyone), A13 (an export imported back through the service as a new draft matches by path), B7, B8, B9 through proposals, C14 (the service half), I3 (paging and scoping through the service).
- Planted bug: skip the confirming-user stamp on proposal apply and show the H2 test fail.

## Decisions left to the implementer

- Whether reads return `Derived` plus a projection or a projection enum; the cache's implementation and bound.

## Decision log

Appended by the implementer.

- Layout: `derived.rs` (the memo and one journey's derivation), `projections.rs` (every derived read, node detail, explanation pages, history). Reads take a `Call` (today and the viewer) and answer `Projected<T>` ([`decisions/2026-10-06-derived-reads-are-memoized-by-everything-the-derive-reads.md`](../decisions/2026-10-06-derived-reads-are-memoized-by-everything-the-derive-reads.md)); a journey that does not exist or a query naming a node it does not hold is a `ReadError`, a failure of the store or an engine panic is `ReadError::Failed`.
- Memo bound: 8 derivations (`MEMO_ENTRY_COUNT_MAX`), least recently read dropped first. A derivation at the limits is a 2,000-node graph and its derive, tens of MiB, so the worst case stays within a few hundred MiB; a small team's open journeys, viewer by viewer, still hit. It is an internal bound of the memo, not a PRACTICES limit: no request can push past it.
- Node detail (C8) carries the node, its path, parent, and children with their states, its stored record, local edits, answer, pin, overrides, notes and links, and its `NodeDerived` with explanation lists cut to `explanation_entry_count_max`; the engine's per-node projection (`Derived::node_derived`, private before) is now public so a detail read projects one node rather than all of them (an edit outside `crates/service`).
- History pages by the store's log position rather than the engine's cursor: the store already pages events by `page_item_count_max` and finds a node's events by every record they wrote, so the service groups one store page by patch (`cairn_engine::history`) and hands back the store's next position. A history total would need a count query the store does not have, so none is given.
- Proposal operations take the destination with the proposal id (the API names both in the path) and a client patch id each, so a lost response is answered from the receipt (H5). `ProposalWritten` answers a create, edit, or discard: `Saved` with the proposal read back, `AlreadySaved` with the receipt, `Existing` for a resubmitted create ([`decisions/2026-10-06-an-upgrade-or-re-link-reaches-a-journey-only-through.md`](../decisions/2026-10-06-an-upgrade-or-re-link-reaches-a-journey-only-through.md)). `ProposalReview` is the engine's `ProposalPreview` with the proposal, the consequences by journey (from the preview for a journey; for a deployment proposal, one more apply and `consequence::of` over the journeys its merges were checked against; none for a route), and the stale base with what intervened. The preview derives for no viewer, as a patch's consequences are ([`decisions/2026-10-06-what-a-domain-patch-reports-and-when-it-is-worked-out.md`](../decisions/2026-10-06-what-a-domain-patch-reports-and-when-it-is-worked-out.md)).
- The loader loads each proposal a patch edits or applies, and reads what an applied proposal's drafted mutations read (route versions, merge journeys) as if the patch held them; an upgrade loads both the version the journey follows and the target (the readiness ruling), and a route patch that opens or publishes a draft loads the route's latest version and the version its draft extends (what 2.7's review fixes ask of the host). An applied proposal's reviewed revision is a commit precondition. A proposal write ticks the proposal, never its destination; an apply ticks the destination and the proposal.
- `crates/api/tests/openapi.rs`: the I1 coverage test lists this brief's operations as awaiting their endpoints (4.9 moves each to its endpoint and empties the list), an edit outside `crates/service`.
- Layout: `drafting.rs` (propose upgrade, save as route, re-link; refresh), `routes.rs` (import, export, the patch-id key allocator). Drafting loads through `load::drafting` (the deployment, the journey, the route it saves to with its latest version, and the versions the draft reads); a draft that cannot be made is `ProposeError::Draft` with the engine's `DraftError`.
- Export names the version it extends: the version itself (an edited export imports as a new draft of it), or the draft's `extends`. Import matches against the version the file names as extended, or the route's latest when it names none; a version it names that does not exist is an invalid rejection (`target_missing`), and a file's own violations are the rejection's list (A15).
- Planted bug: with the confirming user never stamped on a proposal apply's events (`crates/engine/src/pipeline.rs`), `memory::a_proposal_is_previewed_and_applied_with_its_confirming_user` failed with `assertion left == right failed: H2: the confirming user, left: None, right: Some(UserId("u_reviewer"))` (proposals.rs:290); restored, it passes.
- The memo's D6 tests were also checked against a memo keyed by journey and revision alone: both the entity-merge and the midnight case fail, and pass once the key is whole.
- Proof: `briefs/proof/4.8/README.md` shows the vendor evaluation's next list, a proposal's life, and an upgrade to version 2 as before-and-after values.
- Review round 1 (Opus): a resubmitted `apply_proposal` is rebuilt at the destination revision its receipt implies and answered from it (the proposal is no longer open, so the patch built from it differed); `propose_upgrade`, `propose_save_as_route`, `propose_relink`, and `refresh_proposal` look up the receipt (and, for a create, the proposal its author holds) before drafting, so a resubmission after the destination moved is answered rather than refused as a reused id; an import is matched against the route's latest version, which its draft extends, so an older export never brings back a key a later version retired, and a resubmission is rebuilt against the versions newest first; `history` of a journey that does not exist is `ReadError::JourneyMissing`. Each has a test over both stores.
- Review round 2 (Opus): a drafted proposal write resubmitted under a used patch id is answered from the receipt only when that id's event created (or, for a refresh, edited from the named base) the same proposal for the same destination and its draft is the same request (upgrade target, re-link lineage, saved journey and route); a held proposal answers a new patch id only on the same terms. An import resubmission reads the version its draft extended from its import event and rebuilds once, and a store or engine failure while rebuilding is answered as a failure, not a reused id. Both have tests over both stores.
