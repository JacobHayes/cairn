## Goal

Make the priority numbers explain themselves and let a patch say what it moved. Two numbers confuse people today: a container shows "gravity up to" its children one level down, which is neither its own gravity nor the largest inside it, and a node with plenty downstream can show zero leverage with no word on why. And a patch reports only warnings, so anything that wants to know what an action unlocked has to diff the frontier itself, which can credit another person's concurrent change to this one. The formulas do not change.

## Governing

- PRD: Priority (the container bullet: subtree gravity; leverage and its targets), C2 (subtree gravity on containers), C8 (the dependents a node would not yet free), D7 (the informational half), C11 (the unlocked set feeds pass order), I5 (direct writes reported with consequences), Core concepts (Consequences, Leverage).
- ARCHITECTURE: Engine > Read path: derive (pass 6), Write path: apply (`consequences`), Projections (`explanations`), HTTP API, MCP endpoint, Generated artifacts.
- PRACTICES: Explicit limits (explanation lists are capped and paged); Code conventions.

## Scope

In:
- `subtree_gravity` on a container's derived values and the level's roll-up replaces `max_child_gravity`: the counted weight of the container's whole area, the container and its open, in-scope descendants plus everything downstream of any of them, each node once (`decisions/2026-10-09-a-container-shows-the-gravity-of-its-whole-area.md`). The wire keeps `max_child_gravity`, marked deprecated in OpenAPI, until a later breaking release.
- `still_waiting` on node detail (the explanation projection, not every node's derived values): each direct dependent this node would not free, with what else it waits on (a requirement, a condition gate on an unanswered decision, a stage opening, an ancestor's requirement), an explained list capped and continued through the existing explanations endpoint.
- Consequences gain three informational lists, never warnings: `unlocked` (newly on the acting frontier), `out_of_scope` (newly not relevant), and `into_scope` (newly relevant or undecided), computed from both sides at the same revision and today, in every patch and proposal-preview response on every transport (HTTP, MCP, the assistant's reports, the in-browser host).
- `GET /api/journeys/{id}/nodes/{key}` and MCP `get_node` carry `still_waiting`.

Out: the gravity, leverage, and rank formulas and constants (normalizing over the frontier was considered and not adopted for now: `decisions/2026-10-09-the-redesigns-open-questions-are-settled.md`); the UI that shows these (8.5 Recent, 8.7 Why this rank, 8.8 the Signals lens, 7.1 pass order); answer effects (8.3).

## Acceptance

- Behavior by id: Priority (a container's subtree gravity counts a dependent shared by two children once and is at least every member's gravity; a node's own gravity unchanged), C8 (`still_waiting` lists each held dependent and what holds it), D7 (the informational lists; a resubmitted patch id still reports no consequences, H5).
- Over the vendor evaluation: Setup's subtree gravity is at least every open descendant's own gravity; the kickoff milestone's `still_waiting` names each dependent it does not free and the gate holding it; answering the partner decision "no" reports the partner-led nodes as `out_of_scope` and whatever reached the acting frontier as `unlocked`; answering it "yes" reports them as `into_scope`.
- A two-session test: a write by one session that unlocks a node concurrently with another's unrelated write reports the unlock only in the first session's consequences.
- Planted bug: count a dependent shared by two children once per child, and show the shared-dependent test fail.
- Proof: a before-and-after value table for the fixture containers and one consequences example.

## Decisions left to the implementer

- The `still_waiting` entry shape beyond node and blockers (whether it repeats the dependent's weight and owner factor).
- Whether `into_scope` separates relevant from undecided.
