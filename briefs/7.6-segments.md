## Goal

Make a reusable piece of a process a first-class object with as little new machinery as possible. A segment is a route of kind `segment`: versioned, drafted, published, retired, imported, and authored exactly as a route is, but never started, only inserted. It has one root, so an insertion is one subtree you can see, name, collapse, skip, and snooze, wired to the graph it joins through that root. Inserting copies the version's nodes under keys minted from the insertion's key and each segment key, maps its roles and kinds, may leave some nodes out, and adds the wiring edges, all in one mutation. After that the nodes are ordinary: lineage only lets a later upgrade be offered and merged, and an insertion's local edits are its differences from its version, never marked. This brief builds the model and the insert; insertion upgrade is 7.8, and save as segment with linking is 7.9.

## Scope

In, in build order:

- Schema: `RouteKind` on the route header, the route file, and `create_route` (absent means `process`); `InsertionKey` (`i_`), `Insertion`, and `Graph.insertions`; `Provenance::FromSegment`; `Mutation::InsertSegment` (client-minted insertion key, segment version, parent, optional root id and title, role and kind choices, `omit`, and wiring edges named by segment key and host key); the `segment_inserted` event; `Subject::Insertion`; the violation codes `segment_rule`, `insertion_invalid`, `insertion_key_taken`, and `not_a_process_route`; the store records and the touched set.
- Engine lifecycle: `create_route` stores the kind. A validation stage applies the segment rules to any graph of a segment route, and publishing requires exactly one root. `create_journey`, lineage, `relink`, and `save_as_route` refuse a segment; a journey created from a route removes the insertions its version held. Import matches the file's kind to the route.
- The insert handler: admit, map roles and kinds (`owner` maps to `owner`), copy under minted keys (FNV-1a over the insertion key and segment key, shared with import; a key the graph holds or retired rejects), translate every reference, place and name the root, add the wiring edges, set initial `from_segment` states in a journey, and record the insertion. Mapping mistakes are ordinary violations of the final candidate, with no special checks. Removing members drops them from the insertion, and removing the last removes it.
- Stores: an additive Turso migration (a `kind` column defaulting to `process`; an `insertions` table indexed by segment and version), the memory backend, and a conformance round trip.
- Service and API: load the named version for apply; `kind` on route summaries and a `kind` filter on the route index; route detail lists each version's insertions (host, root title, upgrade available); regenerate OpenAPI and the client.
- Agent surface: `list_routes` and `get_route` carry `kind`; insertion goes through `create_proposal`, with an example in its description; a "Reuse a segment" section in `instructions/SKILL.md` and a worked example in `instructions/workflows/insert-segment.md`.
- Fixture: `fixtures/security-review/segment.yaml`, a group root holding *Data sensitivity?*, *Threat model* (relevant unless sensitivity is low, owned by `reviewer`), and *Who reviews?* (fills `reviewer`), with a scenario inserting it twice into a hiring-loop journey; its README entry records the minted root paths and the frontier after insertion.

Out: insertion upgrade (7.8); save as segment, linking, and the merge guard on `from_segment` nodes (7.9); the screens (7.7); dedicated MCP segment tools; the nesting test; save as route listing the insertions it drops (they are dropped silently here, their nodes kept); binding and parameters (PRD Later).

## Acceptance

- A21: a segment draft with `final`, with `default_owner`, or with a second root is rejected with paths; publishing an empty segment draft is rejected; `create_journey` from a segment is rejected.
- B13: two insertions of one version into one journey get disjoint keys, distinct root ids (`security-review`, `security-review-2`), `from_segment` provenance, and initial states; a role defaulting by id resolves participations through the journey's role; mapping onto a role that already has a filling decision is rejected, and the same patch with `omit` is accepted; a cardinality mismatch is rejected; the edges land in the same patch, and a cycle-closing edge rejects the whole insert; an insertion into a route draft survives publish, and a journey created from that version has `from_route` nodes and no insertion; removing every member removes the insertion.
- A13: a segment exports with `kind: segment` and round-trips; a route holding an insertion exports and imports its nodes as plain nodes.
- J3: the scenario "segment insertion twice into one graph" replays field by field. H5: an insert against a stale journey revision is rejected naming the touched set.
- C19 read: route detail of the segment lists both insertions under v1, and `kind=segment` filters the index.
- Store: an insertion round-trips in both backends, and a database migrated from the previous schema keeps its route (kind `process`) and journey.
- Planted bug: copy segment keys unchanged instead of minting, and show the second insertion rejected by the key-uniqueness invariant.

## Decisions left to the implementer

- The name of the shared FNV mint helper.
- Whether the segment rules are a new validation stage or part of structure validation.

## Decision log

- The shared mint helper is `fnv1a_body` in `crates/schema/src/id.rs`: import's key allocator
  and the insertion's `mint` both call it, so the two cannot drift.
- The segment rules are a validation stage of their own (`stages/segments.rs`), run on every
  graph of a segment route a patch wrote; publish adds the exactly-one-root check.
- The migration is `0007_segments.sql` (0005 and 0006 were taken). It widens the `provenance`
  check on `node_states` by rebuilding the table, since a CHECK cannot be altered.
- `insert_segment` touches its whole domain for H5 (the coarse default for a mutation whose
  keys are minted by the engine): a stale insert is rejected whenever the domain moved, which
  is safe and only stops an automatic retry.
- The service loads the segment's route header with its version, so apply can check the kind
  and the retired flag; the web host's route index asks for processes only until the segment
  screens exist.
- A mapping that cannot be made (a named role of the wrong cardinality) stops the insert before
  the copy, so it reports that violation alone; mistakes the copy makes are the final
  candidate's, found by the one pipeline.
- A route's `kind` is never rewritten: the store keeps the column set at creation.
- A role or participation kind an insertion maps onto keeps its cardinality while the
  insertion is there (an edit that flips it is refused as `insertion_invalid`), since the
  segment version that fixed the mapping is not loaded on every role edit.
- Deferred, as the brief lists: insertion upgrade, save as segment and linking, the dedicated
  MCP segment tools, the nesting test, and save as route naming the insertions it drops.
