# 8.1: Display state

| | |
|---|---|
| Id | 8.1 |
| Crates or packages | `crates/schema`, `crates/engine`, `crates/mcp`, `instructions/`, `fixtures/`, `openapi/`, `web/client`, `web/app` (one module) |
| Depends on | 2.6 |

## Goal

Give every node one state that every surface shows, derived once in the engine. Today only groups get a derived display state; every other surface prints stored state and the browser patches it in four places, so a decision ruled out by another decision's answer still says "open". The display state (D8) composes relevance, stored state, effective skip, auto-reach, blocking, and snooze in one precedence, and travels to the API, the snapshot, MCP, and the browser beside stored state, leaving every existing field meaning what it meant.

## Governing

- PRD: D8 (values, precedence, the container rule, the pending rule, secondary detail), D3, D1 (group paragraph), E1 (`unassigned` narrowed), I3 (`by_display_state`), C8 (the pending cause), C18, Core concepts (Display state, Undecided, Group), Gating (a decision that is itself undecided is unanswered), B2 (recorded state is kept).
- ARCHITECTURE: Engine > Read path: derive (passes 1 and 7), Projections, Generated artifacts.
- PRACTICES: Bounds and assertions; Testing > Engine: examples, properties, replay; Code conventions.

## Scope

In:
- `DisplayState` in `crates/schema` (`ready`, `active`, `blocked`, `conditional`, `scheduled`, `snoozed`, `done`, `skipped`, `not_relevant`), a field of each node's derived values beside the D3 flags, which stay booleans: the composite is read from them and replaces none.
- The precedence, the container rule, and the pending rule, computed last in the derive, once blocking, skips, and snoozes are known; the group rule moves there from the level projection. `RelevanceExplanation` gains `pending_on`: the undecided decisions a not-relevant value rests on, found by re-evaluating the node's and its ancestors' conditions with those decisions read as unknown instead of unanswered. Relevance itself is unchanged.
- Wire fields, all additive: the node row and the level node gain `display_state` (the level's `group_state` stays, equal to it on groups, marked deprecated in OpenAPI); the status summary and the snapshot's counts gain `by_display_state` beside `by_state`, which stays and is not deprecated. OpenAPI and the TypeScript client regenerated.
- `unassigned` derived only for non-group nodes that are in scope (relevant or undecided) and unfinished.
- MCP tool descriptions and `instructions/`: read `display_state` and `by_display_state` for "what is this node's status", stored `state` for "which transition applies", using the words below.
- `web/app/src/status/words.ts`, a pure module with its unit test and no screen changes: the display word per value and kind (deliverable or action / decision / milestone / container): ready is READY / TO DECIDE / READY / NOT STARTED; done is DONE / DECIDED / REACHED / DONE; scheduled applies to milestones only; every other value is its own name in capitals (ACTIVE, BLOCKED, CONDITIONAL, SNOOZED, SKIPPED, NOT RELEVANT). OPEN, TODO, and PENDING stay stored-state names only.
- `fixtures/README.md` gains the display state of the fixture nodes it already tabulates.

Out:
- Screens reading the new field: 8.6 to 8.10 adopt it and remove the browser's own composition (`canvas/journey.ts`, `detail/sections.tsx`, `detail/model.ts`, the rows reading stored state).
- `snoozed_via`, which 7.4 adds; display state reads only whether a snooze holds.
- Any change to relevance, gravity, leverage, blocking, or guards for pending nodes.

## Acceptance

- Behavior by id: D8 (a scenario per precedence row), D3, E1, I3, C18.
- Scenarios over the vendor evaluation: answering the partner decision "no" makes the partner-led nodes `not_relevant`, and one with recorded progress keeps its stored state as secondary detail; the test plan with a started child action is `active`, not `blocked`; a container waiting only on its own children with nothing started is `ready`; a snoozed frontier node is `snoozed`; a skipped group's descendants are `skipped`; finished work later made undecided is `done` with "may not apply". The hiring loop and product launch get the same per-row checks where their structure allows (an `auto_reach` milestone with its date ahead is `scheduled`).
- A route-file variant of the vendor evaluation adds a follow-up decision relevant only when a partner runs the testing and a deliverable gated on the follow-up's answer (the variant 7.1 uses): before the partner decision is answered, the deliverable is `conditional` with `pending_on` naming the follow-up, and its relevance is still `not_relevant`; answering "yes" makes it `conditional` with no pending; answering "no" makes it `not_relevant`.
- `by_state` is byte-identical to before on every fixture; snapshot counts agree with the next list; every existing wire field keeps its value (a fixture comparison of the wire before and after, apart from the added fields).
- Planted bug: put `done` above `not_relevant`, and show the recorded-progress scenario fail.
- Proof: a table of about eight fixture nodes with stored state, what the screens showed before, and display state after.
