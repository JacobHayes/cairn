## Goal

Proposal review as a diff over the canvas and as an editable list, with a local preview of the resulting frontier, apply, discard, and the stale-base refresh; and the flows that create proposals: upgrade, save-as-route, re-link, and breakdown. This brief also adds their entry points to earlier screens.

## Governing

- PRD: C14, B7, B8, B9, B10 (break down opens a proposal), A18, I6, C17.
- ARCHITECTURE: Web UI (Previews); Engine > Upgrade, save-as-route, re-link; Engine > Model (Proposal).
- PRACTICES: Code conventions (TypeScript).

## Scope

In: proposal screens for every destination (journeys, routes, the deployment, and a journey or route the proposal creates at revision 0), with the frontier preview only for journeys; `ProposalEditor` over 2.7's documents using 5.6's editors and 5.1's date resolver, previewing through wasm `preview` and drawing on 5.2's `CanvasOverlay`; the upgrade, save-as-route, and re-link flows with entry points on 5.5's overview; "break down" on 5.3's triage card and on 5.1's panel.

Out: producing proposals server-side (2.7, 4.8, 4.4); the assistant panel (5.8).

## Acceptance

- Behavior by id: C14 (every item type editable; preview shows the resulting frontier), B7, B8, B9, B10, A18, I6 (a stale proposal shows the intervening events and blocks apply until refreshed and re-reviewed).
- Playwright over the fixture's version 2: upgrade the scenario journey, resolve each conflict type, apply; save the routeless fixture journey as a route with a mapping and re-link it; break down the placeholder from triage.
- Planted bug: allow apply without re-review after a refresh and show the I6 test fail.

## Decisions left to the implementer

- Diff presentation; conflict resolution controls.

## Decision log

Appended by the implementer.

- Proposal review lives at `/proposals/<id>`; the flows open it on the proposal they drafted. There is no list of a journey's open proposals: the API has none, so a proposal is reached by its link.
- Diff presentation: the canvas draws the graph after with what the proposal removes put back in place, every kind shown, and marks each touched node added, changed, removed, in conflict, orphaned (kept or removed), or left out (5.2's `CanvasOverlay`, a new `marksOverlay` that lights without dimming). Beside it, the diff as a list (fields named per node, edges), the frontier after for a journey with what joins and leaves it, and the violations, a contradictory chain with 5.1's resolution moves, each added to the proposal.
- Conflict controls: one radio per resolution the conflict offers, with a role, a kind, or each removed choice's replacement picked inline; an orphan is kept or removed, its cascade listed when removed; an entity maps to drop, the default owner, an existing role, or a new role named inline; an exclusion is a checkbox. Mutations are listed in words with Edit (an added node with 5.6's field groups, condition and date-rule editors; a set field's value; a pin's date; an answer with 5.1's input) and Drop; a node, a removal with its cascade (5.6's `planRemoval`), and an edge can be added.
- The reviewer's unsaved edits and their confirmation are kept per tab across reloads; edits are saved against the revision they started from (H5), and a stale save shows what moved.
- Break down: a placeholder's triage card and any deliverable or action's node detail take the pieces' kinds and titles, then open a proposal adding them beneath it; the node detail's flags section opens for a placeholder that needs breaking down, where the control sits.
- Upgrade, save as route, and re-link sit on the overview: the versions newer than the journey's, a route id (its own route's by default) and name, and a published route and version.
- Earlier work changed: `actsFor` offers `breakdown` first for a placeholder (5.3); the overview gains the flows (5.5); node detail's flags section gains break down (5.1); 5.1's answer input is exported; the host gains `proposals` and the deriver `preview`; the in-browser root gains the proposal calls (`crates/wasm`, `web/wasm`); the ARCHITECTURE line on the in-browser host names proposals.
- Calls that matter: `decisions/2026-10-07-a-journeys-proposal-is-previewed-in-the-tab-as-edited-any.md`, `decisions/2026-10-07-applying-a-proposal-needs-the-reviewers-confirmation.md`, `decisions/2026-10-07-the-browser-test-resolves-each-conflict-the-fixtures-version.md`.
- Planted bug: a refresh that carries the confirmation over (`reviewedAfter` returning the refreshed revision); I6's test failed: `FAIL src/proposals/model.test.ts > reviewedAfter (I6) > asks for a renewed review after a refresh: the refreshed proposal does not apply until marked again AssertionError: expected [] to deeply equal [ 'unreviewed' ]`, and the browser's stale test with it.
- From review: every node field a proposal sets has its editor (5.6's choices editor and the field's value as a form writes it are exported for it), and an editor follows its change: it starts again from the proposal when its value is replaced by anything but its own edit, and keeps its change's name when others are dropped. An editor holding a value with a problem holds saving and applying. A candidate that breaks a rule shows no diff rather than every node removed; a deployment proposal has no graph to draw. A stale route or deployment proposal lists each record that moved. A draft whose answer was lost is sent again under the same ids while it asks the same.
