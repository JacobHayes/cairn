# 4.3: MCP server and shipped instructions

| | |
|---|---|
| Id | 4.3 |
| Crates or packages | `crates/mcp`, `instructions/` |
| Depends on | 4.9 (shares 4.2's auth layer and conventions; its tools need 4.8's projections and proposals) |

## Goal

The remote MCP endpoint: Streamable HTTP at `/mcp`, an OAuth resource server on 3.2's layer, a curated tool set over the service with bounded outputs, and the shipped instructions served as MCP metadata and published as `SKILL.md`.

## Governing

- PRD: I2 (the minimum tool surface), I3, I4, I6, I7, A12.
- ARCHITECTURE: MCP endpoint (the tool list); Assistant (the same tools in-process).
- PRACTICES: Explicit limits (top-N and pages on every list output); Simulation (`sometimes!` for a paged continuation).

## Scope

In: every ARCHITECTURE tool with a schema from 1.2, 4.1, and 4.8 types, an agent-facing description, and bounded output, each mapping to one service operation; `ToolSet::call(actor, name, arguments)` for in-process use; `instructions/` covering route authoring in conversation, structuring an empty journey, walking decisions, proposing breakdowns, recording answers, summarizing the frontier, resolving a date conflict, and handling a stale proposal; mounting `/mcp` in 4.2's router.

Out: the assistant loop (4.4); code mode.

## Acceptance

- I2 (a coverage test maps every I2 capability to a tool), I3, I4 (instructions are served and name only tools that exist), I6, I7 (an agent-token call records agent and user), A12.
- The PRD success criterion as a scripted test: over the vendor evaluation, an MCP client starts a journey, answers the open decisions, proposes a breakdown for the placeholder, and its acting frontier equals 2.6's `next`.
- Planted bug: drop paging from `list_frontier` and show the bounded-output test fail.

## Decisions left to the implementer

- Tool argument shapes below the service's needs; error wording for agents; instruction structure.

## Decision log

Appended by the implementer.

- Tool shapes. Every write takes a `patch_id` the agent mints and the `base_revision` it read, flat beside its own arguments; resubmitting the same id is answered from the receipt (H5). The journey state tools are one mutation each (`answer_decision`, `transition_node`, `assign` with an absent `source` clearing, `snooze`, `unsnooze`, `set_date` pin / shift / unpin / actual, `override` apply / remove); a write naming entities takes the optional `deployment_revision` E6 asks for. `open_draft` creates the route first when given `create`; `import_route` takes the file as YAML text; `manage_entity` reads the journeys a merge must name from the journey index; `edit_proposal` replaces, discards, or refreshes; `apply_proposal`, edits, and discards read the destination off the stored proposal.
- `list_frontier`: with no `filters`, the acting frontier (the service's `next`, ranked, with `mine`, `kinds`, `within`, and `for_viewer`), paged by the tool at the page limit with a total and a cursor; with filters, the list's flags (`mine` joins them) in rank order, paged by the list's own cursor. Both read at the same revision continue where the last page stopped ([`decisions/2026-10-06-how-the-snapshot-scopes-pages-and-agrees-with-the-next-list.md`](../decisions/2026-10-06-how-the-snapshot-scopes-pages-and-agrees-with-the-next-list.md)).
- Bounded outputs, all at the page limit (200) with totals, adding no limit: a level's nodes (edges are those touching the page), a node's children and notes, a route's nodes and versions, search hits per journey, a proposal review's frontier. Node detail's explanation lists are the service's (50 largest) and `get_node` with `explanations` pages the rest. A proposal's mutations are bounded by the mutation limit and shown whole; its review leaves out the graph after (read the snapshot once applied).
- Errors. A tool error the agent can act on is the tool's result with `isError` and the error as structured content: `arguments` with the path, `rejected` with the rejection unchanged (A15), `not_found`, or `refused`. An unknown tool and a server failure are JSON-RPC errors. `resolve_date_conflict` accepts only the move kinds a chain lists ([`decisions/2026-10-06-chains-gain-answer-and-today-fixers-resolution-moves.md`](../decisions/2026-10-06-chains-gain-answer-and-today-fixers-resolution-moves.md)).
- Instructions: `instructions/` is the skill as published, `SKILL.md` (front matter, the loop, revisions and errors, direct writes or proposals, ids, the tool map) and one file per workflow under `workflows/` with a `description`. The server sends the guide without its front matter as its initialize instructions and serves each workflow as a prompt by its file name. `crates/mcp/tests/instructions.rs` checks every identifier the files write as code against the tool names and every field and value in the tools' schemas, and that the guide names every tool.
- Tests: the tool set's own tests (`crates/mcp/tests`, rung 2) call `ToolSet` over the memory store; the endpoint's (`crates/api/tests/mcp.rs`, its own suite `MCP in process` in rung 4) drive `/mcp` with rmcp's client, whose Streamable HTTP transport is a small client handing each request to the API's router (`tests/support/mcp.rs`), so auth and limits are in the path without a socket.
- Edits outside `crates/mcp` and `instructions/`: the route index in `crates/service` (`reads.rs`, one `pub use`) and `crates/api` (endpoint, wire types, OpenAPI operation, tests), regenerated `openapi/` and `web/client/generated/`; the mount in `crates/api/src/lib.rs` and the `rmcp` client in its dev-dependencies; `World::router`, `World::start_without_mcp`, and `TestClock::now` in the API's test support; the MCP suite in `mise-tasks/check/4`; ARCHITECTURE (MCP endpoint paragraph, the crate graph's `mcp --> api`), three files in `decisions/` ([`decisions/2026-10-06-the-mcp-endpoint-is-stateless-json-inside-the-apis-router.md`](../decisions/2026-10-06-the-mcp-endpoint-is-stateless-json-inside-the-apis-router.md), [`decisions/2026-10-06-the-tool-list-carries-the-mutation-vocabulary-once-and-no.md`](../decisions/2026-10-06-the-tool-list-carries-the-mutation-vocabulary-once-and-no.md), [`decisions/2026-10-06-a-route-index-joins-the-service-and-the-http-api.md`](../decisions/2026-10-06-a-route-index-joins-the-service-and-the-http-api.md)), the 4.3 row in `briefs/README.md`.
- Planted bug: `list_frontier` answering the whole frontier (`rows: Paged { .., next: None, items }` for `rows: page(items, cursor)`); `tests/tools.rs` `the_frontier_is_paged_at_the_limit` fails with `left: 225, right: 200`; restored, it passes. `briefs/proof/4.3/prove.sh` repeats this in a tree copy.
- Review round 1 (Opus): a merge resubmitted under its patch id is matched by what it merges, in the service's receipt check (`write.rs`, `merged_as`), since its journey list is read from the index when drafted and moves with the journeys (the API's deployment patches get the same answer); tool metrics label a name no tool has `unknown`; only write tools run on their own task, so a timed-out read stops with its request; each write's `destructiveHint` is set by whether it can undo or overwrite, and every write is `idempotentHint` under its patch id; a node's children and notes and a route's versions continue from `children_cursor`, `annotations_cursor`, and `versions_cursor`, while search hits and a review's frontier answer their first page and a total with no `next`, saying where the rest is read; the `Host` allowlist for the whole router is in 4.7's scope and acceptance ([`decisions/2026-10-06-dns-rebinding-protection-is-a-host-allowlist-in-front.md`](../decisions/2026-10-06-dns-rebinding-protection-is-a-host-allowlist-in-front.md)).
