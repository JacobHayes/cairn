# Proof for brief 3.1: the store

Generated by `briefs/proof/3.1/prove.sh WORK_DIR`; do not edit by hand. The script fails if
any outcome below differs from the one expected.

What this shows: the store persists what an accepted patch produced, whole or not at all,
and answers from it. Each section below runs against a Turso database file through the
`Store` trait (`cargo run -p cairn-store-turso --example store_proof`); the change sets are
built by hand, as an engine would produce them, since the store has no engine dependency.
The conformance suite then runs the same cases against both backends, each counted on its
own, and a planted bug in the memory backend is caught by it.

## A revision conflict

Two patches to `j_every`, both against revision 1. The first commits and produces revision 2; the second is rejected, naming the revision that moved and the touched set of the events since (H5), so a client can retry on its own when its own touched set does not overlap:

```json
{
  "rejection": "stale",
  "conflicts": [
    {
      "of": {
        "domain": {
          "journey": "j_every"
        }
      },
      "expected": 1,
      "current": 2
    }
  ],
  "intervening": [
    {
      "in_graph": {
        "graph": {
          "journey": "j_every"
        },
        "key": {
          "node": "n_first"
        }
      }
    }
  ]
}
```

## An entity create riding in a journey patch

A patch to `j_every` creates entity `e_new` with no deployment revision check: the journey moves to revision 3, and the deployment from revision 0 to 1. A second create of `e_new`, riding in the next patch, is rejected:


## A create at a hard-deleted journey's id

`j_every` is hard-deleted (its events go with it; the deployment log keeps the deletion), and a create at its id is then rejected:

```json
{
  "rejection": "invalid",
  "violations": [
    {
      "code": "deleted_journey_id",
      "at": {
        "subject": {
          "journey": "j_every"
        }
      },
      "message": "journey j_every was deleted, and a deleted journey's id is never reused"
    }
  ]
}
```

## An oversize commit names the limit

A patch adding 300 nodes with 60,000-byte descriptions to `j_big` would take its graph past 16 MiB; it is rejected, naming the limit:

```json
{
  "rejection": "invalid",
  "violations": [
    {
      "code": "limit_exceeded",
      "at": {
        "subject": {
          "journey": "j_big"
        }
      },
      "message": "Journey(JourneyId(\"j_big\")) would be 18024691 bytes serialized, past graph_bytes_max (16777216)",
      "limit": "graph_bytes_max"
    }
  ]
}
```
