# 4.1: Service layer, composition root, capabilities, notifier

| | |
|---|---|
| Id | 4.1 |
| Crates or packages | `crates/service`; the `Notifier` trait and its in-process implementation in `crates/store` |
| Depends on | 2.4, 3.1 |

## Goal

The one caller of the engine, for everything the engine already offers: resolve who is calling and which entities they are, answer a resubmitted patch from its receipt, load what a patch reads, apply it, report its consequences, commit, and notify. It owns the wiring between engine and store for domain patches (journey creation, status, and hard delete; route drafts and versions; entity create, edit, and merge as deployment patches), the conflict shape, the notifier, the capabilities document, and the composition root types every host fills in. Priority, projections, proposals, and route files join with 4.8, once the engine has them (DECISIONS.md: the service and API split at the engine's 2.4 boundary).

## Governing

- PRD: A11, A12, A17, A19, B1, B11, D7, E6, H2 (the actor), H3, H5 (the service half), H6 (the service half); Non-functional: Journey durability (publishing never touches journeys).
- ARCHITECTURE: Service layer and composition; Storage > Concurrency and notification; Engine > Write path; Terms (Composition root, Capabilities document, Notifier, Host); Assumptions (today per request).
- PRACTICES: Errors, panics, and rejections (engine panics caught here); Explicit limits (SSE subscribers, SSE coalescing interval); Simulation (`sometimes!` sites).

## Scope

In:

- `Service<S: Store>`, generic over the store (its trait is not object-safe, DECISIONS.md 3.1) with the notifier as a trait object; the composition root types (the parts a host assembles, the deployment's time zone and rank constants, the capabilities document); runtime-free, building for `wasm32-unknown-unknown`, checked in rung 1.
- A call context carrying the actor (H2) and the request's clock; today is computed once per call in the deployment's time zone (Assumptions).
- The viewer's entities from the user's verified emails (H3).
- Domain patches: receipt first (H5), then a loader that assembles the engine's `Records` from store loads (the target, the deployment, the route versions the patch reads, and for an entity merge the journeys referencing either entity), `apply`, D7 consequences derived before the commit for the patch's journey and for each journey an entity merge was checked against, the commit with its preconditions (the deployment revision a journey patch names; a merge's journeys and the set referencing its entities), a stale rejection completed with the intervening touched set, and a tick for every revision the commit moved.
- Subscriptions seeded with the current revisions, so a commit between a fetch and a subscription is never missed (H6); the in-process notifier coalescing per domain, with the clock and timer as inputs.
- Store-backed reads: a journey, a route with its draft, a published version, the deployment, the journey index, route detail, text search, events, and entity resolution.

Out: priority and every projection, memoized derived reads, proposals and their lifecycle, upgrade, save-as-route, re-link, import and export (4.8); the domain document (4.2, moved from 2.6); HTTP (4.2); MCP (4.3); the assistant loop (4.4); configuration parsing and the concrete root (4.7); auth providers (3.2).

## Acceptance

- Behavior by id: A11 (a second draft is rejected with the discard option; publishing never touches journeys), A12 (the same mutations from a user and from their agent land identically but for the stamp), A17 (a journey and a route are created at revision 0), A19 (a hard delete, and a create at the deleted id rejected), B1, B11, D7 (consequences on every accepted journey patch and for each journey an entity merge was checked against; none on a resubmission), E6 (a merge that would make a contradictory chain relevant in a referencing journey is rejected naming it; a journey edited, or newly referencing either entity, after the check makes the merge stale), H3 (a verified email matches its entity and an unverified one never does; an email already on another entity is rejected; a merge moves emails to the survivor; a user matching two entities gets both, with a merge offer; emails match case-insensitively), H2 (actor and agent stamped on every event), H5 (a subtree removal conflicts with an edit inside it, and its safe retry after an insertion beneath it is rejected rather than widened; the stale rejection carries the intervening touched set; a lost-response resubmission by patch id, after another patch advanced the revision, is answered from its receipt and never re-applied), H6 (every commit publishes, including a deployment revision moved by an entity create riding in a journey patch; a late subscriber still learns the revision; ticks coalesce per domain within the coalescing interval).
- The write path runs over both stores; a property test holds that `apply`, then `MemoryStore::commit`, then `load` gives what `Records::write` gives.
- Planted bug: skip the receipt lookup before loading and show the H5 resubmission test fail.
- Notifier coalescing and initial revisions as deterministic tests that pass the clock in (DECISIONS.md: notifier point tests).
- Rung 1 builds `crates/service` for `wasm32-unknown-unknown`.

## Decision log

Appended by the implementer.

- Planted bug: with the patch receipt never looked up, `memory::a_resubmission_after_another_patch_is_answered_from_its_receipt` failed with `left: Err(Rejected(Stale { conflicts: [j_h5 expected 1, current 3], .. }))` against `AlreadyApplied` (writes.rs:184); restored, it passes (`briefs/proof/4.1/`).
- Layout: `compose.rs` (the root types), `call.rs`, `viewer.rs`, `reads.rs`, `write.rs` (receipt, apply, commit, announce), `load.rs` (records and preconditions), `consequence.rs` (D7). Errors: `ServiceError` for the store, the subscriber limit, and a caught engine panic; `WriteError` adds the rejection, mirroring the store's `CommitError`.
- Reads take no `Call`: one deployment is one trust boundary (H4), so nothing a store-backed read returns depends on who asks. The viewer read takes one.
- `DomainPatch` wraps a schema `Patch` that does not target a proposal, plus the optional note `ApplyInputs` puts on each event (J1); the note is not part of the patch's content hash, so a resubmission with another note is still the same patch.
- The loader loads route versions for `upgrade` and `relink` mutations too, since `apply` accepts them in a journey patch today; producing their content (the merge) is 4.8's.
- Each write case is one generic `async fn` run twice by a small macro, once over a fresh memory store and once over a fresh Turso file in cargo's per-target temporary directory; the test deployment's zone is `Etc/GMT+5`, so midnight falls at 05:00 UTC and today differs from the UTC date in the morning.
- Fixture routes are published through the service with one route patch (create, open a draft for an import, the roles, kinds, default owner, and whole nodes, publish), so the store holds the version as the engine built it; the scenario test compares the journey read back with the engine's own run of the same patches.
- The notifier's limits take PRACTICES' names (`SSE_SUBSCRIBER_COUNT_MAX`, `SSE_COALESCING_INTERVAL`) in `crates/store/src/limits.rs`; the browser host's in-process subscribers are held to them too.
- Coverage sites: `reachable!` for a resubmission answered from its receipt, a stale patch completed with what intervened, a patch accepted by `apply` that lost at commit, and a resubmission that raced its original.
- Edits outside `crates/service`: `crates/store` (the notifier, its limits, `Store::intervening` with its conformance case) and `crates/store-turso` (`intervening` over its existing query), both logged in DECISIONS.md; rung 1 gains the wasm32 build of `crates/service`, and PRACTICES' rung table says so.
- Review round 1 (`gpt-6.1-sol`): a journey patch whose conditions compare entities is now held to the deployment revision it was loaded at (DECISIONS.md); a stale answer rechecks the receipt first, so a duplicate whose original committed meanwhile is answered from it; the deployment is announced only when an entity write moved it, at the store's revision (a hard delete moved the engine's but not the store's); and a subscriber's first take is complete (`Take::Current`, DECISIONS.md). The planted bug now skips both receipt lookups, since the stale-branch recheck alone would answer the resubmission.
- Review round 2 (`gpt-6.1-sol`): when the deployment revision cannot be read back after a riding entity create, the engine's computed revision is announced rather than none; and a seeded first take is ready (and wakes its waiter) even when nothing watched exists.
