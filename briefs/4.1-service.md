# 4.1: Service layer, composition root, capabilities, notifier

| | |
|---|---|
| Id | 4.1 |
| Crates or packages | `crates/service`; the `Notifier` trait and its server implementation in `crates/store` |
| Depends on | 2.7, 3.1 |

## Goal

The one caller of the engine: load, derive or apply, commit, notify. It owns the lifecycle rules between engine and store (drafts and versions, journey creation and status, proposals with client ids and two revisions, actor stamping, hard delete, entity edit and merge as deployment patches, and resolving the viewer's entity from verified emails), consequences on every apply and preview, the capabilities document, the notifier, and the composition root types every host fills in.

## Governing

- PRD: A11, A12, A13, A17, A19, B1, B11, D6, D7, E6, H2, H5, H6 (the service half), I6, I7; Non-functional: Journey durability.
- ARCHITECTURE: Service layer and composition; Storage > Concurrency and notification; Engine > Model (Proposal); Terms (Composition root, Capabilities document, Notifier, Host); Assumptions (today per request).
- PRACTICES: Errors, panics, and rejections (engine panics caught here); Explicit limits (request duration, coalescing, subscribers); Simulation (`sometimes!` and `buggify!` sites).

## Scope

In: `Service` over trait objects with every operation the API, MCP, and assistant need, each taking an `Actor`; derive inputs built per call; memoization keyed by domain revision, deployment revision, and inputs; the conflict shape for H5 (the service never retries); the notifier trait and its in-process implementation (per-domain coalescing, initial revisions on subscribe, clock and timer as inputs); the capabilities document; runtime-free, building for `wasm32-unknown-unknown` (checked in rung 1).

Out: HTTP (4.2), MCP (4.3), the assistant loop (4.4), configuration parsing and the concrete root (4.7), auth providers (3.2).

## Acceptance

- Behavior by id: A11 (a second draft is rejected with the discard option; publish never touches journeys), A12 (a patch from any caller lands identically), A13, A19, B1, B11, D7 (consequences on every apply and preview), E6 (a merge that would make a contradictory chain relevant in a referencing journey is rejected naming it; a journey edited, or newly referencing either entity, after the check makes the merge stale), H3 (a verified email matches its entity and an unverified one never does; an email already on another entity is rejected; a merge moves emails to the survivor; a user matching two entities gets "mine" over both and a merge offer; emails match case-insensitively), H2 (agent and confirming user stamped), H5 (a subtree removal conflicts with an edit inside it, and its safe retry after an insertion beneath it is rejected rather than widened; a lost-response resubmission by patch id, after another patch advanced the revision, is answered from its receipt and never re-applied), H6 (every commit publishes; a late subscriber still learns the revision), I6 (each clause, including idempotent duplicate submission by id), I7, D6 (cached and uncached reads are identical across an entity merge and across midnight).
- Planted bug: skip the confirming-user stamp on proposal apply and show the H2 test fail.
- Notifier coalescing and initial revisions as `#[patina_dst::test]`s.
