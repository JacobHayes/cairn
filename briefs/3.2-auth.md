# 3.2: Auth providers, users, identities, agent tokens

| | |
|---|---|
| Id | 3.2 |
| Crates or packages | `crates/auth` |
| Depends on | 3.1 |

## Goal

One `AuthProvider` trait and four providers (dev, OIDC, the built-in OAuth authorization server for MCP clients and agent tokens, Tailscale), plus users, identities, and agent tokens as auth state outside any domain, with the auth log, all stored through 3.1's auth records.

## Governing

- PRD: H1, H2 (the actor this crate produces), H4, I2 (MCP is an OAuth resource server on this layer).
- ARCHITECTURE: Auth (all of it); Storage > Store trait and Schema outline (auth state outside domains).
- PRACTICES: Explicit limits (outbound identity call); Scope and dependencies (configuration surface; dependencies are deliberate).

## Scope

In: the trait with optional provider routers; identity-to-user resolution with verified-email auto-link when configured; the four providers; agent tokens shown once and stored hashed, listed and revoked; the auth log; the axum layer function 4.2 applies.

Out: entity emails and matching a user to an entity (4.1); identity screens (5.5); RBAC.

## Acceptance

- H1 (each provider authenticates in a test), H2 (an agent token yields an actor with the agent set), H4, I2 (an MCP client discovers resource metadata and completes dynamic registration against the built-in server).
- Security: wrong issuer or audience, expired, or badly signed ID tokens are rejected; redirect URIs match exactly and dynamic registration accepts only loopback or https; `state` and the PKCE verifier are bound to the browser session; a failing provider never falls through to a weaker one for the same request; proxy mode is refused off loopback; dev mode is refused off loopback without the override; an unverified email never auto-links; stored tokens are never readable in plain text.
- Planted bug: skip the audience check and show the wrong-audience test fail.

## Decisions left to the implementer

- Crates for OIDC, the authorization server, and the Tailscale local API, each evaluated in the decision log; hand-rolled token validation is not acceptable.
- Session and token formats and lifetimes.

## Decision log

Appended by the implementer.

- Store change (logged per the launch rules): `AuthStore::identities_with_email` finds the identities whose provider verified an email, in both backends with a conformance case; auto-link needs it. Turso answers it with an `EXISTS` over `identity_emails` and no new index: the table holds a few rows per user.
- Schema change: `Identity { provider, subject, display, verified_emails }` joins `cairn-schema` (readiness ruling: the API, MCP, and service layers share it with `Actor`, which 1.2 already defined).
- Crate `crates/auth` (`cairn-auth`): `Accounts` (users, identities, linking, sessions, and later agent tokens) over any `AuthStore`; the `AuthProvider` trait (a trait object, boxed futures); `Auth` (accounts plus providers) with `protect(router)`, the layer 4.2 applies, and `router()`, the routes auth serves outside it. Handlers read the actor as `Extension<Actor>`. The layer is tested on a bare axum router through `tower::ServiceExt::oneshot`, with the peer set as axum's `ConnectInfo`.
- Local means a loopback address (an IPv4 loopback mapped into IPv6 included) or a unix socket (readiness ruling). The listener decides whether a local-only provider starts; the request's peer decides whether it is served. A TCP request whose server recorded no peer is not local.
- Identity resolution takes an in-process lock before it writes (one process serves a deployment), so two first sign-ins of one identity create one user; a known identity whose emails are unchanged, the case of every request through a per-request provider, is answered by one read without the lock. A known identity's verified emails are replaced by what its provider says at each sign-in. Auto-link picks the one user holding an identity with a matching verified email; emails pointing at two users link to neither, and a new user is created. The auth log names an identity `provider:subject` (the subject alone if the pair passes the title limit).
- Secrets: 32 random bytes from `getrandom`, lower-case hex, behind a prefix naming their kind (`cairn_session_`, `cairn_agent_`, `cairn_code_`, `cairn_step_`); the store keeps their SHA-256 digest. Minted user and agent ids are 16 random bytes in hex. The dev token is compared in constant time over digests (`subtle`).
- Lifetimes (`lifetimes.rs`, not limits): a session lasts 14 days from sign-in and is not extended by use; a login or consent in progress, 10 minutes; an authorization code, 60 seconds; an agent token, until revoked.
- Cookies (`cookie` crate): `cairn_session` on `/`, `HttpOnly`, `SameSite=Lax`, `Secure` when the public base URL is https. A refused session cookie is cleared in the 401. Sign-out is `POST /auth/sign-out`.
- The dev provider: with a token, a request presenting it as a bearer token is the dev user and a wrong one is refused; without, every request is. It refuses to start on a listener other machines reach, and refuses requests from other machines, unless its override is set. Its token may not start with `cairn_`, so it never shadows Cairn's own.
- Agent tokens live in `Accounts` (`mint_token`, `tokens_of`, `revoke_token`, `token_actor`); the built-in OAuth provider (`OAuthServer`) is what accepts them as bearer tokens, and it claims every bearer token with Cairn's prefix, so a session token or code presented as one is refused. Only a user mints or revokes, and only their own tokens: an agent cannot make agents. The list shows agent, name, and dates, never the digest. Revoking a revoked token changes nothing and logs nothing. The auth log names a token by its agent id.
- OIDC crate: `openidconnect` 4.0.1 (the one the documents name) with its default features: `oauth2` 5, `reqwest` 0.12 on tokio, and rustls 0.23 with ring and the webpki roots (no OpenSSL, no native TLS); it also brings `rsa` 0.9 (RUSTSEC-2023-0071, a timing leak in private-key operations, which Cairn never performs: it only verifies), `p256`, `p384`, `ed25519-dalek`, and `chrono`. Discovery, the code exchange with PKCE, and every ID token check (signature against the issuer's key set, issuer, audience, expiry, nonce, and the algorithms the issuer advertises, never `none`) are the crate's; Cairn sets only the clock it checks expiry against. Every call to the issuer goes through one client (`outbound.rs`, implementing the crate's `AsyncHttpClient`): it calls only https or loopback origins whatever the discovery document advertises (so the key set and the token endpoint are never fetched over plain http), follows no redirects (the crate's own advice against server-side request forgery), times out each call at `IDENTITY_CALL_DURATION_MAX`, and reads a response body only up to the body limit (64 KiB, the nearest named limit; discovery documents, key sets, and token responses are a few kilobytes).
- OIDC sign-in: `GET /auth/<name>/sign-in?return_to=<path>` and `GET /auth/<name>/callback`. The `state` is stored by digest as login state (with the nonce and the return path) for 10 minutes; the PKCE verifier is the value of a `cairn_sign_in_<name>` cookie scoped to `/auth/<name>`, and only its digest is stored beside the state, so the callback needs both the state and the browser that started the sign-in, and no verifier is ever stored. The state is taken on first use. Discovery runs on each step (two calls), so key rotation needs nothing; a sign-in is rare enough to afford it. The return path must be a path on this deployment. An identity's display name is the token's `name`, else `preferred_username`, else the email, else the subject; its email is listed only when `email_verified` is true. A browser already signed in as a user, by its session or by a provider that signs each request in (Tailscale, the named dev user), links the identity to that user (an agent, or a refused credential, signs in afresh); the browser gets a fresh session in place of any old one. The access token is not used, so its `at_hash` is not checked. An issuer must be https, or http on loopback.
- The OIDC tests run a stub issuer on loopback (axum on an ephemeral port, discovery, a key set, a token endpoint that checks the PKCE verifier) with an Ed25519 key from a fixed seed, so nothing leaves the machine and no private key is committed; the issuer's slow-call timeout is not tested, since a test would wait out the 10 second limit.
- Authorization server: no maintained Rust crate serves dynamic client registration and resource metadata (`oxide-auth` 0.6 has neither and its own storage model), so the endpoints are Cairn's, over `oauth2`'s PKCE helper for the S256 check (compared in constant time) and the store's transient state; the tokens it issues are Cairn's opaque agent tokens checked by digest, so nothing parses or validates a token by hand. Endpoints: `/.well-known/oauth-protected-resource` (and its path-suffixed form, RFC 9728, which the 401's `resource_metadata` names), `/.well-known/oauth-authorization-server` (RFC 8414), `POST /oauth/register` (RFC 7591), `GET` and `POST /oauth/authorize` (the consent page and its answer), `POST /oauth/token`. The issuer is the public base URL without its trailing slash; answers carry `iss` (RFC 9207). Scopes and the `resource` parameter are ignored: a token is an identity.
- Authorization checks run client and redirect URI first (an error page, never a redirect to an unregistered URI), then the request (`response_type=code`, an S256 challenge of the right shape; errors go back to the client), then the browser: a signed-in user (an agent is refused; no session sends the browser to sign in with the configured provider and back). The consent page cannot be framed (`X-Frame-Options`, `frame-ancestors 'none'`), is not cached, and escapes the client's name and redirect URI. A failed token exchange uses up its code. Two registrations with the same name and redirect URIs get the same client id, which is harmless: they are the same client.
- Tailscale local API: `tailscale-localapi` 0.6 was evaluated and not taken. Its whois decodes tailscaled's whole node record strictly (`Created`, `Hostinfo`, `ComputedName`, and more required), so a tailscaled release changing a field Cairn never reads would break every sign-in, and it prints connection errors to stderr from a task it spawns. Cairn makes the one GET (`/localapi/v0/whois?addr=<peer>`) with `hyper`'s HTTP/1 client over a tokio unix stream (both already in the tree under axum and reqwest) and decodes only the login name, display name, and the node's tags; the answer is bounded by the body limit and the call by `IDENTITY_CALL_DURATION_MAX`. A 404 (a peer tailscaled does not know) is refused as a peer; a socket that cannot be reached or a timeout is refused as unavailable, so a request is never served past a failing tailscaled.
- Tailscale modes: direct mode starts only on a TCP listener bound to a tailnet address (100.64.0.0/10 or `fd7a:115c:a1e0::/48`); proxy mode only on a loopback or unix socket listener, and it reads the headers only from a local peer. Proxy headers are ignored in direct mode. A display name `tailscale serve` encoded per RFC 2047 (not ASCII) is replaced by the login rather than decoded by hand.
- The fake tailscaled in the tests listens on a unix socket in `XDG_RUNTIME_DIR` when it is set, else in cargo's `CARGO_TARGET_TMPDIR`: a socket path is limited to 107 bytes and this host's target directory is deeper than that. The socket is removed when the test ends.
- Proof: `briefs/proof/3.2/README.md` describes what each provider signs in and refuses, in plain words.
- Planted bug: telling the ID token verifier not to require the audience (`.require_audience_match(false)` in `crates/auth/src/oidc.rs`) fails `oidc::a_spoiled_id_token_is_refused` (`panicked at crates/auth/tests/oidc.rs:193:13`, `assertion left == right failed: Audience`, `test result: FAILED. 0 passed; 1 failed`); restored, it passes.
- Review round 1 (`gpt-6.1-sol`), fixed in one change on top: the consent page's `form-action` admits the registered callback's origin (browsers hold a form post's redirect to it, so the answer never reached a client on another origin); OIDC calls go only to https or loopback and read at most the body limit, whatever discovery advertises (an http key set or token endpoint elsewhere, or an oversized answer, fails the sign-in); the OIDC callback asks the auth layer who the browser is, so a browser signed in by Tailscale or the dev user links the identity to that user rather than creating another.
- Review round 2 (`gpt-6.1-sol`), fixed in a second change: an OIDC sign-in records the user the browser was when it started, and the callback links only if the browser is still that user (a tab that switched accounts between them is refused); the sign-in's two steps fail when a provider cannot be asked (503) rather than carrying on as if the browser were no one, while a lapsed session cookie still signs in afresh; and an authorization from a browser with a lapsed session cookie clears it and sends the browser to sign in, instead of a 401 every retry repeats.
- Review round 3 (`gpt-6.1-sol`), fixed in a third change: the client secret goes where the issuer's discovery says it takes it (`client_secret_post` when that is all it lists; HTTP Basic otherwise, the specification's default; `openidconnect` assumed Basic); a browser at a sign-in step whose session cookie lapsed is asked again without it, so a provider that signs each request in still names its user (the OIDC link and the OAuth consent), and the answer clears the cookie; the root path's challenge names the unsuffixed resource metadata, which is served, rather than a 404.
