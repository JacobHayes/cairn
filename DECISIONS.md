## 2026-10-07, the log sync fix: nothing is answered from a write until a log sync covers it, and a store that cannot sync fails closed

- Question: 6.2's finding (below). Turso keeps a commit whose logical-log fsync failed: turso_core 0.8.2 marks a failed commit committed once its log record was appended, so memory matches what recovery would replay. The store answered `Failed` yet served the commit's receipt, a resubmission was acknowledged from it, and a crash lost it. What is the simplest design that never answers from a write that may not be on disk?
- Call (`crates/store-turso/src/durable.rs`):
  - A `COMMIT` that fails other than by a conflict or a constraint leaves the store unsettled; those two fail before the log record is written. Nothing is answered until a barrier settles it: a read after it has read, a record write or a commit before it begins, and the failing commit itself. The barrier is a commit of its own, counting in the one row of a new table, `log_barrier` (migration 4), which nothing else writes. (A rewrite of an existing row was tried first: rewriting the migrations table's key made Turso build a temporary database for every barrier.) Its successful log sync covers every record appended before it. One barrier runs at a time, and a count of failures against failures covered keeps a barrier from settling a failure that came after it began. A barrier that meets Busy or a write-write conflict (a checkpoint in progress holds the database) synced nothing and failed nothing: the store stays unsettled, the call errs, and the next call tries again.
  - The failing commit is then answered by what is there: applied when its receipt is (it is now on disk, and the service announces it, H6), failed when not.
  - When the barrier fails too, the store fails closed: every call errs until it is reopened, and a write already in flight then is answered failed rather than applied (its own sync may well have made it durable; a resubmission after the reopen is answered from its receipt). Every open runs a barrier before it answers anything, because a reopened or restarted process reads an unsynced log record back from the operating system's cache. An open whose barrier fails does not open.
  - The memory store already holds the contract: it commits whole under one lock and persists nothing, so a failed commit leaves nothing. The conformance case for a failure injected mid-commit runs on both backends. The Turso cases are in `crates/store-turso/tests/conformance/log_sync.rs`. With one failed log sync, the commit is answered applied, and only after a later sync succeeded. With a failed sync and a failed barrier, every call errs, and the reopened store holds the commit whole or not at all. The same two cases run for a record write (a user), and an open is shown to sync the log before it answers.
  - The durability testbed's leg 6 now requires no violation in the crash sweep under errors, the new oracle `turso-failed-commit-applied-once-synced` to fire, and a failed write to be retried somewhere (that oracle left the campaign's gate: most commits that fail at the log now settle as applied). The barrier at open moved seed 31's faults elsewhere, so leg 6 pins seed 12 instead: its first commit's log fsync fails and a crash at `sync:28` follows. With the fix removed (the failure not counted), that run loses the acknowledged commit; with it, the run completes. The multiplayer testbed lists the new oracle as out of reach: it injects no filesystem faults.
  - [patina] Once the guest removes a directory, no later `--fs-crash-at` point fires: the run ends uncrashed. A barrier on a connection of its own, dropped at the end of the open, removed Turso's temporary directory and left every crash point past the open unfired, so the open's barrier runs on a pooled connection, which keeps it. An in-process reopen still drops the pool, so a run that reopens is not crashed after it (true before this fix too). Recorded in the testbed README; worth a patina issue.
- Alternatives:
  - The service treating a receipt as an acknowledgement only when it is known durable: the store would have to track which receipts are, readers would still see the commit and build on it, and the service cannot tell on its own.
  - Failing closed on every such `COMMIT`, with no barrier: simpler, but a transient `EIO`, `ENOSPC`, or `EINTR` would take the server down until it is restarted (Turso reports `EINTR` rather than retrying, 6.2's Turso entry). It still needs the barrier at open, since a restart reads the unsynced record back.
  - A lock holding every read out while any `COMMIT` runs: closes the window below, but every read would wait on every log sync, against "a long write never blocks readers" (ARCHITECTURE, Backends).
  - A checkpoint instead of a barrier commit: Turso does not say whether a checkpoint writes a transaction left in this state, and a checkpoint truncates the log.
  - Waiting for Turso to roll back a commit whose log sync failed: upstream work, and recovery from the record already in the log would bring the commit back anyway.
- Limits:
  - A barrier makes the earlier record durable under the model patina implements: a failed fsync keeps the dirty data, and a later successful one writes it. Linux may instead drop the dirty pages after a failed fsync and report the next one successful. Then no barrier or later commit makes the record durable, and a record missing from the middle of Turso's log could take later commits with it at recovery. Only Turso rewriting its log tail after a failed sync closes that.
  - On a multi-threaded runtime, a read that begins in the instant between Turso marking the failed commit committed and the store counting the failure can answer from it before it settles.
- What would change it: Turso rolling back or rewriting a log record whose sync failed (then both barriers go). Or evidence that deployments lose records past a failed fsync: then fail closed with no barrier and rely on a supervisor restart and a checked disk.

## 2026-10-07, brief 4.7: the configuration is one TOML file with a fixed set of environment overrides, and only the rank constants default

- Question: ARCHITECTURE asks for "a file plus environment overrides; deployment-specific values have no defaults", and PRACTICES fixes the surface (database path, listen address, public URL, auth providers with their security settings, assistant provider and credential, time zone, rank constants). Which values are deployment-specific, how a variable addresses a value in a list of providers, and what a public URL may be.
- Call: `cairn.toml` holds `database`, `listen`, `public_url`, `timezone`, an optional `[rank]` table, `[[auth]]` providers tagged by `kind` (in the order a request is put to them), and an optional `[assistant]`. The first four have no default: a missing one fails startup naming the key and the variable that can set it, every problem listed at once. The rank constants default to the PRD's (Priority calls them defaults) and are checked at startup: each weight finite and non-negative, the four blend weights summing to one, the undecided discount from 0 to 1, the other-owner factor from 1 to the weight limit, the horizon from 1 to the date offset limit (365 days). At least one auth provider is required, names distinct, at most one built-in OAuth server (its metadata sits at the origin's well-known paths), whose `sign_in_with` names an OIDC provider (the only kind with a sign-in page); the security settings (`auto_link`, `allow_off_loopback`) default off. Overrides are a fixed table, not a generic mapping: `CAIRN_DATABASE`, `CAIRN_LISTEN`, `CAIRN_PUBLIC_URL`, `CAIRN_TIMEZONE`, `CAIRN_ASSISTANT_API_KEY`, and `CAIRN_AUTH_<NAME>_TOKEN` or `_CLIENT_SECRET` for a named provider's secret; a secret variable that names nothing fails startup. - Alternatives: a generic `CAIRN_<PATH>` mapping of every key (types would have to be guessed from strings, and list entries addressed by index); defaulting the listen address or time zone (the PRD's A9 makes the zone the deployment's choice, and the brief's planted bug is exactly that default); allowing a path prefix in the public URL (the API's paths and the UI's hash routing assume the origin's root).

## 2026-10-07, brief 4.7: the Host allowlist matches names, not ports, and refuses with 421

- Question: the allowlist (4.3 review round 1) is "built from the public URL's authority, plus loopback names when the listener is loopback-bound". An authority has a port, and proxies differ in whether the `Host` they forward carries one; Vite's development proxy forwards its own `127.0.0.1:<port>`.
- Call: a request is served when the host name in its target's authority, or else its `Host`, equals the public URL's host or, on a loopback-bound listener, `localhost`, `127.0.0.1`, or `[::1]`, compared case-insensitively with a trailing dot ignored; any port is accepted, a malformed one or credentials are refused. A rebinding page can choose its port but never a name other than its own, so the name is what protects the peer-trusting providers. - Alternatives: matching name and port (breaks proxies that forward or drop the port, and the Vite dev loop); 403 or 400 (421 says the server does not answer for that name, which is what happened).
- What would change it: a deployment reached under several names (public URL aliases, as the 4.3 entry says).

## 2026-10-07, brief 4.7: the socket-level write stall is measured from the subscriber's window closing, and keepalive borrows the stall and heartbeat

- Question: the acceptance asks that an SSE client that stops reading lose its slot "within the write stall plus one coalescing interval". With `TCP_USER_TIMEOUT` at the stall, the kernel starts that clock only when the subscriber stops taking data (its receive window closes, after its buffer fills), and only from its first zero-window probe, sent one retransmission timeout later (Linux's minimum is 200 ms). Measured on loopback, the slot is freed 15.24 to 15.28 s after the window closes. Keepalive needs an idle time and a probe interval the limits table does not name.
- Call: the acceptance test measures from the moment the bytes waiting in the client stop growing and allows the stall, one coalescing interval, and the 200 ms minimum before the first probe; it also checks the slot is not freed before the stall. The listener sets `TCP_USER_TIMEOUT` to `SSE_WRITE_STALL`, keepalive idle at `SSE_WRITE_STALL` and probes at `SSE_HEARTBEAT_INTERVAL` (nearest named limits, DECISIONS.md 1.2), and `TCP_NODELAY`. On a kernel without `TCP_USER_TIMEOUT` the binary still runs and warns at startup.
- Alternatives: setting the user timeout below the stall to hit the bound from the moment reading stops (the 4.2 entry fixes it at the stall); shrinking socket send buffers (delays by the buffer, not a time).
- What would change it: a bound that must hold from the moment a client stops reading regardless of its buffers, which no socket option gives.

## 2026-10-07, brief 6.2: how the durability testbed judges durability

- Question: under a crash-restart the process loses its memory, so how does the restarted incarnation know which commits were acknowledged, and how are the PRACTICES invariants checked?

## 2026-10-06, brief 2.7: review items resolve into mutations, and only an unresolved one blocks apply

- Question: 2.1 recorded that a proposal's review items are not enforced at apply and left their resolutions to 2.7; the coordinator's ruling asks that each resolution become mutations and that only unresolved items block apply. PRD B7 lists resolutions (map old to new, keep the local definition as an override, accept the target and clear the now-invalid state, reopen, and keep/remap/remove for what a retained orphan references) that the schema's `ConflictResolution` did not all have, and a conflict carried only a node field.

## 2026-10-06, brief 4.2: where the SSE write stall is enforced

- Question: PRACTICES disconnects an SSE subscriber "that cannot take a write" for 15 s. The API's stream hands frames to the response body through a one-frame channel and drops the subscription when a send waits out the stall, but hyper keeps taking frames while the kernel's socket buffers have room, so a peer that stops reading (or vanishes without a FIN) is not caught until about a megabyte of ticks or the TCP retransmission timeout (about 15 minutes) later, holding one of the 256 subscriber slots meanwhile. - Call: the stall is enforced in two places. The API keeps its channel stall (it catches a server-side writer that is stuck, and a peer whose buffers are full). ## 2026-10-06, brief 6.1 and the H5 fix: a resubmission beside its own original in flight is answered stale (product bug, fixed)

- Question: the multiplayer testbed's smoke campaign failed about one generation in eight (8 of 64) on `nothing-unacknowledged-applied` and `surfaced-not-applied`: a patch its caller was told conflicted is in the journey. Is that the testbed or the product, and how is it fixed?
- Finding (6.1): the product (H5). Mechanism, from the minimized seed (`briefs/proof/6.1/README.md`): a commit holds its transaction open past the caller's attempt timeout; the caller resubmits the same patch; its commit conflicts twice with the original's revision row and, finding no receipt yet, the store answered stale naming the revision in flight (base plus one) with nothing intervening (3.1's call for a twice-conflicted commit). The client's retry (4.2) rebased onto that revision; the engine answered that the patch names a revision past the current one; the client rebased back; the 32-resubmission bound ran out in no virtual time and the conflict was surfaced; then the original landed. The same answer given to any other patch beside a commit in flight named that revision with nothing intervening even when the commit in flight touched what the patch did, so the client could take an unsafe retry as safe. Since 4.2's review a patch runs on its own task, so an HTTP resubmission can meet its original too, not only the in-process agent.
- Call (the fix): (1) the Turso store queues commits in process on what they write: before it begins, a commit takes its turn at every revision row it writes (its target's, its dependencies', the deployment's when it writes it) and at its patch id, in one order, holding them until its transaction ends and waiting at most `store_connection_acquire` (then `AcquireTimeout`, a 503). A resubmission beside its original waits for it and finds its receipt inside the transaction (`AlreadyApplied`); any other commit beside one in flight waits and is then checked against what really committed, so a stale answer carries the real intervening touched set. Commits to different domains wait on each other only through a revision row they both write: a commit that writes an entity reference (a node, answer, role fill, or participation naming an entity), or creates an entity, also claims the deployment's revision row, so those commits queue behind each other across every journey and route (and beside deployment patches and proposals to the deployment); before the fix they already conflicted there, and the second lost or got the phantom answer. A commit held near the acquire limit on one journey can therefore make entity-referencing commits to other journeys answer 503. (2) A second write-write conflict, now possible only from a connection outside those turns, is answered stale only with revisions that have really moved; when none has, it fails rather than name a revision still in flight. (3) The client's safe retry never rebases backward: a conflict whose current revision is not past the one the patch named is surfaced, so no pair of answers can send a patch back and forth. The memory store, the browser host's included, commits whole under one lock, so nothing is ever in flight beside a commit there and it needs no change. Tests: `crates/service/tests/in_flight.rs` (both cases over both stores; with the turns removed the Turso cases fail with `conflicted twice with a commit still in flight`), Turso's race cases (now showing the second commit waits and what it then gets), `client::retry`'s `submit_never_rebases_backward`; the smoke campaign passes 16 of 16 generations with no tolerated finding.
- Alternatives: per-patch-id in-flight tracking in the service (fixes the resubmission only; any other patch beside a commit in flight still got the empty stale answer); answering a twice-conflicted commit as a retryable failure (the first test's caller still gets no receipt, and every commit beside a slow one fails); waiting for "some commit to end" and retrying (two commits holding each other's rows could each wait for the other); the client alone refusing backward rebases (stops the ping-pong but still surfaces a conflict for a patch that lands). This supersedes 3.1's twice-conflicted call below.
- What would change it: a second server process on one database (the turns are per process; ARCHITECTURE assumes one); a commit beside a slow one waiting near the acquire limit in practice; or the deployment-wide queue of entity-referencing commits showing up as latency, which would call for narrowing the deployment claim (to commits that create entities, with a merge's referencing check carried another way), a design change needing its own decision.

## 2026-10-06, brief 4.2: what the client's safe retry resubmits, and how often

## 2026-10-06, store hardening: a persisted type change cannot land unmapped

- Question: engine briefs added persisted fields (`NodeState.skip_reason`, `LocalEdit::Shape`) while the Turso backend was built in parallel from an older schema; Turso silently dropped one and rejected the other, and only a sampled property round trip caught the second. ## 2026-10-06, brief 2.5: what counts toward gravity, and what leverage completes

- Question: gravity excludes "terminal weight" and prunes "not-relevant branches" but does not say whether a node's own weight counts once it is terminal, or what "terminal" covers for effectively skipped, auto-reached, and done groups; leverage's "remaining hard dependencies would be satisfied by completing n, including cascading derived group completion" does not say whether completing a node also completes what then auto-reaches, or a skipped container whose kept work it finishes.
- Call: a node counts (in its own gravity and in any other's) its weight, discounted when undecided, only while it is in scope and open; closed means pass 5's closed (terminal, effectively skipped, auto-reached, or a group whose finish is satisfied), so gravity is what still rides on a node and never decreases upstream along a dependency between in-scope nodes. Not-relevant nodes count nothing, and the pruned set already cuts the edges through them. The normalization set and leverage's targets are in scope, open, and not groups. Leverage simulates completing the node over pass 5's instants with each instant's own rule: a start or entry once its pruned gate waits are satisfied; a group's finish likewise, and so the finish of a pending, relevant `auto_reach` milestone whose effective date is today or earlier, which pass 5 reads as reached once it is unblocked (F1); a skipped container's finish once its kept work's are (D1a, the same rule that makes it satisfy dependencies); every other open finish only by completing that node. A target is a node whose start (`deps_done`) the simulation satisfies. Relevance and dates are held fixed: the PRD fixes relevance, and dates are fixed too, so a milestone the completion would newly bring due through the date network (its first effective date bounded by the completed node's actual) is unblocked but not completed; re-solving the date network for each hypothetical completion would be up to 2,000 date solves of about 1.6 million operations each at the limits, per derive. - Alternatives: own weight counting while terminal (a done node's gravity would exceed its open upstream's, breaking the monotonicity property); no cascade through auto-reach (linear in every case, but it understates what completing a gate frees right now, against F1); re-solving dates per hypothetical completion (exact for milestones the completion itself brings due, review round 2's case, at the cost above).
- What would change it: journeys with long chains of overdue, gated `auto_reach` milestones, where the repeated cascades would show in the cost; an incremental date solve cheap enough to run per hypothetical completion.

## 2026-10-06, brief 2.5: the owner factor compares owner sets

- Question: an owner resolves to a set of entities (a role may have several members), and the PRD's `owner_factor` (2 "when d's owner differs from n's owner, or d is owned by no one and n is owned") does not say what "differs" means for sets, or the case of an owned target and an unowned node; "prioritize for me" recomputes it "relative to the current user", who may hold several entities (H3).

## 2026-10-06, brief 2.3: how the execution layer reads facts, slack, and overdue

Edges to self, ancestors, and descendants are reported under their own codes and left out of the cycle check, so one cause gives one violation.
- Alternatives: explicit and parent-child edges only (misses inherited cycles until 2.2).
- What would change it: 2.2 building the effective graph as a separate structure, in which case this check moves into it.

## 2026-10-06, brief 2.1: engine assertions sit on contracts, not two per function

- Question: PRACTICES (Bounds and assertions) asks engine functions to carry at least two assertions on average.
- Call: 2.1's engine asserts its contracts where they are checkable and meaningful (about 70 across about 190 functions): every write addresses an existing graph and record (`Records::write`); a rejected mutation writes nothing and every write stays in its patch's domain (the dispatcher); each handler's precondition and the shape of its writes; each stage only adds violations; after apply, one event per mutation, the revision advanced by one, the base revision current, and every committed graph re-verified whole. ## 2026-10-06, brief 3.1: a Turso commit writes the revision row of every domain it depends on, and the store numbers the logs

- Question: Turso's MVCC detects write-write conflicts only; a read is never checked against a concurrent write (write skew). Review round 1 found three consequences: a journey patch starting to reference an entity and a merge of that entity could both commit (the merge missing the reference, E6); a proposal created while its journey is hard-deleted could survive the deletion (A19); and a log position Turso numbers at insert could become visible after a higher one a reader had already paged past, so history paging skipped it (J5).
- Call: a commit also writes, without changing it, the revision row of every domain or proposal a precondition names, of a proposal's destination, and of the deployment when it writes an entity reference, so any commit that would invalidate what it read conflicts with it (retried once, then stale). Log rows (events, the auth log) are numbered by the store from one sequencer per log in the process, held by a commit until its transaction ends; a reader reads below the lowest position still held, so every position it can see belongs to a transaction that ended before its read began. A proposal to a hard-deleted journey's id is rejected like a create. Turso cases: `a_reference_and_a_merge_in_flight_do_not_both_commit`, `a_proposal_and_its_journeys_deletion_in_flight_do_not_both_commit`, `history_paging_never_skips_an_event_committed_late`; each fails with its fix removed.
- Alternatives: re-reading the preconditions just before COMMIT (still a race); one global commit counter (every commit serialized, which ARCHITECTURE rejects); history pages by time (not unique, not monotonic across commits).
- What would change it: several processes sharing one database (`Later`), which would need the sequencer in the database; a Turso that checks reads (serializable MVCC).

## 2026-10-06, brief 3.1: what a change set's writes mean to the store

- Question: brief 1.2 made an event's delta a list of writes (put a record's after-state, remove an address, copy a graph) but left what a store does with each, and the engine (2.1, built alongside) must emit deltas that mean the same to every backend.
- Call: a put stores the record at its address, replacing what was there; a whole node's put carries its edges out, participations, and resources, and replaces them. A removal removes everything its address covers: a node takes its fields, the edges at either end, its participations and resources, its state, pin, snooze, overrides, tombstone, and the notes on it (the touched-set rule, H5); a graph's removal clears it; a draft's removal takes its graph; a journey's domain removal takes its fields, graph, proposals, and events (A19). A copy puts every record of one graph into another. A node field is written, never removed; a published version is written once, by the copy that publishes it; routes, versions, the deployment, and deleted journey ids are never removed (A11, A19). Anything else is a malformed change set, refused whole. The memory backend is the reference and the conformance suite (`writes_follow_the_reference_semantics` and the rest) holds Turso to it.
- Alternatives: per-record removal only (the engine would list every row a removal reaches, and a missed one would be an orphan); a removal of a node leaving its tombstone (the tombstone is written after the removal in the same delta instead).
- What would change it: the engine needing a write the list lacks, or a removal that should leave something on the node behind.

## 2026-10-06, brief 3.1: the revisions a commit moves besides its target's

- Question: A17, E6, and H5 say which revision a patch checks, but a few commits write outside their target: entity creates riding in a journey or route patch, a journey's hard delete (its deleted id is a deployment record), and patches to proposals.
- Call: a riding entity create moves the deployment revision once per commit (as brief 1.2's fixtures assume); the deleted-journey record does not, since it is not part of the deployment document and would only make concurrent journey patches stale. A patch to a proposal moves the proposal's revision, carried on the record it writes, which must be the base plus one; its destination's revision does not move. A journey's or route's first commit must write its fields. A published version's revision is always 1. Each stored receipt records what its commit moved (its target's revision, the deployment's, and the revision of any proposal it wrote, as applying one does) and what it wrote in the deployment, which is how a stale rejection finds what intervened, even after a hard delete has removed the events of a journey whose patch created an entity.
- Alternatives: moving the deployment revision on a hard delete (the deployment log keeps the event either way); the store minting proposal revisions itself (then the record the engine wrote and the one stored would differ).
- What would change it: a view of the deployment that lists deleted journeys, which would then need the revision to move.

## 2026-10-06, brief 3.1: Turso checks no foreign key against a concurrent transaction, so the domain revision row serializes parents and children

- Question: at the pinned `turso =0.8.2`, under MVCC (`BEGIN CONCURRENT`), a parent's delete and a child's insert made in two concurrent transactions both commit, leaving an orphan (the readiness scout's open probe item, reproduced by `conformance::turso_lets_a_child_insert_race_its_parents_delete`). ARCHITECTURE (Backends) asks for foreign keys, and for any rule Turso cannot hold to be enforced in the commit transaction, tested, and recorded here.
- Call: the foreign keys stay, deferred to COMMIT (which Turso checks within one transaction), and the store never relies on them across transactions. Every parent row and its children belong to one domain, or the parent is never deleted (routes, published versions, users); every commit's first write is its domain's revision row, so two commits that could race a parent against its child conflict, and the loser is retried once and then answered stale. `conformance::a_delete_racing_a_child_insert_leaves_no_orphan` races a journey's hard delete against a node insert into it and finds no orphan rows. Unique keys need no such help: two concurrent inserts of one key conflict at commit (`two_creates_of_one_journey_in_flight_yield_one_journey`, `two_entity_creates_of_one_key_in_flight_yield_one_entity`).
- Alternatives: WAL with `BEGIN IMMEDIATE` (every writer serialized, which ARCHITECTURE rejects); re-checking every foreign key at the end of each commit (still racy under snapshot isolation).
- What would change it: a Turso release that checks foreign keys across transactions (the gap test starts failing), or a table whose parent can be deleted from another domain than its children.

## 2026-10-06, brief 3.1: uniqueness a patch may pass through is checked at the end of the commit

- Question: ARCHITECTURE's Schema outline makes (graph_id, parent_key, id) unique on nodes, and H3 makes emails unique across entities, but a valid patch can pass through a duplicate on the way (swapping two siblings' ids; moving an email from one entity to another, in either order), and neither SQLite nor Turso has a deferred unique constraint.

Primary keys stay unique constraints, since no patch passes through a duplicate key. Conformance cases: `sibling_ids_may_swap_within_a_commit_but_not_end_duplicated`, `emails_may_move_between_entities_within_a_commit_but_stay_unique`.
- Alternatives: immediate unique indexes (they reject valid patches); ordering a change set's writes so no duplicate appears (the store would need the engine's knowledge of what each write means).
- What would change it: deferred unique constraints in Turso, or a Postgres backend (which has them).

## 2026-10-06, brief 3.1: a commit that conflicts twice is answered stale with the revision in flight

- Question: ARCHITECTURE (Concurrency and notification) retries a Turso write-write conflict once, then answers a revision conflict. When the second attempt conflicts too, the commit it lost to is still in flight: no revision has moved yet, so there is no current revision to report.
- Call: the answer is `stale`, listing the target with the revision the in-flight commit is producing (the base plus one), any other revision the patch named that has moved, and the touched set of whatever has committed since. The client's refetch-and-resubmit is the retry; no backoff knob.

## 2026-10-06, brief 1.2: an event's delta is the after-state of the records it wrote

- Question: J1 asks each event to carry "the after-state delta needed to replay it", and J3's replay must be exact; ARCHITECTURE's change set is "entities put and removed by key" for a store that does not depend on the engine. The readiness scout left the delta's representation open.
- Call: one record vocabulary (`Record`, addressed by `RecordKey`, mirroring the Schema outline's tables, with a node field addressable on its own) serves both. An event's delta is the ordered list of `Write`s its mutation made: `Put(record)` as after-state, `Remove(address)` (an address may cover a whole domain, graph, or node), or `CopyGraph` (publishing). Replay applies the writes and re-derives nothing; the change set is the receipt plus the events, and its writes are what a store persists. Side effects (a local-edit marker set by an edit, a snooze cleared by a transition, tombstones written by a removal) appear in the delta as writes, so replay never needs the rules that produced them.
- Alternatives: a typed delta per event type (readable history, but replay re-implements each mutation's effects and must match apply exactly); deltas as full graph snapshots (exact but large).
- What would change it: a store that needs coarser rows than per-field node writes, or history display (J4) needing the mutation as submitted beside its effects, which would add the mutation to the event.

## 2026-10-06, brief 1.2: touched sets by record address, coarse when in doubt

- Question: H5 retries a stale patch automatically when its touched set does not overlap the intervening events', "by key and field"; the scout left the granularity open, and some mutations' effects (create, publish, upgrade, apply a proposal) depend on content they do not name.
- Call: a touched set is a set of record addresses. Node fields, edges, participations, resources, local-edit markers, and each kind of journey state are addressed separately, so an edit and a transition on one node, or edits to two fields, never overlap; a whole node overlaps everything on it (an edge belongs to both ends), so a removal overlaps any change to what it removes. - Alternatives: per-node granularity (simpler, fewer automatic retries); computing touched sets from the graph at apply (exact but not available to a client deciding whether to resubmit).
- What would change it: retries in the multiplayer testbed (6.1) failing too often, which would refine the coarse cases.
