# Decisions awaiting review

Judgment calls made while implementing the briefs, for the user to review (`AGENTS.md`, Decide, record, keep going). Newest first. Each entry: date, brief, the question, the call, the alternatives, and what would change it.

## 2026-10-06, brief 2.7 (review round 1): an empty draft carries its route's retired keys, and publishing retires what it left out

- Question: a draft opened by an import or a saved journey starts empty, so it held none of the route's retired keys, and nothing retired the keys of the extended version that its content left out. A key could come back, and later versions lost the retirement history (Invariants: no key is ever reused).
- Call: import rejects a supplied key the base retired (`retired_key_reused`). `open_draft { import | save_as_route }` on a route with versions writes the latest version's retired keys into the new draft, so `add_node` refuses them. `publish_draft` retires every node, role, and kind key of the version the draft extends that the draft leaves out. Both read that version, so the host loads it for those two mutations; a missing one is `target_missing`. A save-as-route of a journey behind its route that would bring back a retired key lists one violation per key, naming the version that retired it and the remedy (upgrade the journey to that version first, save it as a new route, or, for a node, exclude it).
- Alternatives: retiring at open time (the import's matched keys would then be refused); retiring at publish only when the version happens to be loaded (a silent gap).
- What would change it: a store that keeps a route's retired keys outside its version graphs.

## 2026-10-06, brief 4.9: a proposal is created under its domain and addressed by its id alone afterwards

- Question: ARCHITECTURE spells proposals as `POST /{domain}/proposals` with client-generated ids, then `PATCH`, `POST .../apply`, and `POST .../discard`, and the brief adds `GET` by id and `POST .../preview`; neither says whether the later operations sit under the domain (`/journeys/{id}/proposals/{proposal}/apply`) or under the proposal's own id. I6 asks that an agent that lost a response can fetch by id.
- Call: a proposal is created at `POST /journeys/{id}/proposals`, `/routes/{id}/proposals`, or `/deployment/proposals` (a body of patch id, proposal id, and draft); afterwards it is addressed by its id alone: `GET /proposals/{id}`, `PATCH /proposals/{id}`, and `POST /proposals/{id}/preview`, `/apply`, `/discard`, and `/refresh`. The handler reads the destination off the stored proposal (a proposal's destination never changes) and passes it to the service, so a missing proposal is a 404 before any write. Upgrade, save as route, and re-link are drafted at `POST /journeys/{id}/upgrade`, `/save-as-route`, and `/relink`, each answering the proposal it stored; their review and apply go through the same proposal endpoints. Every proposal write answers `ProposalAnswer` (`saved` with the proposal, `already_saved` with the receipt, or `existing` for a create resubmitted by proposal id); an apply answers a `PatchAnswer` like any domain patch. ARCHITECTURE's HTTP API line now spells this out.
- Alternatives: every operation under its domain (three copies of six endpoints, and a client that knows only the proposal id, as I6's lost response leaves it, must fetch it first to learn the path); the destination in each body (a second statement of something the proposal already holds, which could disagree).
- What would change it: proposals whose destination can change, or per-domain authorization that needs the domain in the path.

## 2026-10-06, brief 4.9: a request Cairn cannot draft answers 422 with a problem, not a rejection

- Question: an upgrade, save as route, re-link, or refresh can fail before any patch exists: the journey follows no route, the version is older than the one it follows, or the draft passes a proposal's limits (the engine's `DraftError`). PRACTICES keeps `Rejection` for a patch that was submitted and refused, and 4.2 answers everything else as a `Problem`; neither names a status for a well-formed request the engine cannot draft.
- Call: a missing journey or route version answers 404 `not_found`; the other draft errors answer 422 with a `Problem` whose code is `cannot_draft`. The OpenAPI document lists 422 on the drafting operations as one of a `Rejection` (the proposal write was invalid) or a `Problem`; the two are told apart by their fields. A refusal is counted with the patch outcomes as `not_drafted`.
- Alternatives: 409 (nothing conflicts: the request would fail the same way on any revision); a `Rejection::Invalid` with a made-up violation path (a draft error is not a violation of a candidate graph, and A15's list is the engine's); 400 (the request parses).
- What would change it: a client that needs to tell draft errors apart programmatically, which would give `DraftError` its own wire enum.

## 2026-10-06, brief 4.8: a stale proposal is refreshed by drafting it again on the new base, its choices carried by what they are about

- Question: I6 says that on a stale base the service shows the intervening changes and refreshes the proposal against the new base, requiring renewed review; the readiness ruling says the service re-runs the upgrade on the new base and carries resolutions by (node, field). Neither says what refreshing a save as route, a re-link, or an ordinary (assistant-drafted) proposal means, which choices besides conflict resolutions carry, or what happens to a choice the new item does not offer.
- Call: `refresh_proposal` reads what the proposal was drafted as off its mutations: an `upgrade` (journey destination) or `relink` is drafted again by the engine from the journey and versions as they are now; an `open_draft { save_as_route }` (route destination) is saved again with the name its `create_route` carried (or the route's own); anything else keeps its mutations and items and names the destination's current revision. Each choice on the old items is carried to the new item about the same thing: a conflict's resolution by what it is about (node and field, edge, node and kind, node and resource, a node's shape, a decision's answer, a role, a kind, the default owner), only when the new conflict still offers it; an orphan's keep by node; an entity's mapping by entity; an exclusion by node. An item with no counterpart starts at the draft's default. The title and description stay as edited. The refresh is an ordinary proposal edit against the editing revision the caller saw, so the proposal's revision moves and an apply naming the reviewed revision from before is stale: review is renewed by construction. The intervening changes come with the stale apply (and with the preview, as `StaleBase`).
- Alternatives: refreshing in place on apply (applies something nobody reviewed); carrying a resolution the new conflict does not offer (apply would refuse it as not offered, so the reviewer would see a blocked item rather than an open one); re-basing an upgrade without re-running the merge (its clean outcomes are computed at apply anyway, but its items would describe the old base).
- What would change it: proposals that must remember how they were drafted beyond their mutations (an assistant draft that could be re-asked), which would need a drafting record on the proposal.

## 2026-10-06, brief 4.8: an imported route file mints its new keys from the patch id

- Question: import mints keys for keyless nodes, roles, kinds, and resources through a host-supplied allocator ("random bodies in production, a counter in tests"), but the service is runtime-free with no randomness, and a resubmitted import must be the same patch to be answered from its receipt (H5), which random keys would break.
- Call: the service mints a key body as 16 hex digits of the FNV-1a hash of the patch id, the key's prefix, and a counter; the engine already draws again for a body the graph holds or the route retired. The file is matched against the route's latest version, whatever version it names as extended, since the draft it opens extends the latest (A13): an older export cannot bring back a key a later version retired (review round 1); a version it names that does not exist is refused. A resubmission rebuilds the patch once, as it was committed: at the route revision its receipt implies, against the version its import event's draft record says it extended; the same file under the same patch id is answered from the receipt, any other content is a reused id, and a store or engine failure on the way is answered as a failure, not a reuse (review rounds 1 and 2). Proposal drafts (upgrade, save, re-link, refresh), whose content depends on a destination that may have moved, are answered from the receipt only when the patch id's event is a proposal create (or, for a refresh, an edit from the base named) of the same proposal for the same destination, by the same author for a create, whose drafted request (upgrade target, re-link lineage, saved journey, route, and name) is the one asked; anything else is a reused id (review round 2). An import is an ordinary route patch (open a draft, then the file's structure), so the draft is reviewed and published as any other (A11), not a proposal.
- Alternatives: random keys from a host-supplied source (a new composition-root part, and resubmissions would differ); a counter per route (two imports racing would mint the same keys); an import as a proposal (the draft it opens already waits for publishing).
- What would change it: a store-assigned key sequence, or imports that must be reviewed before the draft opens.

## 2026-10-06, brief 4.8: an upgrade or re-link reaches a journey only through its applied proposal; a proposal id answers a resubmitted create

- Question: the engine accepts `upgrade` and `relink` in any journey patch (a proposal's mutations run through the same handlers), so a client or agent could submit one directly and change a journey with no review, while B7 says an upgrade "is a proposal, applied only on confirmation", Journey durability says route edits reach journeys only once an upgrade is confirmed, and I7 that an agent applying an upgrade goes through the same confirmation as anyone. I6 asks that an agent that lost a response can "fetch or resubmit by id", without saying what a create naming an existing proposal id answers.
- Call: (1) the service refuses a domain patch holding `upgrade` or `relink` as invalid, `mutation_not_for_target` at each such mutation, after the receipt lookup (a resubmission is still answered from its receipt); they reach a journey only as the drafted mutations of a proposal someone applies, whose events record that person as the confirming user (H2), user or agent alike. (2) A create naming a proposal id that already holds a proposal for the same destination by the same author (user and agent) answers that proposal as it now stands (`ProposalWritten::Existing`), never a second one; anyone else's create at that id is stale against the proposal's revision. A resubmitted patch id is answered from its receipt as for any patch. (3) Applying a proposal that is not open, belongs to another destination, or does not exist is checked at the destination's current revision, so the rejection names that (`proposal_not_open`, `mutation_not_for_target`, `target_missing`) rather than a stale base.
- Alternatives: (1) allowing direct upgrades (a confirmation anyone can skip); refusing them in the engine (the engine cannot tell a proposal's mutations from a patch's without a flag on every handler). (2) Comparing the resubmitted content too (an agent whose proposal a reviewer edited meanwhile would be refused and have to fetch anyway); refusing every create at an existing id (an agent cannot tell its own lost create from a collision).
- What would change it: a host that needs scripted upgrades without review (a bulk migration tool), which would be its own confirmed operation.

## 2026-10-06, brief 4.8: derived reads are memoized by everything the derive reads, the viewer included, and answer the revisions they came from

- Question: D6 allows a cache only if it is invisible; ARCHITECTURE lets hosts memoize `Derived` per (domain revision, deployment revision, inputs), and the readiness ruling and the brief name today and the viewer in the key. The engine's `derive` reads no viewer (the per-viewer ranking is computed by `next` and `list` on demand), so keying on the viewer splits the memo per user for nothing today. Nothing said what a derived read answers besides the projection.
- Call: the memo key is the journey, its revision, the deployment revision, today in the deployment's zone, and the caller's entities (the time zone and rank constants are the service's settings, fixed for its life). The journey, the caller's identities, and the deployment are loaded on every read, so a commit or midnight always changes the key before a stale entry could answer; a miss derives outside the lock. The viewer stays in the key as the brief says, so a future pass that reads it cannot make the memo visible. Every derived read answers `Projected<T>`: the projection with the journey revision, deployment revision, and today it was derived from, so a client compares a tick with what it holds (H6). The memo holds at most 8 derivations, least recently read dropped first (brief 4.8, Decision log).
- Alternatives: a key without the viewer (one entry per journey and day instead of per user, correct only while derive reads no viewer); keying on the deployment's content rather than its revision (a hash of every entity per read); returning bare projections (a client could not tell which revision a view shows without a second read).
- What would change it: memory pressure at the limits (a derivation of a 2,000-node journey is tens of MiB), which would argue for dropping the viewer from the key first.

## 2026-10-06, brief 2.7: re-link sets lineage, provenance, and markers in one mutation; save-as-route maps entities per participation

- Question: the ruling asks for a re-link mutation that sets the lineage and the markers atomically (B9: preserve the old lineage until apply). The schema's `relink` set only the lineage. B8 leaves open what "set the graph default_owner" does to an entity's participations, and what happens when one participation names entities mapped differently.
- Call: `relink { lineage }` now writes, in its own event, the lineage; for each journey node the version holds, `from_route` provenance and exactly the markers its differences from the version's node call for (set where they differ, cleared where they match); for every other node, `local` provenance and no markers; and the version's roles and kinds the journey lacks. `relink(records, journey, lineage)` drafts that mutation with one conflict per difference, kept by default; taking the route's value writes it after the re-link and clears the marker. Save as route drafts `create_route` (for a new route) or nothing, `open_draft { save_as_route }`, then the journey's structure (roles, kinds, default owner, nodes by path, keys kept, no state) as ordinary mutations, with one participation item per explicit entity and one exclusion item per node (a journey-local child of a placeholder starts excluded). Resolving rewrites the drafted node additions: an excluded node and its subtree are left out with the edges into them; a participation naming explicit entities becomes the one role they map to (the default-owner choice maps to the graph's `default_owner` role), goes when all are dropped, and blocks every involved item when they map to different roles.
- Alternatives: re-link as many mutations (provenance and marker writes per node, past the patch limit at 2,000 nodes with several differences each); the default-owner choice clearing the participation so the node inherits (equal at the root, different under an ancestor with its own owner); exclusion as removals after the additions (would retire the excluded keys in the route).
- What would change it: the review screen (5.7) wanting per-participation rather than per-entity mappings, or re-link offering exclusions of nodes the version holds.

## 2026-10-06, brief 2.7: the upgrade mutation applies the merge's clean outcomes; conflicts ride after it

- Question: the schema had the upgrade's merge ride in its patch as ordinary mutations. Written out that way, an upgrade at the limits (2,000 nodes, 22 fields each, plus edges, participations, resources) can pass the 8,000-mutation patch limit, and every field it takes from the route would set a local-edit marker (B4) unless each write were followed by a marker clear, doubling the count.
- Call: `upgrade { to }` computes the three-way merge at apply, from the version the journey follows and the target (both loaded), and writes its clean outcomes in its own event: route changes on aspects the journey did not mark, converged markers cleared, new route nodes (unless held, retired, tombstoned, or under a node the journey removed) in their initial state with `from_route` provenance, orphans marked `orphaned`, roles and kinds by value (a removed one goes only when unedited and unused), and the default owner. A kind or answer-type change applies whole only to a node with no markers, no answer, and its initial state. Everything else is a conflict, which the merge leaves at the journey's side; the proposal's resolutions and orphan removals follow as ordinary mutations. `upgrade(records, journey, to, inputs)` drafts the proposal from the same merge, so what review shows and what apply does agree by construction, and lists every violation of a trial apply (conflicts left at the journey's side) as an item. Roles, kinds, and the default owner carry no markers, so a journey value that differs from the base's is the journey's edit.
- Alternatives: the merge as explicit mutations (reviewable one by one, but past the patch limit at the limits and marker-clearing on every write); a flag on field mutations that suppresses markers in an upgrade patch (an implicit rule on every structural mutation).
- What would change it: a review screen (5.7) that must let a reviewer drop a single clean route change, which B7 does not offer; markers on roles and kinds.

## 2026-10-06, brief 2.7: review items resolve into mutations, and only an unresolved one blocks apply

- Question: 2.1 recorded that a proposal's review items are not enforced at apply and left their resolutions to 2.7; the coordinator's ruling asks that each resolution become mutations and that only unresolved items block apply. PRD B7 lists resolutions (map old to new, keep the local definition as an override, accept the target and clear the now-invalid state, reopen, and keep/remap/remove for what a retained orphan references) that the schema's `ConflictResolution` did not all have, and a conflict carried only a node field.
- Call: a conflict says what it is about with both sides (`Conflict`: a field, an edge, a participation, a resource, a node's shape, an invalidated answer, a role, a kind, the default owner), and `Conflict::offers` says which resolutions it takes; `ConflictResolution` gains `MapChoices` (every removed answered choice to a remaining one), `RemapRole`, `RemapKind`, and `Remove`. `resolve(draft)` is the proposal's drafted mutations, rewritten by the save-as-route choices (excluded subtrees left out with the edges into them, explicit entities mapped to roles), then each chosen resolution's mutations in item order, then the orphans removed. `ApplyProposal` runs the resolved list, so apply enforces items: one still needing a choice, or holding one it does not offer, rejects the patch as `unresolved_review_item`, one violation per item; a resolved list past the mutation limit is `limit_exceeded`. Items with nothing to choose (kept local edits, cascades, violations found when drafting) never block; strict validation at apply is what stops an invalid candidate. A resolution that takes the route's value writes it and then clears the marker the write sets, so markers stay exact without a special rule for upgrade patches.
- Alternatives: writing resolutions into the proposal's mutations on every edit (the items and the mutations could disagree); a violation item that blocks until acknowledged (the reviewer fixes the cause by editing the proposal, and apply re-checks anyway); keeping `MapChoice` for one choice (a multi-choice answer can name several removed choices).
- What would change it: the review screen (5.7) needing a resolution per sub-part of an item, or a proposal whose resolved list routinely passes the mutation limit.

## 2026-10-06, brief 4.2: where the SSE write stall is enforced

- Question: PRACTICES disconnects an SSE subscriber "that cannot take a write" for 15 s. The API's stream hands frames to the response body through a one-frame channel and drops the subscription when a send waits out the stall, but hyper keeps taking frames while the kernel's socket buffers have room, so a peer that stops reading (or vanishes without a FIN) is not caught until about a megabyte of ticks or the TCP retransmission timeout (about 15 minutes) later, holding one of the 256 subscriber slots meanwhile. Review round 1 of 4.2 reproduced it.
- Call: the stall is enforced in two places. The API keeps its channel stall (it catches a server-side writer that is stuck, and a peer whose buffers are full). The listener, which 4.7 owns, sets `TCP_USER_TIMEOUT` to `SSE_WRITE_STALL` (with TCP keepalive, so an idle connection is probed): unacknowledged data older than the stall closes the connection, hyper drops the body, and the pump, which watches the channel close, drops the subscription at once. 4.7's brief carries it in scope with an acceptance case.
- Alternatives: a per-connection timer in the API that writes and measures acknowledgment (it cannot see the kernel's buffers); smaller socket send buffers (delays detection by the buffer size, not a time); leaving it to the retransmission timeout (a vanished peer holds a slot for 15 minutes).
- What would change it: a listener that cannot set `TCP_USER_TIMEOUT` (non-Linux hosts, a unix socket behind a proxy), where the proxy's own idle timeout must stand in.

## 2026-10-06, brief 4.2: what the client's safe retry resubmits, and how often

- Question: H5 says a stale patch is retried automatically when the intervening touched set does not overlap its own: "the client refetches and resubmits". It does not say which revision the resubmission names, whether it keeps its patch id, which conflicts are retriable, or how many times; PRACTICES bounds every loop but names no retry limit.
- Call: (1) The resubmission names the revisions the rejection reports as current, never one refetched since: only the events up to those were compared, so a commit landing in between makes it stale again and it is compared again. The view's refetch (H6) is separate and happens either way. (2) It keeps its patch id: a stale patch left no receipt, so the id still names one change, and a resubmission whose response is lost is answered from its receipt. (3) Only a conflict on the patch's own domain, or on the deployment when the patch names a deployment revision, is rebased; a revision the patch names elsewhere (a merge's journeys, inside its mutation) or a proposal's is surfaced. (4) At most 32 automatic resubmissions per patch, PRACTICES' assistant tool-loop limit borrowed as the nearest runaway stop (DECISIONS.md 1.2: values the table does not name take the nearest named limit); past it the last stale rejection is surfaced. The logic (`cairn_api::client::retry`) knows no transport: the HTTP client and an in-process caller of the service (6.1) drive the same code.
- Alternatives: rebasing onto a refetched revision (skips comparing whatever landed between the rejection and the refetch); a new patch id per attempt (a lost response to a retry could then apply twice under two ids); retrying a merge by rewriting its journeys' revisions (changes what was checked, which E6 makes the author's call); an unbounded loop (forbidden), or a new named limit (needs sign-off).
- What would change it: 6.1 finding retries exhausted under contention, which would make the bound a named limit for sign-off.

## 2026-10-06, brief 4.2: the OpenAPI document comes from schemars, and the Rust client is written, not generated

- Question: ARCHITECTURE named utoipa for the OpenAPI document and progenitor for the Rust client. utoipa 6 writes only OpenAPI 3.1 and 3.2, progenitor 0.15 reads only 3.0 (it rejects a 3.1 document outright), so the two cannot meet on one document. utoipa also builds schemas from its own `ToSchema` derive, while every schema type already derives schemars' `JsonSchema` for the file format; and progenitor generates its own copies of every type unless each of the ~150 components is mapped back to its Rust path by hand.
- Call: the document is OpenAPI 3.1, written by `cairn_api::openapi` from the endpoint table the router serves, with each operation's parameters, body, and answers declared once beside it, and every schema the type's own schemars JSON Schema (draft 2020-12 is 3.1's dialect), gathered under `components/schemas`. No utoipa. The TypeScript types are generated from it (openapi-typescript), as ARCHITECTURE says. The Rust client (`cairn_api::client`) is written over the same Rust types and the same endpoint table, so it cannot drift from the server, and a test validates real answers, accepted and refused, against the document's schemas for their operation and status.
- Alternatives: utoipa with a second derive on every schema type (two schema sources that can disagree, and utoipa in the engine's dependency tree through the schema crate); a 3.0 document for progenitor (schemars' 3.0 mode loses `const` and `prefixItems`, and the TypeScript types would come from the weaker dialect); a second, 3.0 copy of the document only for progenitor plus hand mapping of every component to its Rust path (a generated client whose types are all replaced is a URL builder).
- What would change it: progenitor reading OpenAPI 3.1, or a client that must be generated for another language from a 3.0 document.

## 2026-10-06, brief 2.6: what a canvas level draws, marks, and rolls up

- Question: C2 fixes the roll-up rules but leaves open which graph edges a canvas draws, what "a hidden, unsatisfied prerequisite that has no visible stand-in" means when the prerequisite reaches the node through an ancestor, whether badges read children or all descendants, and what a group's derived display state (D1) is.
- Call: a level draws the explicit requirements, condition gates, and stage openings of the full structural graph (C1 grays not-relevant nodes rather than hiding them); containment is nesting and inherited requirements are drawn once, on the ancestor. A blocked visible node carries the marker for each unsatisfied gate dependency (own, inherited, condition, or opening; not its children, which roll up into it) whose edge from the dependency's stand-in to the stand-in of the node holding it (the node, or the ancestor whose requirement, condition, or opening it is) is not drawn: either has no stand-in, or both land on one node. So a node under a hidden root whose opening is ahead is marked, and so is everything in a drilled-in container whose own opening is outside it. Badges read direct children, as `max_child_gravity` does (2.5). A group's display state is, in order: not relevant, skipped (stored or effective), done (it satisfies dependencies), waiting (its entries' gates are unmet), active (anything beneath it started or finished), not started.
- Alternatives: every effective edge drawn (inherited ones copied onto each descendant, the materialization 2.4's ruling forbids); a marker only for hidden prerequisite nodes (a visible requirement on a hidden root would leave its contents looking free); badges over all descendants (a deep checklist would mark its top container "children active" through a grandchild).
- What would change it: the canvas (5.2) needing inherited edges drawn per node, or a different group state vocabulary.

## 2026-10-06, brief 2.6: how the snapshot scopes, pages, and agrees with the next list

- Question: I3 asks for "depth/subtree scoping and pagination" and "the ranked acting frontier top N with the rest as counts plus keys" without saying what depth bounds, what a page is, or how a cursor stays meaningful; the brief asks that snapshot and `next` agree and that counts add up.
- Call: a subtree scopes everything in the snapshot (the node and everything beneath it); a depth bounds only the node list (levels below the subtree's node, roots at depth 1 when there is none), so an agent zoomed out still sees the frontier and the lists. The node list is in tree order and pages at 200; the acting frontier's first 200 items are exactly the next list's for the subtree, the rest are keys, and `counts` cover the whole subtree (by state adds up to in scope; the frontier shown plus the rest is the acting frontier count). A `Cursor` is a position in a projection's order, valid for the same revision and derive inputs; a page read at another revision starts over. The page limit (`page_item_count_max`, 200, PRACTICES' "snapshot frontier top-N, history page") is now a schema constant beside the explanation limit, with the value the store's own constant has; the store could read it from the schema.
- Alternatives: depth bounding the frontier and lists too (an agent at depth 1 would miss deep work that is next); a cursor naming the last key (stable across revisions, but the frontier's order is by rank, which a revision can reshuffle anyway); a separate top-N limit (needs sign-off, and PRACTICES gives one number for both).
- What would change it: agents needing a cursor that survives a revision, which would argue for a key-based cursor per order.

## 2026-10-06, brief 2.6: history pages events it is given, and finds a node's by the records they name

- Question: J4 wants history per node and per journey, grouped by patch; the store already keeps an `event_nodes` index (3.1), and the engine never reads the store (the ruling: `history(events)` takes schema `Event`s).
- Call: `history(events, node, cursor)` takes the journey's events in log order, keeps those naming the node (when one is given), and returns at most 200 events, grouped by patch, with the total and a cursor; a large patch spans pages. Which events name a node is `Event::nodes` in the schema: the subject, both ends of an edge, and the node every written record hangs off, the same rule as the store's `backend::event_nodes`, which could now call it. The store additionally names the nodes whose requirement a whole-node removal takes, which needs the graph before the commit; a host that wants that exactness passes the store's node-filtered events and no node.
- Alternatives: the engine reading store rows (forbidden); per-node history only in the store (the browser host, which has events and no store index, could not show it).
- What would change it: a node's history needing the removal's requiring nodes in the browser host too.

## 2026-10-06, brief 2.6: what the decision view, timeline, status summary, list, and "mine" show

- Question: C12's "which nodes each answer affected", C13's "derived due dates", C18's counts, C9's search, and E4's "filterable by kind" each admit more than one reading.
- Call: the decision view is the level with only decisions shown (its edges and markers by C2's rules), each decision with its answer while in effect (E3), its owners, the nodes whose relevance its answer can change (a condition on the node or an ancestor reads it, up to the nearest force include, which drops them, or reads a decision it affects in turn, since a condition reads a decision that is not relevant as unanswered), the milestone it pins, and the role it fills. The timeline holds each in-scope milestone at its effective date (actual, pin, or due), each other pinned node at its pin, and each other open in-scope node with a due date at it; done work has no due to show, and milestones with no date are listed as undated; the `final` milestone is the end anchor. The status summary counts in-scope nodes by stored state and lists what remains open, overdue, short, and stale, the milestones not yet reached with a date, and open decisions (stored open and not closed, so not under a skipped container) with owners in rank order; answers in the decision view and the snapshot name entities through aliases (E6). The list's text search is a substring of the title, description, notes and links on the node, and resources (labels and content as written), ignoring ASCII case like the store's cross-journey search. E4's kind is the participation kind (owner, reviewer, and the graph's own), and "mine" in the list and next list is any participation.
- Alternatives: decision-to-decision edges through hidden work (paths through non-decisions, quadratic at the limits); due dates of done work on the timeline; Unicode case folding (in-journey and cross-journey search would disagree); E4's kind as node kind (C9 and C10 already filter by node kind).
- What would change it: the screens (5.3, 5.4) asking for a different cut, which changes only these functions.

## 2026-10-06, brief 4.1: a journey whose conditions compare entities is held to the deployment it was checked with

- Question: review round 1 found a race: a journey patch that names no deployment revision (a pin, say) is validated against the aliases loaded with it, and an entity merge committed between that validation and the patch's commit can make a condition comparing entities true, so the patch commits a graph that no longer holds the plan invariants (F5, A15). The merge's own check saw the journey before the patch; the patch's commit checked no deployment revision. E6 asks only a patch that writes an entity reference to name one, and DECISIONS.md 2.1 (9) checks none when none is named.

## 2026-10-06, store hardening: a persisted type change cannot land unmapped

- Question: engine briefs added persisted fields (`NodeState.skip_reason`, `LocalEdit::Shape`) while the Turso backend was built in parallel from an older schema; Turso silently dropped one and rejected the other, and only a sampled property round trip caught the second. ## 2026-10-06, brief 2.5: what counts toward gravity, and what leverage completes

- Question: gravity excludes "terminal weight" and prunes "not-relevant branches" but does not say whether a node's own weight counts once it is terminal, or what "terminal" covers for effectively skipped, auto-reached, and done groups; leverage's "remaining hard dependencies would be satisfied by completing n, including cascading derived group completion" does not say whether completing a node also completes what then auto-reaches, or a skipped container whose kept work it finishes.
- Call: a node counts (in its own gravity and in any other's) its weight, discounted when undecided, only while it is in scope and open; closed means pass 5's closed (terminal, effectively skipped, auto-reached, or a group whose finish is satisfied), so gravity is what still rides on a node and never decreases upstream along a dependency between in-scope nodes. Not-relevant nodes count nothing, and the pruned set already cuts the edges through them. The normalization set and leverage's targets are in scope, open, and not groups. Leverage simulates completing the node over pass 5's instants with each instant's own rule: a start or entry once its pruned gate waits are satisfied; a group's finish likewise, and so the finish of a pending, relevant `auto_reach` milestone whose effective date is today or earlier, which pass 5 reads as reached once it is unblocked (F1); a skipped container's finish once its kept work's are (D1a, the same rule that makes it satisfy dependencies); every other open finish only by completing that node. A target is a node whose start (`deps_done`) the simulation satisfies. Relevance and dates are held fixed: the PRD fixes relevance, and dates are fixed too, so a milestone the completion would newly bring due through the date network (its first effective date bounded by the completed node's actual) is unblocked but not completed; re-solving the date network for each hypothetical completion would be up to 2,000 date solves of about 1.6 million operations each at the limits, per derive. The simulations of nodes only completion satisfies never satisfy the same instant, so together they read each instant and edge once; an overdue, gated `auto_reach` milestone is ranked too, and its own simulation repeats the part of a cascade behind it (review round 1 moved the call here from "auto-reach does not cascade").
- Alternatives: own weight counting while terminal (a done node's gravity would exceed its open upstream's, breaking the monotonicity property); no cascade through auto-reach (linear in every case, but it understates what completing a gate frees right now, against F1); re-solving dates per hypothetical completion (exact for milestones the completion itself brings due, review round 2's case, at the cost above).
- What would change it: journeys with long chains of overdue, gated `auto_reach` milestones, where the repeated cascades would show in the cost; an incremental date solve cheap enough to run per hypothetical completion.

## 2026-10-06, brief 2.3: how the execution layer reads facts, slack, and overdue

- Question: F3 and F6 leave open what an actual does to its own node's estimate (work estimated at four days, done in one), which side of a fact counts as a shortfall (ARCHITECTURE: "a constraint it violates ... is reported as a shortfall"), what slack means for work already started (`slack = latest_start - today` would read "start overdue" forever once started), and what `overdue` means for a group, whose state is derived (2.4's derived group completion does not exist yet; the coordinator put `overdue` in 2.3).
- Call: (1) In the execution layer a done node's own work counts no days: its actual dates replace its estimate, so finishing early is never a shortfall. The plan layer keeps every estimate. (2) A fact is short only when it is later than the constraints after it allow ("an actual date later than a chain allows"); a fact earlier than the chain before it requires is seen at that chain's upstream end, as an earliest bound past its latest or as a fact too late, so every violated constraint is still reported once. An unfixed instant is short when its earliest bound passes its latest; a node's shortfall is the larger of its start's and finish's, with the chain from the seed that holds it back to the seed that caps it. (3) Work whose start is a fact is judged by its finish (F4, F6): its slack is its due minus today; its latest start is the fact itself. (4) `overdue` is unfinished work in scope (not skipped, non-terminal) whose due is before today; a group is unfinished while any such non-group node lies beneath it. (5) A pin on skipped work still bounds its instant: pins are plan, and only work (today) and actuals depend on state.
- Alternatives: (1) estimates holding against actuals (every early finish a shortfall); (2) reporting both sides of a fact (each violation twice, once as "too early"); (3) slack from the actual start (negative forever) or from the chain's latest start (a start date that already passed); (4) waiting for 2.4's group completion (the coordinator's ruling puts `overdue` here); (5) pins on skipped work ignored in execution only (the two layers would disagree on what is fixed).
- What would change it: progress tracking on started work (a remaining estimate would give slack a better reading); 2.4's derived group completion, which may refine (4).

## 2026-10-06, brief 3.1: what a change set's writes mean to the store

## 2026-10-06, brief 3.1: a commit that conflicts twice is answered stale with the revision in flight

- Question: ARCHITECTURE (Concurrency and notification) retries a Turso write-write conflict once, then answers a revision conflict. When the second attempt conflicts too, the commit it lost to is still in flight: no revision has moved yet, so there is no current revision to report.
- Call: the answer is `stale`, listing the target with the revision the in-flight commit is producing (the base plus one), any other revision the patch named that has moved, and the touched set of whatever has committed since. The client's refetch-and-resubmit is the retry; no backoff knob.
- Alternatives: report the revision read (then `expected` equals `current`, which reads as no conflict); retry with a backoff (a knob, and commits take milliseconds).
- What would change it: the multiplayer testbed (6.1) seeing second conflicts often.

## 2026-10-06, brief 1.2: entity creates in another domain's patch advance the deployment revision

- Question: E6 lets an entity create ride in any patch with no deployment revision check, and asks a journey patch that writes an entity reference to name the deployment revision it was validated against. Whether a create riding in a journey patch advances the deployment revision is left open, and the fixtures need an answer.
- Call: yes, once per patch that creates entities (it writes deployment records, and A17's revision counts a domain's changes). A later patch referring to those entities names the resulting revision; a patch referring only to entities it creates itself names none. Each fixture scenario runs in a fresh deployment, and a fixture test checks the rule.
- Alternatives: only deployment-domain patches advance the deployment revision (then a reference check could miss a create that landed in between).
- What would change it: the engine or store (2.1, 3.1) committing riding creates without a deployment revision bump.

## 2026-10-06, brief 1.2: an event's delta is the after-state of the records it wrote

- Question: J1 asks each event to carry "the after-state delta needed to replay it", and J3's replay must be exact; ARCHITECTURE's change set is "entities put and removed by key" for a store that does not depend on the engine. The readiness scout left the delta's representation open.
- Call: one record vocabulary (`Record`, addressed by `RecordKey`, mirroring the Schema outline's tables, with a node field addressable on its own) serves both. An event's delta is the ordered list of `Write`s its mutation made: `Put(record)` as after-state, `Remove(address)` (an address may cover a whole domain, graph, or node), or `CopyGraph` (publishing). Replay applies the writes and re-derives nothing; the change set is the receipt plus the events, and its writes are what a store persists. Side effects (a local-edit marker set by an edit, a snooze cleared by a transition, tombstones written by a removal) appear in the delta as writes, so replay never needs the rules that produced them.
- Alternatives: a typed delta per event type (readable history, but replay re-implements each mutation's effects and must match apply exactly); deltas as full graph snapshots (exact but large).
- What would change it: a store that needs coarser rows than per-field node writes, or history display (J4) needing the mutation as submitted beside its effects, which would add the mutation to the event.

## 2026-10-06, brief 1.2: touched sets by record address, coarse when in doubt

- Question: H5 retries a stale patch automatically when its touched set does not overlap the intervening events', "by key and field"; the scout left the granularity open, and some mutations' effects (create, publish, upgrade, apply a proposal) depend on content they do not name.
- Call: a touched set is a set of record addresses. Node fields, edges, participations, resources, local-edit markers, and each kind of journey state are addressed separately, so an edit and a transition on one node, or edits to two fields, never overlap; a whole node overlaps everything on it (an edge belongs to both ends), so a removal overlaps any change to what it removes. A mutation whose effect depends on unnamed content, and any mutation the dispatch does not list, touches its whole domain: too coarse only costs an automatic retry, never correctness. A transition or answer also touches the node's snooze and answer; proposal edits touch only the proposal.
- Alternatives: per-node granularity (simpler, fewer automatic retries); computing touched sets from the graph at apply (exact but not available to a client deciding whether to resubmit).
- What would change it: retries in the multiplayer testbed (6.1) failing too often, which would refine the coarse cases.

## 2026-10-06, brief 1.2: the file format names a node's parent rather than its full path

- Question: PRD Identity and references says paths are how files refer to nodes. A file could give each node its full path, or its id and its parent's path.
- Call: a node in a file has `id` and `parent` (the parent's path, absent for a root), and every reference (`requires`, conditions, rules, stage bounds, `feeds_milestone`) is a full path. The graph form has the same three fields with `parent` a key, so the two forms share one node type and one wire shape (ARCHITECTURE, File format: one schema). Nodes are a flat list, so parsing never recurses through containment (PRACTICES, No recursion); a canonical file lists them as written, and export (2.7) sorts.
- Alternatives: `path: setup/access` on each node (the path is visible at a glance, but the graph form needs a different identity shape, and a node's id is repeated in its children's paths); nested `children:` (reads as a tree, but recursion in parsing and deep indentation at depth 16).
- What would change it: authors finding parent-plus-id harder to read than full paths in practice.

## 2026-10-06, brief 1.2: mutation semantics the PRD leaves implicit

- Question: the PRD defines what can change but not every mutation's shape; three readings shape the engine.
- Call: (1) start and reach take no date: apply records today (a derive input) and `set_recorded_date` edits it, so a mutation never carries a default the server must trust (F1, F2). (2) A guard bypass is an override mutation applied in the same patch as the transition it covers, so it is its own event as J1 lists ("guard bypassed"), and the engine records the specific failures present on it (D4). (3) In a journey, editing a node's weight or participations is state (B5, glossary), every other field edit is structural, and every change to a route is structural; applying a proposal is structural, since its content is not in the patch.
- Alternatives: dates on the transitions; a bypass flag on the transition mutation (one event, which J1's separate event type argues against).
- What would change it: the engine (2.1) finding a guard bypass in a separate mutation awkward to tie to its transition.

## 2026-10-06, brief 1.2: values the limits table does not name take the nearest named limit

- Question: PRACTICES (Explicit limits) puts a limit on everything, but its table names no limit for keys, client-generated ids, names (entity, route, journey, role and kind titles), emails, choice labels, condition values, reasons, URLs, or for collections such as emails per entity, attachments per node, or entities per deployment. Adding a limit needs the user's sign-off.
- Call: no new limits. Keys and prefixed ids take the id slug limit (64 bytes, prefix included); single-line labels (names, emails, choice titles, condition values) the title limit (256 bytes); free text (reasons, prompts, help) and URLs the body limit (64 KiB). A collection the table does not name is bounded by the serialized graph cap (16 MiB, checked on the graph a patch produces) and, in any document, by the request-body cap (24 MiB), which every parse checks first.
- Alternatives: new named limits (URL 2 KiB, emails per entity, attachments per node), which need sign-off; leaving those values unbounded, which PRACTICES forbids.
- What would change it: a value that is legitimately longer than its borrowed limit (a long URL is the likeliest), or a collection that grows large inside the 16 MiB cap; either becomes a named limit after sign-off.

## 2026-10-06, brief 1.3: 6.1 drives the real HTTP server, on one current-thread runtime

- Question: does 6.1's multiplayer testbed drive the real HTTP server (axum on tokio) under the patina shim, or call the service in-process (PRACTICES, Simulation with patina: Testbeds)?
- Call: the real HTTP server. The spike (`testbeds/spike`, README) runs an axum server and hyper clients under the shim with a clean audit and no allowance, byte-identical repeats, flag-free replay, a passing 16-generation campaign, and 200 seeds of dropped, refused, reset, and delayed connections, all with the faults visibly reaching the retry and deduplication paths. Conditions, from the three patina gaps below: the server and every client run as tasks on one current-thread tokio runtime (not a multi-thread runtime, not a runtime per client thread; blocking `std::net` client threads beside it also work, shown only by a reproducer); a task wakes the runtime every millisecond while delayed-delivery faults are on; network faults run as explicit knobs (`cargo patina explore run` or `run`), not `campaign --faults`. So 6.1's "N client threads" are N client tasks (6.1 brief updated), and 4.2 must let a caller serve the API's `axum::Router` on a runtime the caller builds (a function from the composition root's `Service` to a `Router`), so the testbed and the binary differ only in the runtime around it.

## 2026-10-06, brief 1.3: [patina] a delayed TCP segment does not wake epoll_wait

- Question: do patina's network delay knobs (`--net-latency-nanos`, `--net-jitter-nanos`, a drop's retransmit backoff) work for a tokio guest?
- Call: only with a timer keeping the reactor awake. A segment whose delivery time passes while the reader blocks in `epoll_wait` is delivered at the reactor's next wake instead: 1 ns of latency makes a ping-pong under a 1 s timeout take the full 1 s of virtual time, and with no timer armed the shim aborts (`a shim lock was re-entered by the thread that holds it (a signal handler ran over shim code)`). Blocking `std::net` reads are delivered on time. The spike's `--tick-ms 1` task bounds the lag to 1 ms; with it every delayed run passes. Patina's `pubsub` testbed passes its latency leg because its heartbeat timers do the same. Reproducer: `testbeds/spike/README.md`, gap 2.
- Alternatives: no delay faults for tokio guests (loses the timeout and retry paths 6.1 exists to test); a larger attempt timeout (delays then always cost a full timeout, which is a different fault than the one configured).
- What would change it: a patina fix; then the ticker is dropped and the `delayed-delivery` gap leg starts failing.

## 2026-10-06, brief 1.3: [patina] campaign --faults is unusable for a TCP-only guest

- Question: can `mise run sim` sweep network faults with `cargo patina campaign --faults`, as PRACTICES' campaigns assume?
- Call: not at the pinned revision. The `--faults` bands draw `--net-duplicate-permille`, which acts on datagrams only, in every generation; a TCP-only guest applies no duplicates and every such generation is classed `VACUOUS_NET_FAULT` (4 of 4 in the spike), with no spec field to drop one band and no `classify` rule that can override a vacuity class. The vacuity class also masks the guest's own outcome: generations whose guest gave up (exit 4) are still `VACUOUS_NET_FAULT`. Separately, the vacuity diagnostic is a zero-count test, so a live knob that draws no effect by chance is reported inert (seed 158 of the spike's sweep: 0 refusals in 55 connects at 100 per mille). The spike's campaign therefore runs `--buggify --sched-pct`, and network faults run as a seeded explicit-knob sweep (`cargo patina explore run`); 6.1 does the same.
- Alternatives: give the guest a UDP side channel so the duplicate knob fires (a guest change made only to satisfy the classifier: green by construction, rejected); `--allow-unmet-sometimes` or similar waivers (none covers vacuity).
- What would change it: a patina revision that bands datagram-only knobs only for guests with datagram traffic, or lets a spec deselect a band; then the spike's campaign adds `--faults` and the `campaign-faults-vacuous` gap leg starts failing.
